## Contracts and boundaries

`@tt/application/ports/catalog-records` defines 25 explicit normalized source-record families: canonical entity facts/identifiers/aliases/relationships/plant codes; vehicles/lookups/reviewed links/code values; fitment configurations/axles; models/SKUs/availability/evidence/prices/components; climate/rules/advice/citations; recalls/source targets/mapped targets. Values preserve nullable unknowns, known zero/false, exact decimal strings and bigint money/counts. Required nullable fields cannot be omitted. Schema-bearing records currently accept version 1 only. These are internal normalized source contracts, not verified engine recommendations or API responses.

`ports/catalog` exposes a pinned manifest and typed keyset pages with provenance and current license rights. `ports/ingestion` separates dataset/run registration, leases, staging and materialization from validation, manifest publication and privileged reverse-dependency reads. The unused 009 catalog/import prototype ports are refined; report/permission/source-fetch contracts remain. No shipped external API changes. Fact-family descriptors use a fixed table/column/codec allowlist; runtime caller values are always parameters. SQL/driver objects do not cross application ports.

Public fact projections omit reviewer identities, private source details and source notes. Pins report available/partial/unavailable licensed components, not verified coverage or recall clearance. Empty results preserve uncertainty. Stored published datasets remain immutable; an explicit bundle pin does not drift when the market head advances. Current license/provider checks still apply to old pins. License expiry is distinct from evidence freshness; source freshness and the current recall safety overlay are S3 policy. Snapshot/derived rights are exposed for policy checks, never inferred from a successful public read.

## Database capabilities and compatibility

Additive `0012_catalog_access` leaves all applied migration bytes/checksums unchanged. History becomes 12 app/two CMS migrations; inventory becomes 120 app/28 CMS tables and 31 app views. No package versions, lockfile, CMS schema, product routes or UI change.

| Role | Capability |
| --- | --- |
| `tt_catalog_runtime` | Registry and security-barrier published catalog views only; no raw catalog, license, staging, staff or privacy tables |
| `tt_ingest_runtime` | Source metadata reads, immutable identity registration, staging-only fact inserts, run/lease/checkpoint writes and materialization ledger; no publication/head/audit writes |
| `tt_publish_runtime` | Validate datasets, create/publish manifests, CAS market heads, publication receipts and outbox; read matching approval/staff state and reverse dependencies; no source fact edits, license edits or private contacts |

The general app/staff/asset roles gain no catalog authority. A narrowly granted security-definer function with fixed search path locks only the supplied manifest's source rows and licenses; it does not return private data or permit license edits. Published views require active provider, reviewed/effective/unexpired version-1 license and explicit display/API rights. Publication also requires derived/snapshot rights; staging requires cache rights. This deliberately conservative initial policy requires S3 source-policy review before activating a provider. No local fixture license grants rights to real data.

Stored fact rows have a 64 KiB serialized-row bound, and published manifests have at most 16 components, including direct privileged SQL paths. `app.import_materializations(run_id,row_number,record_kind,record_id)` binds each accepted normalized row to its inserted fact in the same transaction. Its composite FK prevents premature staging deletion; the later retention worker must delete ledger rows before expiring staging. It is internal persistence metadata with no reader-role access. Existing S1 recovery tests include the new inventory, grants and objects.

## Import and publication protocol

1. Register a dataset using immutable provider/kind/external-version identity and checksum/license/times, then register one run for that dataset with provider/upstream key, mapping/schema version and content hash. Exact retries return the existing identity; changed identities conflict. Source adapters must give flattened child records stable unique keys (their IDs where there is no source-record-key column).
2. Acquire a 1–300 second lease. Each acquisition increments the fence and revision; expired workers cannot write. Resume from the persisted `throughRow` checkpoint. Validated runs can reacquire a publication lease without reverting to staging.
3. Stage contiguous batches of 1–100 rows, at most 256 KiB total and 16 KiB normalized data per row. Expiry must be future and within 30 days. Repeated source keys become duplicates; exact completed-range replay is a no-op. Any changed replay or checkpoint gap conflicts. Rejected/duplicate rows block the initial strict complete-publication path; a corrected import uses a new source version/run rather than editing prior facts.
4. Materialize typed records only from matching accepted, unexpired staged content and source key. Fact inserts and ledger writes commit together; identical retries do not insert twice. A failed row rolls back the entire batch. Once validated, ingestion-role fact inserts stop.
5. Validation requires the asserted complete input count to equal accepted, staged and materialized counts, with no rejected/expired rows. The repository proves persisted completeness relative to that count. The future source parser/use case must establish upstream completeness; passing `complete: true` is not proof of an authoritative feed or source license review.
6. Create an immutable sorted manifest hash. Publication locks the run, bundle, datasets and licenses; checks required component keys/kinds, current rights, active actor and a prior approved audit record bound to the manifest digest; verifies cross-dataset references resolve inside the manifest. Full staff MFA/RBAC, approval issuance/separation of duties and source validation remain S3/015–016; workers cannot create their own approvals.
7. In one SQL transaction, publish validated datasets/manifest, compare-and-set the head by both prior bundle and revision, write durable publication receipts, add one outbox event and finish participating runs. A stale/ABA head or any error rolls everything back. Caught repository exceptions poison the transaction. Replaying a successful receipt returns its bundle without moving the head again or duplicating the event. Delivery of the outbox event and safe retry/reconciliation policy remain S3.

`affectedBundles` reads published reverse dependencies under the publisher role even after license revocation, supporting later invalidation. It cannot become a public route. Cursors bind the lookup kind, bundle/market and filters; cross-scope cursors fail. Source-key filters permit exact provenance lookup without exposing arbitrary SQL.

## Performance and verification

Catalog pages request at most 100 items plus one lookahead, in one statement. Each manifest contributes at most that many rows to the outer merge, with at most 16 members. The query uses indexed filters/keysets and bounded transaction/statement/lock deadlines; it makes no N+1 per-item calls. The 20,000-SKU synthetic benchmark checks all 1,000 selected IDs across 10 pages, row bounds, heap growth and the SKU index plan. PostgreSQL may scan/sort all matching rows inside the security-barrier view before its limit; this is recorded rather than claimed to be constant-cost. Production-scale cardinalities, all query shapes and pool concurrency must be profiled again at S2/013 and S6/042. Indexes cover current vehicle/alias/lookup/SKU/evidence/price/recall/code/entity lookup paths; they do not promise performance for arbitrary filters.

The [validation record](evidence/P1/p1-pr-010-validation.md) includes TDD failures, real-role round trips for all 25 families, exact large money, unknowns, ambiguous aliases, staggered fitment, unresolved recalls, SQL-injection literals, partial/coherent manifests, rights revocation, caught-error rollback, lease fencing, publication contention/ABA and query/memory evidence. Coverage runs unit/use-case and real database projects together; thresholds remain unchanged. No UI/API/provider functional test is claimed because those entry points do not exist in this slice.
