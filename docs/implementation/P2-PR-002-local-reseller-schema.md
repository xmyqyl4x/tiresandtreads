The ordinary 33 app and three CMS migration manifests, P1 generated models, bootstrap/CLI/preflight, runtime role inventory, admission policy, packages/dependencies and historical evidence are unchanged. The only existing-table DDL in the opt-in database is an additive unique `(id,owner_subject_id)` key on `email.email_sends`, used for same-owner send FKs. No P1 business row or existing table permission is rewritten. The fixture compares all 141 entries in the P1 table inventory: 140 complete data-table snapshots and the original 33-row migration-history prefix. ## Relational and access design

| Area | Implemented local integrity |
| --- | --- |
| Organizations and memberships | Explicit pending/active/suspended/closed state, verification status, market, current actor membership, immutable tenant identities and transaction-local scope |
| Agreements/assets/verification/locations/domains | Same-org asset/actor FKs, typed asset purpose and readiness, versioned noncharging pilot/privacy/DPA terms, private verification evidence, approved business addresses and reviewed expiring domains |
| Offers and targeting | Same-organization deferred published-version pointer, distinct creator/reviewer, minimum three-day interval, seven specified discount types and bounded typed money/percent/service/minimum-purchase fields; typed geography, SKU/model/brand/category/rim/size/vehicle/tier targets |
| Publication | Reviewed terms/targets cannot be changed; current pointer cannot retain a retired version. Eligibility rechecks current active verified organization, all three accepted terms, target market, validity, domain and logo readiness |
| Pools and codes | Shared encrypted pool text is distinct from exclusive generated/unique code entries; stable HMAC identities, same-tenant/version/pool chains, deduplication, bounded ciphertext and expiry; no plaintext code column |
| Assignments and decisions | Same-owner send FK; one live exclusive-code assignment, one organization per send and slots 1–3. Immutable decision identity/reasons; explicit reservation state and definitive release evidence |
| Frequency and caps | Stable global subject/scope guards, explicit rolling/calendar windows and saved policy version. A new reservation checks the current guard policy under a row lock; later policy changes preserve old evaluation identity. Configured cap/window identity is immutable; counter bounds survive concurrent updates |
| Redemption/corrections/disputes | Idempotent reported events, same-assignment correction/reversal FKs, no verified-sale claim, no exact shared-code redemption attribution, same-tenant dispute/resolution parents, encrypted details and append-only event history |
| Insights | Reuse P1 consented visitor capture; add only organization aggregate storage. Tenant projection suppresses small/unreviewed/foreign/dirty or old-generation cells and omits recipient/send/code/visitor identifiers |

All 23 new tables have forced RLS. Partner-owned children use organization FKs and compound tenant parent keys; the two cross-organization frequency tables remain worker-only. Three actual synthetic runtime logins have no table ownership, superuser, inheritance, database/role creation, replication or RLS bypass. Tenant reads require organization plus current active actor membership. Column grants withhold private asset links, shared-code secrets and individual assignment/frequency/decision/aggregate-source data. Existing P1 runtime roles receive no `partners` access. Current default P1 roles and the actual staff/identity provider are not changed.

Context is a server trust boundary, not external authentication. Future services must derive organization/actor from verified authority, set it transaction-locally on one connection and keep runtime credentials private. The tests do not claim an end-user cannot impersonate an actor if those server credentials and arbitrary SQL were exposed.

## Concurrency, retention and later service obligations

Native races use separate real worker connections. Exactly one of two assignments wins the last exclusive code; the loser gets the live unique constraint. Exactly one competing counter increment consumes the last cap unit; the other violates the bound. These are storage proofs, not an implemented complete coupon allocator. S2/S3 must lock guards/caps/codes in the documented order, recheck consent/eligibility, and atomically coordinate code state, all cap/frequency reservations, assignment and immutable delivery selection. Source/provider uncertainty is never released by elapsed time alone. Cryptographic envelope validation and key rotation belong to the actual provider adapters and acceptance review.

Target inserts/edits hold a shared parent-version row lock until their transaction ends, so concurrent review/publication waits for the edit; edits after review fail. Issued frequency usage is terminal and cannot return to reserved or uncertain before release. Corrections/reversals require an already visible parent in the same assignment, including bulk inserts; ordered parent-first reversal quantities must cancel exactly. Redemption URLs require a non-null matching verified HTTPS authority, default port or explicit 443, and no backslashes. These are local storage checks; external URL resolution and redirect validation remain service responsibilities.

Current-version selection also holds that version's shared row lock through commit, serializing it with retirement in either transaction order. Every state-reading insertion guard requires its parent to be visible before validation: target version, evaluated frequency policy, redemption reservation and correction predecessor. A data-modifying CTE cannot supply that parent later in the same statement and bypass the state check. These cases fail atomically; parent-first valid inserts remain supported.

The aggregate query uses an organization/generation/day index with a bounded 51-row page over 10,000 synthetic records. Timing is a local observation, not a production SLA. A local cohort floor of ten demonstrates suppression; actual privacy thresholds and publication authorization remain unconfirmed. New aggregate generation, invalidation and rebuild services still require implementation and privacy acceptance. Raw P1 analytics ingestion is not extended or duplicated here.

Restrictive FKs intentionally expose the future private-data dependency graph. Existing P1 erasure is not claimed to purge partner assignments, frequency records or disputes. P2 privacy/service integration must define and test ordered purge, permitted audit retention, cancellation, generation invalidation and restore/deletion replay before real data or promotion. Normal runtime roles cannot delete or rewrite history; privileged controlled privacy purging remains future work. No money ledger, charging, webhook/API credential system or automatic billing conversion is added.
