November 15, 2026. This is a separate engineering cycle for the existing staff/consent API card. It does not appoint operators, activate an account, change production bootstrap/CLI/preflight/policy or accept a provider/hosting/live gate. All six S3 gates stay open; HS01–HS08 proposed, operators/coverage/rates unconfirmed, specialist/licensed work pending. No provisioning, purchases, actual recipient notifications or live provider/model effects.

## Verified identity and current authority

The original local API accepted only explicitly synthetic opaque grants. That remains useful test support but does not implement the approved AS05 Clerk integration. The new opt-in server adapter uses pinned `@clerk/backend` 3.29.0 `authenticateRequest` with explicitly supplied retained public keys, issuer, audience and authorized parties. It accepts session tokens only, with the current SDK's signed session category, version-two claims, valid signature/time and a recent verified second factor. Template, machine, impersonated, pending, wrong-instance/origin/audience and missing/stale-factor tokens fail closed. The rounded factor age is interpreted conservatively; it adds no MFA grace. The existing five-minute recent-MFA policy remains unchanged.

A namespaced hash of the configured issuer plus the verified provider subject selects a pre-existing active database identity. A current, non-revoked, already effective local role with permissions must exist. Neither a JWT role claim nor a supplied staff UUID/MFA timestamp grants authority. Mapping is read-only and never creates a user or role. The parameterized, unique-subject lookup uses an explicit existing `tt_staff_runtime` scope; an elevated or different scope is refused. The runtime accepts an already bounded transaction scope rather than opening a new unbudgeted pool. A future host composition must reserve that identity lane explicitly; the current service-host budget and production composition are unchanged.

The identity transaction finishes before a fresh bounded GET of the verified session's fixed Clerk resource. Current status, subject/session binding, expiry and abandonment must remain valid. The approved maximum is **12 hours absolute and 30 minutes idle**, not the separate synthetic grant's stricter local limit. The existing business services still check current database permissions on every operation, including after authentication. Session results are not cached. A three-second outer deadline, abort checks between awaits, bounded 64-KiB JSON reader and fixed read URL prevent late lookups from dispatching later provider reads. Secrets/tokens/private keys and provider session bodies are not logged or returned.

The ordinary owner/reseller verifier stays independent. API access declarations select the staff verifier; its refusal never falls back to an opaque local grant or owner credential. Existing compositions without a dedicated verifier retain their local fixture behavior. When the Clerk adapter is explicitly disabled its staff realm refuses all credentials. The two-person reviewer path selects the same dedicated verifier and preserves current, distinct reviewer permissions. CSRF is server-derived from the verified issuer/user/session and retained secret, stable across token refresh and different across sessions.

## Scope, tests and acceptance

The dependency is explicit and pinned. The lock adds Clerk and its eight transitive packages; existing resolutions are unchanged. One existing Smithy deprecation description refreshed during lock generation; no Smithy version changed. An exact old/new lock digest advances the read-only evidence reconciliation without rewriting historical manifests or receipts.

A generated-key positive control failed before implementation; the SDK also exposed that synthetic tokens missing its current category are not session tokens. Final focused verification passes 51 real-signature/session adverse controls, 29 HTTP core cases and four retained console contract controls, plus five actual PostgreSQL/HTTP/service cases (89 executions). Strict TypeScript checking passes at the existing 1,536-MiB heap budget. Tests cover retained-key rotation without key fetches, bounded stalled reads, timeout with late lookup refusal, immutable configuration, stable/session-separated CSRF, exact 12-hour/30-minute boundaries, route-selected realms and no fallback. Real PostgreSQL controls prove disabled identities, removed/future grants, independent service permission denial, wrong database scope and freshly revoked provider state. The synthetic provider read also observes zero identity connections idle in transaction.

All identity tokens and provider responses in this proof are locally generated synthetic fixtures. No Clerk account, sign-in, notification or live API read occurs. Actual provider enrollment, MFA methods, accepted key/issuer/audience settings, revocation/idle behavior and independent identity/security review remain acceptance inputs. The API composition is callable and tested but is not a deployed staff SSO session. Browser sign-in/refresh/reverification and private proxy transport belong to the separate P1-PR-039 follow-up. Payload's native admin/REST/GraphQL access remains denied; its internal sealed Local API continues behind the current editorial service authority, not a new alternate password login. Full exact-source Linux validation, a fresh review, all nine PR checks and all nine main checks are required before reporting this cycle complete.
