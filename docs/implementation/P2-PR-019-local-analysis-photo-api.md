# P2-PR-019 — Local owner analysis and private photo HTTP APIs

These opt-in adapters expose the shared analysis/photo services through the existing loopback HTTP boundary. The owner authorized local implementation, validation and merge of cards018–020 while actual service/API acceptance and all existing deployment holds remain. No production host, provider/model choice, role assignment, frontend or external account is activated.

Owner analysis endpoints request optional processing for an exact immutable report/version, read request status, read the current permitted attachment with its revision, and change processing permission with an expected revision. The wire accepts an approved policy ID, explicit processing choice and exact notice version; it accepts no prompt, provider/model override, owner identity, source URL or caller command identity. The idempotency header supplies the shared command key. Share-only and other-owner callers cannot invoke processing or read its output.

`createLocalReportAnalysisRuntime` checks its explicit local mode, unit-of-work binding and existing analysis service role, then composes the reviewed SQL cost plan, bounded retry/circuit execution, exact command/reuse cache and fresh-scope erasure protection. No default host uses it. HTTP requests persist work; they never directly dispatch a model. Missing/exhausted admission cannot charge or call a model. A missing, stale or exhausted reviewed plan terminalizes work as unavailable without dispatch; a temporary in-flight concurrency limit can leave it pending. Terminal refusal/expiry is reflected in status. The shared worker owns dispatch, reconciliation and unknown-charge handling.

The analysis states are `not_requested`, `pending`, `available`, `unavailable` and `expired`. Decline creates no AI work. Available output contains validated selections over deterministic report facts or a permitted reviewed generic explanation; it cannot rewrite eligibility, rankings, prices or immutable report snapshots. Other states carry null output. Attachment reads reauthorize the owner/report and use the existing current-permission/source/expiry-filtered projection. They return an exact revision for a later explicit frozen delivery selection, or an unavailable/null attachment. No attachment revision is silently attached to a send.

Exact reuse includes owner/purpose permission and invalidation revisions, report/version, authoritative input/data/rule/configuration/prompt/schema/validator/canonical versions and current source/expiry rules. A new valid command may find the same permitted exact work/artifact without a second model call. A duplicate HTTP admission returns409 for fresh authorized reconciliation; it never replays a cached permission or blindly repeats an uncertain effect. Private owner results are not shared across owners. Periodic generic refresh remains a separately reviewed worker operation.

Photo endpoints create a bounded capture, reserve an owner-bound upload intent, upload/finalize bytes, queue sanitized extraction, read candidates, explicitly confirm/correct a supported field, request deletion and explicitly save under a reviewed retention plan. Binary finalization uses `application/octet-stream`, at most10MiB, and a grant in `X-Upload-Grant`; it accepts no file path, URL, SVG or grant in a query string. The common boundary permits only two concurrent binary body readers. Shared services recheck ownership/grant/hash/magic bytes, capture/daily/active byte quotas, current processing permission and source/policy state. Required scanning and the bounded isolated decoder precede extraction; only sanitized bytes reach its transport. Original/sanitized objects remain encrypted/versioned/private, and no image/object-store URL is returned.

Candidates are suggestions. An explicit supported field/value, candidate ID or manual choice, and confirmation revision creates a separate confirmation history entry. Neither extraction nor status reads apply fields to a report/form. Unsupported condition/roadworthiness claims are rejected, partial DOT remains unverified, and manual entry stays available. The deterministic assessment service remains responsible for validating a later user-submitted assessment.

Photo deletion resolves the current owner's target internally and calls the full journaled analysis lifecycle. It returns202 with an opaque job ID and cleanup pending after processing denial/erasure intent commits. It does not use the older image-only removal shortcut or execute provider cleanup inside HTTP. Reads stop immediately; the separately composed worker drains original/sanitized objects, candidates/confirmations, AI work/artifacts/reuse, provider references and SQL leaves subject to holds and charge reconciliation. Existing report facts remain unchanged. A retained/saved image needs an explicit matching reviewed save notice/plan; default unsaved retention remains24hours and the reviewed extension is at most30days.

Private response schemas project nested candidate, confirmation and analysis DTOs explicitly. Future internal metadata does not become a wire field. Dates, revisions, counters, sizes, arrays and enum states are bounded; an invalid private service result becomes an opaque unavailable response. Available/null state inconsistencies are refused. Prompts, manifests, provider references, raw SDK outputs, object coordinates, billing details and unrelated owner identities are absent. Private replies retain no-store/noindex/no-referrer, CSRF/Origin, quotas, opaque errors and durable SQL command admission from card018. No new migration, dependency, default manifest/model, production bootstrap/CLI/preflight/policy or runtime-composition change is introduced.

The dedicated command is `node tests/fixtures/phase2/analysis-http-run.mjs`. It performs strict Linux typing and real listening HTTP/PostgreSQL journeys with encrypted versioned local storage and the real isolated codec. Identity/scanner/model/provider/journal evidence remains synthetic; a bounded in-memory signed journal is not off-host custody or independent durability. Full exact-commit regression, build, coverage, P1 HTTP/browser behavior, schema, recovery and deployment/capacity/observability checks run separately; actual PR/main results are verified before and after merge.
