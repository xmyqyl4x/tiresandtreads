It uses only `HeadBucket`, `GetBucketLocation`, `GetBucketVersioning`, `GetBucketEncryption`, `GetPublicAccessBlock`, exact-version `GetObject`, `DescribeKey` and `Decrypt`, then a local workflow health GET. It never creates, publishes, sends, grants, repairs, adopts, retries an unknown effect, mutates a database or invokes business-service work. Object bytes are bounded to 1 KiB and the body is closed; decrypted canary bytes are cleared in `finally`.

Results contain only local scope, `compatible`/`incompatible`/`configuration`/`unavailable`, fixed finding codes and the fixed false hosted-acceptance/external-effects flags plus no-send status. Keys, ciphertext, bucket/account/endpoint identifiers, raw service errors and canary bytes are omitted. `compatible` means these local checks passed, not that actual IAM, an ESP or a hosted service is accepted. Unavailable/ambiguous dependencies refuse with no remote fallback; no acceptance is inferred from metadata alone.

## Signed callback proof without a deployed route

The [signature probe](../../packages/integrations/src/provider-preflight-workflow.ts) uses the pinned Inngest SDK's public Web API `serve` adapter in explicit signature-verification mode (`isDev: false`). This is an offline protocol test, not cloud authentication: it supplies a synthetic `signkey-test-…`, fixes its base origin to the local fixture and denies every SDK outbound fetch. No functions or HTTP listeners are created and the existing worker/host are unchanged.

Only an in-process POST Request to the fixed local URL with the pinned SDK's `probe=trust` query is admitted. GET/PUT/sync, function-dispatch, product and remote URLs refuse. Bodies are bounded to 8 KiB and a two-second deadline; the SDK receives an explicit trusted local Host header, and its raw response/error is replaced by masked local verification status. The pinned protocol probe must be regression-tested on any SDK upgrade; it is not a general callback interface or production readiness path.

Actual SDK verification accepts a current signature and refuses missing/wrong-key, semantically tampered and stale signatures even when a development-mode environment variable is inherited. Its explicit primary and fallback are the same synthetic key: an unrelated inherited fallback authority is refused. The tests assert zero global fetch calls. The development server itself does not demonstrate signed hosted callbacks. Timestamp checks do not deduplicate an otherwise valid request within the freshness window; no function/effect is executed by this probe. Existing SQL inbox/job idempotency, fencing and workflow replay regressions remain required, and actual hosted replay/ingress acceptance remains pending.

## Reproducible local command

```sh
pnpm verify:provider-preflight
```

Run from the repository root with the existing Node/pnpm/Docker Linux prerequisites. The command accepts **no target or credential arguments**, creates one randomly scoped internal-network test project, builds the pinned tooling and starts only Moto/Inngest. Fixture setup creates new disposable synthetic buckets, key and canaries after refusing existing/unavailable bucket targets. These setup/fault-injection writes belong to the test harness, not the read-only inspector. Cleanup removes that project's containers/volumes/env file in `finally`; no new dependency/install is required.

The test tooling's existing TLS-volume declaration may create an empty disposable volume; this diagnostic starts no PostgreSQL, app or TLS certificate-generator service. Retained dev/stage Docker configuration, native PostgreSQL, existing credentials/data/keys/journals/provider manifests and all runtime endpoint guards are unchanged. No retained file or dump is exported. The default service host continues using its existing local adapters; this preflight is not a hosted composition factory or a runtime configuration migration.
