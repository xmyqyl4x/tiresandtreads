## Access, callbacks and readiness

The [test-only TLS ingress](../../tests/fixtures/deployment/server.ts) is a disposable fixture in the tooling image, not a production proxy/configuration or product route. It loads only fixed local files, uses a fresh CA and TLS 1.2 minimum, and pins the fixture operator certificate fingerprint for `GET /health/ready`. A client with no certificate, an unrelated certificate, a different certificate signed by the same trusted CA or forged forwarding headers cannot acquire operator access. Incorrect Host headers refuse. Exact raw route/method matching denies products, staff UI, sync, traversal/alternate paths and unapproved queries even to an authenticated fixture operator.

Only `POST /internal/preflight-inngest?probe=trust` has the separate machine-signature boundary. It reuses the [SP03 pinned SDK verifier](../../packages/integrations/src/provider-preflight-workflow.ts), translating only to its fixed in-process URL. Both primary/fallback signing authority are the same fresh synthetic key; development-mode inheritance is refused, no functions/listeners are registered by the SDK and all SDK outbound fetches are denied. This is a real signature verification probe transported over local TLS, not a deployed business callback, workflow sync or actual provider connection. Valid repeated probes can authenticate within the freshness window; there is no effect to deduplicate. Durable business replay/effects and actual hosted callback acceptance remain separate obligations.

Callback bodies are capped at 8 KiB, including chunked bodies, and two seconds for body receipt; HTTP/TLS headers and requests are bounded. Private responses are masked, `no-store`, `noindex` and `no-referrer`. Raw errors, keys, certificates, DSNs and body contents are not published. Wrong CA, hostname mismatch, expired certificate, plaintext transport, missing/wrong/tampered/stale signature, oversized payload and unapproved route/method inputs refuse.

Readiness loads a fresh, bounded selection file and requires the exact reviewed fixture expansion digest. It checks app/CMS database reachability using the existing `tt_app_runtime` / `tt_cms_runtime` identities and the selected runner's actual health, with fixed internal destinations, redirect refusal, bounded deadlines and connection cleanup. Unknown, malformed or oversized state refuses. The TLS container's TCP liveness check only waits for a listener; it is not evidence of certificate validation, database readiness or operator authorization. The actual TLS/access tests supply those separate proofs.

A fixture-only, fixed-search-path database function returns a boolean comparison against the protected app/CMS migration-history snapshots and the additive column. Runtime roles can execute this read-only capability but cannot read the snapshots. Actual checksum drift in either database withholds readiness and signed callbacks until restored. The ingress receives only runtime DSNs in a private read-only fixture file; neither it nor the production runners receive migration/admin database environment variables. This disposable capability introduces no production migration or grant and still needs a production readiness design before actual hosting.

The fixture ingress mounts the state and secrets read-only. Only the local test controller can change selection; it performs an explicit file replacement after admission. All fixtures share Docker/root authority and are not an independent security/failure domain. Client certificates do not supply actual staff/MFA acceptance, approved operator staffing or production secret custody.

## Migration and rollback meaning

Setup creates separate disposable application/CMS databases, uses the existing ownership bootstrap and reviewed 33 / three migration histories, and captures full history rows. Production runner startup receives no migration credentials and runs its existing `node start.mjs`; it does not execute schema push or startup migrations. App/CMS history remains unchanged across startup, outage/recovery and image rollback.

The additive fixture creates `deployment_fixture.release_state` with a sentinel row, then adds one nullable column under the existing restricted-owner [migration lock](../../scripts/database/migrate.ts). A competing executor fails before its callback can run; lock release permits the controlled expansion, and a repeat is a no-op. Only the exact source/hash of this synthetic statement is admitted. Arbitrary, appended or destructive SQL is refused. This is an exact fixture allowlist, **not a SQL safety scanner or a claim that all historical production migrations are expand-only**. New production migrations require individual review, compatible old/new contracts and selected-host proof.

The runner stops PostgreSQL and proves readiness/callback refusal, restarts the same disposable DB, stops the candidate image and proves continued refusal with no automatic fallback, then explicitly selects the running previous immutable image. Readiness returns only after the selected backend and both runtime database lanes succeed. The rollback test verifies exact app/CMS migration history, original sentinel data and retained nullable column; no down migration runs. Product routes remain denied throughout.

These images are the existing headless foundation runner, with product APIs/frontends still held. Its image rollback plus the database compatibility probe does not prove rolling upgrade compatibility of a complete future business/API host, all physical pools, real traffic/callback drain, production providers or selected-host capacity. Those remain actual SP05/SP06 and later-stage acceptance work.
