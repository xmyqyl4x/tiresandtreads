## Application boundary

`createReportServices` composes the accepted owner/report/capability repositories, durable command receipts, the 017 engine, 018 pricing and narrow evidence/encryption/cryptographic ports. It exposes these channel-neutral operations:

| Operation | Behavior |
| --- | --- |
| `create` | Normalize driver answers, compile current evidence, evaluate and atomically create a report/version/receipt |
| `saveDraft`, `refine` | Optimistic draft revisions; rerun the exact selected draft into a new immutable version with an answer/data/rule-aware diff |
| `readOwner`, `readShared` | Fixed historical output plus a separately checked live safety overlay; share recipients receive a read-only allowlisted DTO |
| `saveQuote`, `readQuote` | Owner-scoped structured quote values and context-bound encrypted product/shop text; decrypt outside SQL and recheck authority before returning it |
| `compare`, `readComparison` | One to four unique catalog-plan/owned-quote references; immutable comparison revisions pinned to an exact report version |
| `share`, `revoke`, `fork` | Explicit fixed/latest version scope, optional chosen fixed comparison, revocation and a fresh assessment under the recipient's own owner capability |
| `ownerDownload`, `sharedDownload` | Short-lived grants for an existing registered ready PDF with matching report/version/view/comparison scope |

Transport supplies audience-separated verified key digests, never a client-authored `Owner` object, source snapshot, approval flag, policy, score or report output. Requests use exact fields, canonical IDs, decimal money/revision strings and explicit quantities/bases. Unsupported fields and paid terms fail validation. HTTP, cookies, Turnstile, CSRF, rate limiting, public wire/OpenAPI contracts and browser rendering remain S4/S5 responsibilities; the running web host still exposes only the accepted health contract. Anonymous owner-session establishment remains an authentication-adapter concern using the accepted owner repository, before these owner-scoped commands.

`createReportRuntime` is a callable headless composition with explicit bounded scopes for **`tt_private_runtime`**, **`tt_catalog_runtime`** and **`tt_report_source_runtime`**. It checks the actual database roles. The caller owns pool admission, aggregate connection budgets, secrets and shutdown. The source metadata role can verify existing connector approvals, licenses, published receipts and freshness; it cannot import facts, advance feeds, publish bundles or access private notes. Its `UPDATE(id)` grant permits PostgreSQL row locking only; the existing identity trigger prevents ID reassignment. No ingestion credential is required by the report process. Hosted pool sizing and transport activation remain later deployment/API gates.

## Transactions, idempotency and snapshots

The service first authenticates and looks for a completed command. New work resolves catalog/source evidence or encrypts notes **outside the private write transaction**. It then rechecks current evidence, reauthenticates, claims the durable command and atomically commits the private mutation and safe receipt. Report publication pins bundle/rule/engine/schema/scoring/data versions, normalized inputs, exact evidence/prices/product-display facts, structured reasons and output. Indexed report items retain the at-most-five picks; full decisions/exclusions remain in the bounded output snapshot.

Receipts are scoped by owner subject (or share capability for shared PDF), operation and idempotency key, with a versioned canonical body HMAC. They store scalar resource/report/version/revision/expiry/key-version references, never bearer tokens, answers, free text or snapshots. Replaying a successful create/refine/compare returns its original version/revision, even after later edits or a data outage. A different body, expired receipt or stale optimistic revision conflicts. Current authority is checked before replay; a revoked/expired share or download is not resurrected. Receipt failure rolls back the report and claim. Commit uncertainty retains the existing retry-with-same-key semantics.

Refinement reads the selected draft/base version, recomputes against current approved evidence and checks both report and draft revisions again at commit. Publication removes the draft atomically. Historical versions never change. Diffs distinguish answers, dataset/bundle changes and policy/scoring/engine changes; score deltas are not comparable across different scoring rules. Comparison creation also rechecks selected quote revisions after evidence work, so a concurrent quote edit cannot silently change the saved result.

Owner activity refreshes report retention to 180 days, capped at one year from creation, without changing the content revision used by optimistic editing. Shared reads never renew that activity. Drafts expire within seven days, private quote text within 30 days, shares within 30 days and downloads within 15 minutes, clipped to the relevant report lifetime where applicable. Parent expiry or revocation can end download access before the grant’s 15-minute upper bound. Expired/restricted/deleted authority fails closed. The later privacy/retention jobs still own physical purge and deletion completion; activity tracking is not a claim that those jobs are implemented.

## Current evidence and safety

Migration **0023** adds `report_policy_heads(market, region_key, rule_version_id, revision, updated_at)`. It points to the current published policy while retaining the existing immutable `rule_versions` documents. The restricted `report_policies` projection verifies published schema, active reviewer, reviewed time and region binding; the repository checks the review deadline. Moving a head does not edit an older rule or report. There is no duplicate policy document or approval store. An actual reviewed policy and controlled head publication are required before real-source acceptance; fixture staff identities are not specialist approval.

The repository-backed resolver pins one current complete market bundle, checks all five display/API/cache/derived/snapshot rights **before storing any source-derived snapshot**, and requires explicit reviewed freshness windows. It loads exact configuration/axle constraints, SKU/model facts, availability, SKU-level measurements, regional climate/guidance, prices and current recall mappings. Bounded batch reads avoid query-per-SKU work: at most 200 lookup identities, 2,000 related records and 100 explicit reviewed model-pair plans; incomplete pages or overlarge portfolios fail rather than silently truncate coverage. Model-family evidence does not transfer to a SKU. Unknown seasonal markings and absent authorized partial-replacement inspections remain unknown. No generic AWD limit, life, size equivalence or vehicle fitment is invented.

Recall readiness uses the existing connector approval digest, current rights, exact published dataset/receipt, successful complete check and 48-hour gate. The engine snapshot retains the **actual source check timestamp**, not the report creation time. An absent catalog recall match never establishes clearance. The current resolver does not manufacture a per-SKU clearance contract: absent mappings remain unknown, and real positive clearance/source coverage remains an acceptance gate. Read overlays inspect current SKU/model mappings and preserve historical known recall warnings during failed or missing refreshes. They do not rerank or overwrite saved scores/prices. A new known match can add a warning; source failure cannot clear one.

All persisted results remain **`purpose: technical_evaluation` / `issuanceAuthorized: false`**. Wiring the resolver does not convert the 98 draft scenarios into reviewed production rules. Licensed providers, actual mappings/coverage, tire-marking/inspection contracts and named specialist review must still be accepted before verified production advice or G1 can close.

## Comparison and private access

Saved comparisons reference catalog plans from the fixed report portfolio or owned quotes. Current evidence is reevaluated separately for those products, and the comparison records its own current dataset/clock context against the historical report version. A product missing from the current portfolio stays unverified. Newly introduced products outside that saved portfolio require a new assessment/version. Fit, climate and price findings stay independent. A known tire with the wrong axle size can be blocked while retaining its known identity; an unknown quote never receives a fabricated match score. Quote quantities, service/tax inclusions and explicit user tax-context confirmation are retained as declarations, not independent verification of tax law or jurisdiction.

Catalog price construction uses only coherent same-retailer/source/date USD offers with unambiguous stored quantities and fixed/per-line tire-subtotal components. Unsupported package counts, ambiguous order-fee allocation or taxable-service dependencies remain unavailable; the 018 core supports richer explicit inputs when a real adapter contract supplies them. There is no cross-retailer cheapest-cart blend or midpoint budget claim. Missing/stale prices cannot win. Ownership-scenario mathematics remains in 018; this comparison command does not invent life/horizon inputs and records that no ownership scenario was requested.

Private product/shop text is encrypted using the existing purpose/quote-ID envelope context before the SQL write, stored only in `privacy.quote_private_data`, and excluded from comparisons, share DTOs, receipts and telemetry. Owner reads decrypt outside SQL and reauthenticate afterward. Shared DTOs select fields from report/product/price/decision snapshots; they never return input budgets, owner/session identities, policy-review internals, rights, source snapshots or private text. Legacy comparison fields are also allowlisted, rather than cloned and filtered by a blacklist.

A share includes no comparison by default. Choosing one requires a fixed report version and exact comparison revision, enforced by a composite FK. Latest shares cannot silently follow mutable comparisons. Forks require an independently authenticated owner and fresh supplied answers; they recheck the source capability at commit and copy no original private answers, quote notes, owner secrets or consents. PDF authorization selects an existing asset with the exact view/version/comparison scope. Rendering/registration belongs to 022; byte delivery uses the existing 014 service's before/after authority checks. Revocation denies subsequent shared reads, forks and derived downloads.

`createReportCrypto` separates bearer audiences and command identity keys. It derives 256-bit HMAC capability values from random capability/grant IDs and retained key versions; tokens are returned only after commit/current authorization and never stored in receipts. A separate stable identity key preserves command deduplication across bearer-key rotation. Keys are server-supplied, validated and copied; stable plan IDs use a public namespaced hash and convey no authority. Hosted key custody/rotation remains within the existing security and provider-proof gates.
