# P2-L02 — Durable local runtime

The authorized local Phase 2 host composes existing application services with restricted PostgreSQL repositories and retained encrypted files. It is an explicit opt-in library, not a production deployment or a change to the default worker/bootstrap.

## Composition and use

`createPhase2LocalHost` takes `mode:local-opt-in`, `effects:synthetic-injected`, eleven exact local role URLs, connection accounting, an existing absolute key-file path, an owned object directory and an explicit typed binding callback. `bindPhase2LocalServices` constructs repositories/crypto from those checked scopes and caller-supplied identity, model, scanner, codec, render, policy, mail and journal ports. No identity/provider is silently invented in production modules. Staff authority can reuse P2-L01's dedicated verified staff bridge; current service/database permissions still decide access. Synthetic identity/model/mail implementations live in test support only.

The fourteen exposed service groups cover onboarding, offers, coupons, moderation/review, insights, pilot delivery, report analysis, generic advice, photo processing, report delivery, combined P1/AI privacy fulfillment, AI/photo erasure, operations and CSV review/publication. Coupon consumption uses its own worker scope. Business rules remain in the application layer. Existing API adapters can consume these same services; this change does not open an HTTP listener or activate a frontend.

Every pool has one connection and a queue bound of four. Role names, local database identity, non-superuser/no-bypass authority, latest opt-in catalog presence and total connection capacity are checked before use. The native proof uses the 55-migration/225-table chain; installation and schema promotion are separate. Readiness authenticates a representative ready object for each retained key version after releasing its SQL transaction. This is key-coverage sampling, not an exhaustive filesystem integrity scan. The service profile pins the active asset-key version: ready rows from another version are refused because existing repository/file ports bind one active asset profile. Changing that version requires a separately reviewed data migration; retaining decryption keys alone does not imply repository migration or rotation acceptance.

## Retained state and recovery

Provide an existing UTF-8 JSON key file with exactly `current`, `keys` and `lookup`: one to four named 32-byte hex keys, the current name and an independent 32-byte stable lookup key. Keep it outside version control with restricted local custody. Startup never generates replacement material. Purpose-derived keys separate objects, envelopes, partner/report capabilities, contacts and privacy journals. Retain old versions and the stable lookup material while stored state requires them. This is a new explicit local profile; older Map-backed test ciphertext is not silently migrated.

Private objects are immutable AES-256-GCM files with authenticated metadata, ciphertext-version SHA-256 and plaintext size/checksum checks. Writes use exclusive temporary files, file synchronization and atomic same-directory creation. Conflicting bytes, wrong/missing keys, symlinks, unsupported paths and altered versions are refused. Erasure records persistent local negative state before removing sealed bytes and exact owned crash fragments; subsequent puts/gets remain refused across restart. There is no independent custody, authentication, fencing or power-loss guarantee.

A tick discovers only the existing version-one report/generic/photo/coupon job types, uses their leases and current authorization, refreshes popular generic work, expires photos, progresses recorded erasures and combined P1 privacy fulfillment and dispatches due deliveries. Pilot-captured sends have a single owner and never fall back to the P1 dispatcher, including uncertain or terminal states. Unknown AI/provider outcomes retain their existing conservative reconciliation and charge holds. No arbitrary stored handler name is executed.

`startPhase2LocalWorker(host,{pollMs})` serializes ticks at an explicit 1–60 second interval. Its observer reports only fixed state labels; deferred service work is reported as deferred. The embedding process must await `done` or `stop()`. Stop blocks new work, interrupts the poll timer and quiesces/drains the host. The host bounds active calls at 32 and waits up to five seconds before bounded pool drain; an in-flight service's existing provider deadline may outlast that grace period. This is not an unconditional five-second process-exit promise.

## Validation and limits

Focused tests cover encrypted state/adverse material, worker lifecycle, complete reconstruction with pending coupon/report/generic jobs, identical-command recovery, immutable reports, startup refusal, an actual owned child-process SIGKILL followed by a second cold process, real lease expiry, unresolved AI holds and exclusive pilot dispatch. Generated technical fixture data and injected synthetic ports exercise actual PostgreSQL and encrypted local files. The initial focused set passed 32 executions. After review corrections, the runtime subset passes 39 executions (35 unit and four native), within a combined76-test runtime/recovery/security proof. [Source-bound evidence](evidence/P2/p2-l02-durable-local-runtime.json) records the actual markers and corrected fixture assumptions. Exact-source full build/coverage, fresh review and actual PR/main CI remain required for cycle completion; the evidence record states measured results.

Retained dev/stage environments are untouched. No default 33-app/three-CMS manifest, production bootstrap/CLI/preflight/admission policy or migration promotion changes. All six S3 gates remain open; HS01–HS08 proposed; operators/coverage/rates, licensed/specialist/provider/model/scanner/inbox/AT/privacy/security/hosting/phase/live acceptance remain pending. No provisioning, purchases, live model/provider effects, actual recipient notifications or original case/gate closure.

P1 owner/privacy commands use the existing `createAnalysisPrivacyRuntime`, including its linked AI cleanup, journal barriers, bounded downstream I/O and atomic operator retry. P1 and AI journals have separate explicit retained directories. The local host does not expose an unwrapped P1 completion path or a raw nested service that bypasses host drain.

## Review and adverse-file corrections

Eight targeted regressions fail against the initial reviewed source: FIFO key/object opens hang before nonregular-file rejection; supported4/16 MiB objects exhaust the repeated-group Base64 regex; pilot envelopes exceed a generic1 MiB cap despite the existing7 MiB delivery contract; and pending email rights requests never receive their synthetic verification callback. The fixes use nonblocking opens before regular-file inspection, bounded canonical Base64 decoding, matching encrypt/decrypt limits of7 MiB for `pilot_payload` and1 MiB for other purposes, and existing privacy notification discovery/dispatch capped at four per tick. Key derivation, stored encryption formats, business payload limits and production policy are unchanged.

The combined76-test proof passes, including a large serialized pilot message with uncertain frozen bytes preserved across restart, five synthetic verification requests with one failed attempt then two pending requests recovered after restart, retained proof confirmation, and all existing SQL/object/privacy recovery checks. The verification-mail port is an injected in-memory test capture; there are no actual recipient notifications.
