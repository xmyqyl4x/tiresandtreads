## Request and cancellation

`createDeliveryServices.request` resolves owner-session digests and delegates address/contact handling to the existing contact service. Its application-only effect runs inside that service's command transaction: specific consent evidence, report/comparison/template/content snapshot, stable send identity and opaque delivery outbox intent either all commit or all roll back. The effect and its fingerprint must never be accepted from an HTTP/MCP/mobile client. The future API exposes only the delivery command and its bounded data schema.

The command fingerprint includes comparison revision, delivery policy, sender, template and fixture mode. An exact duplicate returns the existing send; a changed command body conflicts. Delivery resource identities also have a separate namespace, so reusing a key on the contact endpoint cannot collide with a delivery intent; existing contact proof identities remain valid. The template must be published, match the report locale and the installed renderer hash. An older requested report version remains fixed after refinement. Comparison absence is explicit, and an unavailable requested revision is rejected. The public report/comparison allowlists omit private notes, raw address/location inputs and capability tokens.

The server stores `send_after = cancel_deadline = created_at + 60 seconds`. `created_at` is request acceptance; `accepted_at` is later provider acceptance. Status exposes an opaque send ID, revision, dispatch state and server times. It never promises inbox arrival or reveals the contact/provider/storage identity.

Cancellation uses the existing owner/subject locks and compare-and-set revision. Before the deadline a winning cancellation prevents the claim. After the deadline cancellation is closed even if work is still queued; a conflict does not itself prove provider handoff. Status remains Queued until a dispatch claim or provider acceptance, and the later UI must reserve Already sending for a claimed handoff rather than promising recall. Repeating a successful cancellation is harmless. Cancelling the report invalidates its unused report proof while preserving an independently requested offers subscription. Explicit `correct_address` cancellation also invalidates that request's unused offers proof; it never withdraws already-confirmed preferences. Correcting an address creates a new command/send and a fresh interval rather than editing the queued recipient. If the replacement fails, the original remains cancelled and the new request can be retried.

## One requested report and current authorization

An explicit requested report may go to an unverified destination, as the approved delivery design requires. This is a narrow one-send exception: the immutable snapshot binds the original owner, contact, report/version scope, current notice and exact permission event to the newly recorded request intent. A later withdrawal, invalidation, contact restriction, owner/report expiry, hard bounce, complaint or retained address tombstone denies handoff. General contact permission and marketing still require their existing inbox confirmation rules. A report request does not confirm the address or infer offers, analytics, identity sharing or general future delivery permission.

Current permission is checked before private I/O, again while freezing the payload, and in the final SQL claim. Current reviewed learning routes are also checked; removed/expired content blocks handoff. The final claim is the serialization point. A later withdrawal cannot promise recall of a handoff already claimed; it prevents subsequent attempts and future sends. Network/encryption/rendering work does not hold those SQL locks.

Current report services mark output as `technical_evaluation` with `issuanceAuthorized: false`. Production requests are denied while that remains the case. Fixture policy, renderer and provider modes must match; the real Resend adapter refuses fixture payloads. These are technical orchestration proofs, not specialist-approved advice or production delivery acceptance.

## Fixed files and provider identity

Request capture stores the safe report/comparison DTO, template version/hash, sender/policy and deterministic reviewed learning selection. Versioned reason-to-topic weights use the shared selector, with no interaction history. Fewer eligible articles produce fewer links. A newer public article cannot silently rewrite the captured selection; withdrawal still blocks it before handoff.

The first eligible worker renders through a versioned port. The included fixture emits a labeled HTML/text message and a valid single-page PDF saying **TECHNICAL FIXTURE — NOT TIRE ADVICE**. Actual React Email/PDF content, accessibility, glossary links, physical address/preferences/privacy footers, commercial streams and client render matrices remain P1-PR-037/S5 work. The fixed-message contract bounds subject/text/PDF bytes and keeps HTML below 100,000 UTF-8 bytes. Remote attachment URLs and arbitrary provider headers are not accepted.

PDF and email payload are private versioned assets. `createDeliveryFiles` composes the existing restricted asset repository and encrypted S3-compatible adapter; the private workflow role cannot read object locations. Object I/O happens outside SQL. Registration/immutable PUT retries adopt only identical bytes; a ready record cannot be replaced with a different body. PDF linkage uses the exact report/comparison and owner scope so existing later download grants can authorize it. The recipient is decrypted outside SQL and stored only inside the frozen private email object, never the snapshot/outbox/status DTO.

The worker reads and verifies the exact frozen object before claiming. Provider retries use the same opaque HMAC-derived provider key, sender, recipient, template output and base64 PDF bytes; they never render again or generate a new send identity. An orphan after an interrupted upload cannot activate a send. Asset expiry/deletion and incomplete uploads remain subject to the existing cleanup mechanism; request snapshots/work rows must be erased in the P1-PR-025 dependency order before their linked intents/contacts/assets.

## Durable attempts and uncertain handoff

`email.delivery_work` uses a 120-second token/generation lease and SQL deadlines. Duplicate workers cannot claim concurrently; an expired worker cannot freeze or finish another generation. A crash after claim but before recording the provider response is recovered as uncertain, including a crash after actual provider acceptance. The next safe attempt uses the frozen identity/body. Definitive rejection is terminal; uncertain responses retain the same permanent receipt and bounded retry state.

There are at most five provider attempts, with a conservative 23-hour cutoff from the first SQL attempt and bounded backoff up to five minutes. This leaves margin inside [Resend's documented 24-hour deduplication window](https://resend.com/docs/dashboard/emails/idempotency-keys); it does not extend that provider guarantee. Window/attempt exhaustion becomes manual review, never an automatic new key. Repeated failures before any handoff stop after eight leases and retain a suppressed send with a bounded reason. Reconciliation returns at most 20 due sends. A scheduled worker's actual cadence, alarms and backlog/latency proof join P1-PR-027; the local service does not claim measured p95 handoff under production load.

The Resend adapter uses the fixed HTTPS endpoint, an approved sender allowlist, bounded response bytes and a five-second deadline including credential retrieval. It distinguishes explicit refusals from ambiguous responses, redacts provider error bodies and can retrieve a known provider message ID without returning recipient/message content. It does not invent lookup by idempotency key. Unknown acceptance can be recovered by an identical safe retry inside the window; signed webhook ingestion and operator reconciliation belong to P1-PR-023. See the [send contract](https://resend.com/docs/api-reference/emails/send-email) and [retrieval contract](https://resend.com/docs/api-reference/emails/retrieve-email). No live provider credentials, domain setup or real mail is used by tests.
