## Authority and request clocks

`createPrivacyRuntime` accepts only `tt_privacy_runtime`, a separate non-owner, non-inheriting database role. Ordinary private/public/catalog/CMS/analytics roles gain no purge grants. The worker composes narrow request/owner/reliability/asset ports; application services decide the workflow, SQL repositories own persistence, and integrations own cryptography, envelope storage and external acknowledgments. The worker cannot grant staff roles, change a live legal hold or publish catalog/content. Staff review uses a fixed security-definer authorization function that locks the current active identity, unrevoked assignment and privacy role through commit.

`requestOwner` takes a bounded client request key and resolves existing browser owner-session digests. It persists a separate HMAC receipt binding so a retry can recover the same proof after a journal outage or physical session erasure. This binding grants request-status recovery only and expires with the status receipt. A share/view/download capability or an entered address does not become owner authority. `requestEmail` normalizes the address without consulting contact records, encrypts the reply context under the separate `privacy_reply` purpose and commits a durable `privacy.verify` outbox reference. Known and absent addresses receive the same `{accepted:true}` response. The verification worker sends a dedicated `privacy.*` proof through an injected mail port; it never returns the proof/address to the requesting browser. Provider idempotency derives from the original proof version and remains stable through key rotation. An absent address can verify and complete an empty request without account-existence disclosure.

Email verification requires actual notification acknowledgment, the stored MAC lookup/version, an unexpired proof and a still-pending request. Confirmation is a single transition. After proof verification, the request matches only the contact identity. Contact verification/unsubscribe, report, share and download audiences cannot substitute. Owner requests need no account or email. Current permission revocation and the initial journal acknowledgment precede a successful destructive-request response; journal failure returns Unavailable while committed restrictions and retry work remain in place. Unverified requests never delete or export data.

Every jurisdiction/request-kind pair needs a reviewed immutable `privacy.retention_policies` row with data class `rights:<kind>` and the configured version. Its typed rule contains response days, escalation days, proof lifetime and retry cap. Unknown/unreviewed configuration fails closed. There is no seeded production jurisdiction policy or universal statutory period. The request snapshots its rule and response deadline at receipt. Near-deadline work is highlighted in the queue and continues fulfillment; lateness must not become a reason to retain deletable data. Holds, unsupported downstream erasure and exhausted retries require operator attention. G2 still approves notices, applicability, acknowledgment/extension/appeal/downstream clocks, exceptions and evidence lifetimes before public activation.

Access, export and correction use an explicit manual fulfillment step. Their authorized operator records actual fulfillment/delivery or rejection evidence through `review`; current staff authority and a digest are mandatory and the decision is audited. The method cannot close an unfinished deletion or bypass a hold/provider acknowledgment. The implementation does not claim an automated access-package renderer, correction form or an actual delivered export. S4/S5 supply the public request/status and staff flows.

## Immediate restriction and deletion graph

Verified deletion locks the full sorted subject set, rechecks it for concurrent relationships, marks the target subject/contact pending deletion, increments permission revisions, suppresses current processing, invalidates verification proofs, revokes sessions/shares/downloads/email links, suppresses eligible sends and cancels matching outbox/jobs. Existing analytics suppression triggers hide affected generations in that transaction. A restriction preserves data behind the same access barriers. An opt-out applies marketing/analytics/ad/identity-sharing suppression while preserving independent report/session access.

Browser ownership and recipient contact identity remain separate. Contact erasure removes addressed delivery material and that contact's identifiers, not another browser's report. PDFs bound to independently retained reports are excluded from the contact's asset erasure set. Owner/report erasure removes obsolete report-purpose current permission/linkage while preserving independent contact subscriptions and justified minimal consent facts.

Destructive work follows these persisted, fenced steps:

1. **Journal:** acknowledge signed HMAC resource markers and contact suppression keys on storage independent of the application database restore domain. No address, report input/output, owner token or raw subject/report ID is written to the journal.
2. **Email:** select one send at a time. An unattempted send has no provider copy; any attempted/uncertain/accepted send requires an explicit `erased` or verified `not_stored` result. `unsupported` produces manual review. No provider deletion API or retention exception is assumed.
3. **Objects:** erase all exact-key versions/delete markers through the private object port, then record a receipt and the asset tombstone. Failure leaves work incomplete. Bucket and encryption-key versions must match configured storage. Object I/O occurs outside SQL transactions.
4. **Analytics:** purge up to 250 rows per pass, retain only event-ID/expiry replay barriers for the remaining receipt horizon and invalidate affected days in the same transaction. Current restriction and generation fences prevent a stale rebuild restoring visibility.
5. **SQL:** erase one send/report aggregate per pass, then identity mappings in FK dependency order. This includes delivery reservations/snapshots/work, callbacks/inbox observations, links/feedback/events/attempts/receipts, report/private/quote/comparison data, challenges/intents, contact lookups, cookie state, sessions and erasable audit links. Immutable snapshots are deleted through restricted retention authority; their UPDATE guards and composite FKs stay active.

A request completes only after all required steps finish. It then clears target/subject/reply linkage and per-resource receipt IDs, retaining request timing/state, protected proof lookup for bounded status access, step evidence digests and necessary suppression/replay records. Minimal work/event IDs and linkless consent/audit facts remain governed by reviewed retention; they are pseudonymous operational records, not automatically anonymous information. Existing seven-day command receipts can outlive an owner solely as non-authorizing security evidence; resource-bound receipts are removed with their aggregates. No deleted authority can use a retained receipt to regain access.

Each worker call leases one stage/item for 30 seconds with a monotonic generation. Competing workers serialize; stale/expired leases cannot acknowledge or complete work. Retries are bounded by the snapshotted policy and delayed 30 seconds; progressing a stage clears its failure count. Actual provider limitations remain visible. An active hold on a target/child escalates that case without globally disabling deletion. Only already-released subject holds can be removed by the worker's narrow function; live holds cannot be edited or deleted by its role.

## Late workers and asset reservations

A verified request starts a 45-second settling barrier before physical erasure, including when an email proof is confirmed long after receipt. Journal persistence can progress immediately. This exceeds the current 30-second delivery lease plus bounded provider/storage I/O; the real host/provider shutdown and cancellation contract must be proven before activation. Fixture tests fast-forward this stored barrier only because no real provider call is outstanding.

Delivery capture now reserves deterministic PDF and mail-payload IDs in the same transaction as the send snapshot/work. Privacy erasure writes permanent owner-free asset-ID barriers before deleting anything. Asset registration and barrier insertion share an advisory lock; the INSERT trigger refuses a barrier even if an old renderer finishes after the send and report rows have gone. Existing objects become deleting/deleted and cannot transition back to ready. The journal's subject/report markers reconstruct these barriers from a restored graph before access can resume.

Delivery runtime backfills up to 100 legacy work rows from frozen asset IDs or the unchanged identity derivation before accepting work; a larger backlog fails startup for a controlled operator migration. Deployments must drain old worker processes before schema/runtime changes. Future render paths must reserve their IDs before work and reuse the same erasure contract. An unbound artifact is not permission to retain private bytes indefinitely.

## Retention and recovery operations

`sweep(jurisdiction,true)` returns bounded counts without mutations; apply mode creates verified report-only/subject deletion cases for persisted expiry. It also expires bounded batches of drafts, quote notes, cookies, unreferenced challenges, replay barriers, completed command receipts and unverified reply contexts. Report expiry does not revoke an otherwise live owner. `retentionAssets` reuses the private asset lifecycle for bounded expired/pending/deleting/deleted object reconciliation and supports dry-run counts. PR #24's raw-event/aggregate expiry and import staging/source-rights cleanup remain their owning services; #27 composes their schedules and alarms. No arbitrary SQL policy expression is executed.

`createFilePrivacyJournal` appends immutable signed records with exclusive creation, file sync, idempotent content checks and POSIX directory sync. Configure a restricted encrypted volume independent of DB dumps/restore; an ignored local folder is a development fixture, not evidence of independent production durability. Windows volume durability and hosted replication/restore permissions require actual deployment proof. Capture checks file/signature integrity and produces a signed current manifest. The initial adapter refuses more than 1,000 records or a 2 MiB canonical snapshot; it must be replaced with a reviewed paged/compacted durable journal before that capacity is approached. It never silently drops records.

`replay` requires the authenticated manifest, the independently obtained expected digest, a capture no older than five minutes and no earlier than the backup finish, and every referenced privacy/contact key version. It imports suppression/erasure markers, scans at most 100 restored subjects/reports per transaction with a checkpoint and recreates ordinary fenced cases for matching resources. Readiness is withheld until scanning and the replay's cases finish; held/unacknowledged cases remain quarantined. Matching old outbox/jobs are cancelled and capabilities revoked before physical cleanup. The method reports readiness; it does not itself reopen database connectivity. The restore operator must retain the existing runtime CONNECT quarantine, keep only the controlled privacy worker authorized, reconcile CMS and metrics, verify current independent ledger/high-water evidence, then explicitly reopen through the reviewed recovery procedure. A caller-selected old digest is not independent recovery evidence.

Domain ingestion remains limited to the existing fixed non-personal fact vocabulary. Arbitrary restored/batch private records cannot enter through that importer. Any later importer that admits identity data must consult the same suppression/marker authority. Privacy key retirement fails startup while retained markers, tombstones or status proofs need an omitted key; external journal signatures also require complete key coverage. AI/photo/provider files, app/device stores and buyers must extend this graph and its tests when their phases activate.

## Review and activation limits

The implementation and tests are headless. Test mail, encryption and journal/provider acknowledgments are labeled synthetic; no tire report, real message or privacy export is issued. The local full-schema backup/restore proof and service-level replay checks support this implementation; hosted RPO/RTO, object-version recovery and actual ESP deletion/retention handling require G0/G2/S6 evidence. Before public activation, #27 binds schedules/alarms, #29 supplies transport/auth/CSRF/body limits/non-enumerating intake quotas and staff endpoints, and S5 supplies accessible controls and production templates. Licensed adapters and specialist review remain pending under the user's standing deferral.
