## Runtime and ownership

`createRuntime` is a server composition root in integrations. Pure application job/command services receive opaque transactions and narrow ports; they never import `pg`, AWS, Inngest or configuration. The root composes separate `tt_private_runtime` and `tt_asset_runtime` pools, repositories, provider transports, fixed-name telemetry and host-neutral image revision/environment metadata. A handler factory receives transaction-bound repository ports. Application transactions use PostgreSQL's current clock for leases, deadlines and permission checks; caller clocks cannot extend authority. Provider SDK clocks do not decide SQL ownership.

Two connections per pool, eight waiting requests per pool and 500ms checkout bounds are defaults. Existing UOW limits remain: five-second transaction deadline, two-second statements, 500ms locks and three-second idle transactions. Startup verifies actual PostgreSQL role identities and `replicas × (2 × poolMax + otherConnections) + reserve <= max_connections`; defaults are one replica, three other/CMS connections and 20 reserved connections. New role pools require an updated budget. A startup budget is not a measured production capacity claim.

`pnpm build` bundles a separate worker into the same Linux runner image. Its private `/internal/inngest` callback and readiness endpoint have bounded headers/body/request time, no-store responses and no product UI. The existing web host stays health-only. SIGTERM stops HTTP admission, drains requests for at most five seconds, then drains pools for at most five seconds and destroys SDK clients. Forced pool cleanup and ordinary successful query drain are tested separately. New enqueue/command/relay operations are refused during shutdown. Product business handlers remain at their owning S3 cards and product API/auth contracts at S4.

Only explicit local fixture configuration is accepted in this PR, including when `NODE_ENV=production`. Storage and workflow endpoints must be local; real AWS credentials, hosted app environments and implicit provider selection fail closed. No migrator, admin, CMS or licensed provider credential is mounted in a worker. SDK loggers are silenced; operational telemetry accepts four fixed events without arbitrary IDs, payloads, exceptions, keys, headers or URLs. A failing telemetry sink cannot change a committed outcome.

## Durable command, job and outbox contracts

| Boundary | Behavior and bounds |
| --- | --- |
| Command idempotency | Actor/operation/key digests and canonical body/version are fixed. A required current-authorization callback runs inside the UOW before every claim, including completed-response replay. Claim, SQL effect, safe response and completion commit together; stored result status is 201 for created and 202 for accepted. Concurrent retries serialize on the same durable identity; mismatched bodies, expired identities and previously committed pending identities fail closed. There is no automatic key reuse after the seven-day response window. Raw keys and arbitrary response bodies are never persisted. |
| Job registration | `(job_type,business_key)` is durable; schema version and resource reference must match. Registration and a minimal stable-ID outbox event commit in the same private UOW. |
| SQL job effect | Lease, then lock/recheck token, generation, deadline and state. The SQL effect and completion use the same transaction. Failure rolls back both. Completion rechecks lease expiry; late workers cannot commit or fail a newer generation. Completed jobs remain no-ops beyond provider deduplication windows. |
| Retry policy | Thirty-second leases, eight attempts, exponential delays capped at 300 seconds, and a fixed one-day job deadline. No automatic retry starts with less than 30 seconds remaining. Expired/deadline/legacy jobs are reconciled; exhausted jobs enter `manual_review`. |
| Outbox relay | Claim in SQL, send minimal resource references outside SQL, acknowledge in a new fenced UOW. A lost acknowledgement resends the same event identity. Resource `version`/`revision` remain exact and separate from `schema_version`; delayed events cannot silently substitute the schema number for a frozen report version. Eight failed attempts move work to `quarantined`; no silent discard or changed event identity. |
| Scheduled reconciliation | Every minute or on the internal reconciliation event, Inngest updates at most 100 expired/exhausted rows, drains at most four outbox events, sweeps one private asset, and dispatches at most four eligible SQL jobs through named durable steps. The recovery function has concurrency one and a one-minute deadline. Event jobs have concurrency four, two transport retries and a 20-second deadline. SQL leases/attempts remain authoritative. |

Inngest's [documented event/function deduplication window](https://www.inngest.com/docs/durable-execution/guides-and-advanced/idempotency) is 24 hours. It cannot replace durable database identities. The inbox receipt, bound job and stable outbox event commit atomically after the transport verifies a signature. Duplicate receipts reuse the existing job; changed digests conflict. A SQL consumer rechecks its job fence and exact receipt binding, then commits processing, its SQL effect, processed state and job completion together. Crash/failure rolls the processing state back. Processed/quarantined receipts cannot repeat the effect. Reconciliation adds at most four missing jobs from an indexed unqueued set (at most eight candidate rows), and examines at most 100 legacy processing rows; committed legacy processing without live fenced work is quarantined rather than blindly repeated. A 5,000-job backlog proof checks the recovery index and bounded result. Provider-specific signature/DTO/policy and external-effect consumers remain 023.

The SDK request deadline is two seconds; abort state propagates through internal SDK retry attempts so timed-out sends cannot initiate a new outbound request. Receipt uncertainty still allows replay of the stable identity.

SQL handlers may perform only transaction-bound database work. Email, payments or any other external effect must use the owning service's permanent effect identity, provider idempotency and uncertainty/reconciliation policy. This PR does not claim universal exactly-once network effects. Delivery's dispatch window, consent/cancellation and late-provider reconciliation remain 020/022/023. Manual review/quarantine inspection uses authorized operations queries; staff UI and reviewed redrive procedures remain 024/026. Never automatically reset a dead job's identity or resend uncertain mail.

## Private asset lifecycle and encryption

The asset adapter accepts opaque `assets/<UUID>` keys, a configured private bucket, registered purposes and bounded metadata. PDF byte headers, exact length and SHA-256 are checked. Objects are at most 16 MiB and expire after 30 days in this initial adapter. Purpose-specific retention and larger chunked import flows are reviewed in 015/025; unsupported inputs fail explicitly. No unbounded upload or row-embedded object bytes is introduced.

Uploads use conditional `If-None-Match: *`, explicit SSE-KMS, an exact configured key and versioned object storage. On an ambiguous PUT, the adapter verifies current encryption, size/type and the bytes of the exact existing version before adopting it. S3's [PutObject contract](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/client/s3/command/PutObjectCommand/) supplies the checksum/encryption/conditional request fields. Metadata moves `pending -> ready` by revision CAS only after verified storage receipt. SQL freezes storage identity/evidence and prohibits lifecycle resurrection. A failed metadata commit leaves a recoverable pending asset, not an authorized download.

Downloads resolve current owner/share grants through the private repository, look up ready versioned metadata through the separate asset role, read bounded checksum-verified bytes, then recheck authority. Revocation/restriction/expiry observed at that final authorization check prevents return. This is an authorization linearization point, not a claim that bytes already transmitted to an authorized recipient can be recalled. No bearer S3 URL is exposed by this adapter. A future direct signed URL requires a separately reviewed revocation/expiry contract; it must not silently weaken DB15. Public configuration reads use a separate bucket and a strict `public-config/<revision>.json` allowlist, 4 KiB bounds and the existing checksum/expiry reader.

Deletion first commits a non-downloadable SQL state, then deletes exact-key versions and delete markers, then records the tombstone by revision CAS. Each pass is bounded to 100 versions; at most 100 passes within a ten-second I/O deadline. Partial/outage cleanup remains retryable. Tombstones are retained and re-swept in bounded order: a PUT already in flight at erasure may physically finish later, but cannot restore SQL authority and is removed by reconciliation. Exact physical erasure time under provider outage is not promised. Larger retention/tombstone policy, rights-request deadlines, provider retry horizons and production lifecycle rules remain 025/042.

Private database fields use a versioned binary envelope: version byte, wrapped-key length, KMS-wrapped AES-256 key, random 12-byte IV, 16-byte GCM tag and ciphertext. Plaintext is limited to 60,000 bytes to fit the existing 65,536-byte persistence envelope. A fresh KMS data key is generated per encryption, used through standard Node AES-256-GCM and zeroed afterward; decryption zeroes the unwrapped key too. Purpose and resource ID bind both KMS encryption context and local authenticated additional data. Wrong context, key, format or authentication tag fails closed. [KMS encryption context](https://docs.aws.amazon.com/kms/latest/developerguide/encrypt_context.html) contains nonsecret values; no contact details enter it. Key rotation, retired-key retention and complete deletion protocols remain explicit deployment/privacy work.

## Migration, dependencies and acceptance limits

Additive `0015_runtime_durability` adds `job_runs.deadline_at` and `resource_id`, workflow grants, the outbox quarantine state and asset lifecycle/identity guards. Historical jobs receive a bounded deadline but no fabricated resource; missing-resource jobs enter manual review. `0016_inbox_job_binding` adds the inbox job pointer, a composite FK enforcing the job resource, immutable binding and partial recovery indexes. Applied migrations 0001–0015 remain byte-identical after their first use; 0015 is not rewritten to add the later inbox proof. No new table, view, role or CMS migration is introduced: **123 app tables, 39 app views, 1,577 app columns; 28 CMS tables; 16 app/two CMS migrations**. Generated Drizzle declarations are regenerated from actual PostgreSQL and checked in CI.

Pinned AWS S3/KMS SDK 3.1156.0 and Inngest SDK 4.26.0 are runtime dependencies of integrations and matching test dependencies at the root. OpenTelemetry API 1.9.0 is pinned to satisfy the SDK's transitive `<1.10` peer bounds. Protobuf dependency lifecycle scripts are explicitly disabled; production bundling and actual dev-server callbacks exercise the installed JavaScript implementation. No Redis, ClickHouse or Vercel service is added. Inngest's embedded development-server state is a disposable test fixture, not a production datastore decision.
