## Observer design

The existing permission-scoped health application service and security-barrier SQL view remain the source of bounded queue, age and quota-capacity measurements. The [local observer](../../packages/integrations/src/local-observer.ts) projects only ten fixed queue codes, counts, ages and cap indicators. Actor IDs, source rows, callback IDs, raw exceptions, URLs, credentials and unknown fields never enter its output. The operations service verifies an active `operations_read` actor before and after the snapshot. The new CLI never grants a role or activates the disabled seeded identity.

One sample reads the application snapshot and independently checks the existing host readiness URL, local fixture-provider health and local workflow history. HTTP probes refuse hosted destinations, credentials, query strings, alternate paths and redirects; they have a three-second deadline. Workflow history uses its existing five-second bounded reader and requires a completed maintenance cron for the exact environment in the preceding 180 seconds. A reachable engine without that recent run is not a fresh schedule. This is a local heuristic, not a production SLO, failure-rate measurement or hosted signing proof. Host readiness still concerns application/CMS connectivity; provider health alone does not establish KMS/object custody. The earlier canary/restart verifier retains that separate responsibility.

Queue thresholds are explicit local defaults: backlog 100, lag 300 seconds and quota capacity 8,000 basis points. Existing overdue privacy, unknown recovery and uncertain-mail states request review immediately. The observer emits a masked alert on the first active reason set, on a changed reason set, and a recovery when fresh evidence resolves it. Stable repeats produce no duplicate alert event. Malformed, missing or duplicate queue rows fail telemetry validation. Permission loss, database failure or missing telemetry never clears an earlier queue alarm; the output withholds counts and marks `fresh: false` until a fresh authorized review succeeds.

Alert state is bounded to the ten queues, three dependency checks and telemetry, in memory for that invocation. Restarting a monitor starts a new observation session and can re-emit outstanding alarms. There is no durable alert inbox, delivery/acknowledgement guarantee, remote notification or automatic repair. Output is local JSONL; a separately reviewed hosted monitor, retention policy, destination and staffed responder remain open S3/S6 work. These local thresholds do not accept live operating policy.

## Local operator commands and resource budget

`pnpm local:host observe dev|stage <staff UUID> [samples]` is read-only. It requires an existing explicitly authorized operations actor. The parent selects only the existing operations credential from the ignored file and supplies it to a dedicated non-root, read-only container. That process receives no migrator/CMS credentials or host settings/journal mounts. It uses Node’s TSX loader directly; no runtime dependency install is allowed. It never opens a migrator connection. A single observation is the default; at most 12 serialized samples are allowed, with five seconds between completed samples. The first summary and later alert/recovery changes are printed. Rerun a single sample for fresh counts during a stable incident. An unhealthy, denied or failed observation exits nonzero; the masked output distinguishes the alarm. Configuration failure is generic.

The process owns one `tt_operations_runtime` pool, maximum one connection, one queued admission, bounded connection/statement/lock/transaction timeouts and a bounded drain. It uses one of the **two already declared operator slots**; a synthetic response drill uses both (one observer and one fixture operator). The existing 17 host pools + five external slots + reserve 20 = 42 of 100 remains unchanged. Do not run extra undeclared operators concurrently. An ignored per-target exclusive lock prevents the supplied observer/drill commands overlapping. After interruption, verify no such process/container is active before removing its stale lock; there is no automatic lock adoption or key/data reset.

The normal command does not invent an active staff identity for current seeded targets. `pnpm local:host prove-observability dev|stage` is the separate, explicitly synthetic test drill. It deliberately creates a temporary operations-read actor, requires an initially healthy baseline, and injects exactly 101 owned callback fixtures dated one hour earlier. These timestamps and verification fields are test input, not accepted ESP evidence. The drill observes backlog/lag, suppresses a stable repeat, revokes only its own role, withdraws only its own fixtures and confirms the old alarm survives denied telemetry. After restoring that temporary role it requires fresh authorized evidence and observes recovery. Finally it removes its own actor/assignment and any remaining own rows. Actor-assignment cleanup also checks the exact synthetic provider subject, so a failed identity creation cannot remove another actor’s grant. It does not mark synthetic messages processed or claim an external send/deletion was completed. An interrupted or failed cleanup needs inspection of those exact fixture IDs; never bulk-delete unrelated queues to clear an alarm.
