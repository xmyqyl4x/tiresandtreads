## Contracts, roles and migration

Typed application ports cover public publication/reads, operational projections, analytics receipts/rebuilds and fixed-window quotas. PostgreSQL adapters use the existing explicit transaction context and checked-out client; errors poison the transaction even when callers catch them. No provider call runs inside a database transaction. Pure application contracts do not import the driver, ORM or integrations. Configuration validation and the object-reader adapter use the same versioned, fixed-field wire format and SHA-256 checksum.

| Runtime role | Authority |
| --- | --- |
| `tt_content_runtime` | Trusted approved-publication writer: immutable public history, monotonic heads, typed public configuration; only ID readback from private configuration history |
| `tt_public_runtime` | Current public-content and public-configuration views only |
| `tt_operations_runtime` | Staff role/status, configuration metadata, commercial/SEO/search/ad projections and visible aggregate metrics; no contacts, raw events, private configuration or storage locations |
| `tt_analytics_runtime` | Permission/subject checks and subject guards; event receipt/purge, dirty-day lease and metric replacement; cannot alter consent or activate collection |
| `tt_limiter_runtime` | Read/lock immutable policy identities and mutate/clean quota buckets; cannot enable policies or read private records |

These are process credentials, not user authorization. Later services authenticate staff, enforce permissions, derive trustworthy inputs and compose the appropriate pools. Row-lock privileges use immutable columns; existing/new triggers forbid changing their identity or immutable event bodies. The subject-restriction trigger is a fixed-search-path, migration-owned function; runtime users cannot call it to manufacture results.

Additive `0014_operations_access` adds three tables (content receipts, content heads, typed public configuration), eight views, explicit grants and privacy invalidation. Inventory is **14 app/two CMS migrations, 123 app/28 CMS tables, 39 app views**. Earlier migration bytes/checksums and Payload ownership remain unchanged. Retained local bootstrap appends five secrets while preserving all old credentials. Recovery uses forward repair or verified restore; no destructive down migration is supplied.

## Public publication and configuration

Content publication takes a stable content key/locale/market, a monotonically assigned numeric generation, the upstream CMS revision, validity times and either an allowlisted public text DTO or a withdrawal tombstone. The publication service at 021 must assign the generation durably from its approved work order; CMS revision strings and delivery time are not sortable authority. Advisory locks serialize publication of the same key. Immutable receipts compare the complete canonical input checksum, reject changed replays and advance the head only for a higher generation. Late messages remain history and cannot resurrect removed content. An expired/future head yields no content, with no fallback to an older row. A retry after committing the app projection is safe even if CMS acknowledgement failed.

The public text format accepts only title, summary and bounded paragraphs. The later CMS service transforms reviewed rich documents into this shape, verifies source/rights/expiry and escapes text during rendering. Shape validation is not editorial approval, HTML sanitation or permission to publish personal information. Durable CMS work leasing, cross-database acknowledgement and object writes remain 021; this adapter is the idempotent application projection side of that bridge.

Public configuration schema 1 has an integer revision, canonical UTC issue/expiry times and explicit analytics/advertising booleans. Unknown fields, non-booleans, unsupported schemas and lifetimes over 24 hours are rejected. Published versions link to existing reviewed configuration history, are immutable and retain their checksum. SQL selects the highest version, even if expired; the reader then fails closed. Private configuration values are absent from public and dashboard projections.

The portable configuration reader obtains the authoritative SQL snapshot on every refresh, including restart. Optional S3 `GetObject` reads the deterministic `public-config/<revision>.json` key and verifies the same schema/checksum. Composition supplies the credentialed bounded object transport; no bucket, URL or credential comes from a UI. Each I/O wait has a two-second deadline, object size is at most 4 KiB, concurrent refreshes coalesce, and cache lifetime is at most 30 seconds or the earlier explicit expiry. Reads never regress within a process or accept changed content at the same revision. Invalidation discards a pending older fetch. Missing, stale, corrupt, expired or unavailable data returns no configuration; services must interpret that as disabled/unknown. No stale permission is extended during an outage. Fleet polling, S3 credentials, durable writes and measured propagation under 60 seconds remain 014/021.

## Analytics protocol

Receipt accepts at most 50 events/64 KiB for one subject and current scope/policy/permission revision. It locks the subject before checking active status, expiry and confirmed current analytics consent. Event UUIDs are ordered; server receipt time defines the UTC day and 13-month maximum retention. Only registered event/route/channel/bot/property values are accepted. Digest identity includes original context; a changed body or subject conflicts without exposing another event. Exact retries insert nothing. Each newly affected day increments its requested generation once in the same transaction. Denied or unavailable transactions cannot commit receipts. Signed context and HTTP status mapping remain the analytics service/API.

Worker capture first leases and locks a pending day, then computes all source counts in a fresh statement snapshot while retaining that lock in the same transaction. Receipt/restriction/purge cannot commit a new invalidation for the locked day until capture commits. This avoids PostgreSQL READ COMMITTED rechecking a newer dirty row while a sibling SELECT still sees an older event snapshot. A deterministic interleaving test reproduces and prevents that drift. Internal/suspected bots, expired events and inactive/expired subjects are excluded. Internal metric definition `internal-v1` counts events and distinct `(subject, session)` pairs per UTC receipt day/market at either all-channel or one-channel grain; null sessions do not count. These metrics are separate grains, not values to sum together, and daily distincts do not produce monthly distincts. Unknown bot classifications remain included and retain that limitation.

Publication locks the day and checks token, unexpired lease, privacy revision and generation. It replaces the complete day's metrics and completion marker atomically. Ordinary intake can advance requested revision during computation: the older accurate generation publishes with its timestamp and the day remains pending. A privacy revision change rejects the candidate. Retry releases only the matching unexpired lease, with bounded exponential delay; exhausted work requires operational attention rather than endless retries. Initial workload bounds are statement/transaction timeouts and one day per capture; larger daily volumes require measured capacity work at 013/024.

A subject status transition to restricted/pending deletion invalidates every affected day and hides its aggregates in the same database transaction, including restrictions made through PR-011. The trigger follows subject-before-day order; dirty days lock in ascending date order. Purging requires a restricted subject and uses at most 1,000 rows per transaction. Each deletion batch marks affected days privacy-blocked again. Expiry cleanup also invalidates affected days. A replacement snapshot excludes restricted subjects even while their raw rows await purge. The full privacy service at 025 determines when withdrawal requires historical erasure, traverses all stores, retains restrictions until completion and replays deletion markers after restore. Withdrawal by itself stops new collection; it does not silently decide retention policy.

## Quotas and operations reads

Quota consumption runs in its own short unit of work before the protected command. A successful attempt remains consumed if that later command fails. Trusted services select every applicable versioned policy; database time determines all fixed UTC windows. All configured HMAC overlap versions are required. Sorted advisory locks serialize shared principal aliases across old/new deployments. Usage takes the maximum existing alias usage and writes the next count to every active alias with capped upserts. All policies/windows are checked before writing; any exhausted window returns denial with the greatest relevant Retry-After and consumes nothing. SQL errors roll back and fail closed.

A rotation deployment must preserve overlap for at least the complete active-window horizon, and every process must use the same reviewed overlap configuration. Retiring keys or changing policy versions needs a reviewed carry-forward/cutover procedure; the adapter does not authorize resetting capacity. Inputs are capped at eight principals/four keys; cleanup removes at most 1,000 expired buckets. Expiry follows window end plus one hour; current-window reads never depend on cleanup. Launch policies remain disabled. Platform admission/cardinality budgets and HTTP enforcement remain later service/operations work.

SEO pages use scoped keyset pagination. Staff projections omit provider subjects; configuration projections omit values. Affiliate projections require an active link and the latest valid unexpired check; ad-slot projections expose reviewed storage state only, not permission to load a tag. Host allowlists, approved agreements, consent, placement and rendering policy remain services. Search/ad reads return null for missing data and retain explicit zero, nullable denominators and exact bigint signed revenue. Ad reads require one dimension/currency/revenue-status grain and use the accepted newest complete-period snapshot view, excluding superseded dimensions even when the replacement has no row. Dashboard metrics hide privacy-blocked generations and expose pending/freshness metadata.
