## Observation and capacity contract

The [fresh observer](../../scripts/observability/observer.ts) reuses the existing [local queue observer](../../packages/integrations/src/local-observer.ts) and permission-scoped health service. It adds a separate connection-capacity signal and checks timestamp freshness before accepting successful queue, capacity or dependency observations. Receipt timestamps must be canonical UTC, no more than ten seconds old or one second ahead. Invalid/missing/stale evidence withholds measurements and cannot clear a known queue/capacity incident. Duplicate unchanged alarms remain suppressed. Dependency status distinguishes healthy, unhealthy, stale and unavailable; a cached successful probe does not establish recovery. One observation loop runs at a time.

The original `quota_capacity` measurement concerns **rate-limit table rows** in `app.rate_limit_capacity`; it is not PostgreSQL connection usage. SP07 leaves that schema/view/service contract unchanged and adds independent `database_capacity` / `capacity_telemetry` signals. This clarifies the earlier SP06 handoff's raw-capacity telemetry wording without rewriting its historical validation receipt.

The [reader](../../scripts/observability/postgres.ts) uses one `tt_operations_runtime` pool, maximum one with one queued checkout and bounded statement/lock/transaction/drain deadlines. Existing staff authorization is checked before and after both the queue and capacity reads. Revocation withholds both. It receives only a restricted disposable DSN, explicit fixture actor and required budget; no new role, membership or schema grant is introduced. The reader runs inside the privileged synthetic test controller, so it is not a separate OS security boundary or accepted production operator identity.

Ordinary roles cannot inspect all other sessions' `pg_stat_activity` details. An initial filter on `backend_type='client backend'` undercounted other roles. The final reader sums `pg_stat_database.numbackends` across the cluster and labels the result **observed database backends**, not an exact ordinary-client count. This can conservatively include privileged and background database sessions. No query text, PID, username, DSN or per-database names are emitted. It needs no `pg_read_all_stats` membership. [PostgreSQL 18 statistics visibility and current numbackends semantics](https://www.postgresql.org/docs/18/monitoring-stats.html).

Connection percentages use raw maximum minus both PostgreSQL server-reservation settings, matching SP06 admission. Declared requirements remain separate from sampled use; `overbooked` means required exceeds usable capacity. The fixture has **75 raw − five reserved = 70 usable**, with **69 required**: 17 host lane maxima + 28 existing harness/web allocations + one observer + three controlled pressure clients + 20 operational reserve. The extra observer/pressure allocation is declared before host composition; no second host replica runs. Application/CMS share one physical capacity. The proposed hosted 45-slot budget and HS sizing remain unapproved.

The harness has six pools of maximum three (five app, one CMS), five direct clients including the control client, and three padded slots within its 26-slot allocation. CMS setup's separate migration pool/lock run within that allocation before the full host. The dormant web allocation is two; no frontend starts. Three pressure clients are bounded direct connections, including an ordinary operations-role visibility probe. Inngest/Moto open no application database pools. Tooling/helper processes, worker HTTP listener and loopback receiver share the existing tooling container; no hosted monitor is installed. Existing memory/CPU caps remain unchanged.

The default local connection alarm threshold is 8,000 basis points of usable capacity. The controlled three-client integration case deliberately chooses a lower fixture threshold between measured baseline and added clients; it proves signal behavior without attempting production saturation. That threshold is recorded, not accepted as operating policy. Backend counts and the row-capacity signal are not interchangeable, and idle snapshots do not replace declared pool maxima.

## Local incident and delivery journal

The [response controller](../../scripts/observability/response.ts) projects only fixed component/reason codes, synthetic incident/event UUIDs, state and times into an exact project-bound schema. Queue details, staff identity, errors, source data, recipient addresses, credentials and upstream response bodies are excluded. Private Linux directories are owned by the controller and mode 0700; the fixed `response.json` and exclusive lock are mode 0600. Symlinks, foreign projects, unknown fields, malformed/oversized files and overlapping controllers refuse. A stale lock is not automatically adopted after interruption.

State is bounded to 16 component incidents, 32 unresolved delivery events, at most 64 delivered history events and 128 KiB on disk. Delivered history expires after five minutes or its count limit during journal operations; unresolved delivery and active incidents are not evicted. Exceeding the unresolved limit refuses the new transition without changing the previous journal. This is a fixture retention policy, not a selected hosted retention/SLA. Local write, file fsync, atomic replacement and directory fsync precede delivery. It does not prove power-loss recovery, independent custody or tamper-resistant storage.

An event's stable ID survives controller close/reopen and retries. Delivery is FIFO, at most four attempts per flush, with one-second retry spacing and a maximum of three automatic attempts per event. An exhausted or uncertain delivery remains visible and blocks later delivery until explicit fixture-operator retry. That retry retains the event ID. An interruption after the final persisted attempt cannot authorize a fourth automatic send. The loopback receiver deduplicates IDs while it remains alive; receiver restart/durable provider deduplication are not proved.

Acknowledgment by the loopback receiver marks fixture delivery only. A separate synthetic operator acknowledgment records local incident review, leaves the alarm open and does not cure notification failure. Unacknowledged incidents become visibly escalated after 15 seconds on a simulated clock. This is local status, not a page/email/escalation notification or actual staffed response time. Neither acknowledgment nor elapsed time resolves an incident. Fresh healthy observations resolve known incidents, including persisted incidents after observer/controller re-creation; denied or unknown evidence retains them. There is no automatic repair, queue truncation or source/policy acceptance.

The [transport](../../scripts/observability/transport.ts) can send only to the exact loopback fixture path with a fresh project token. Hosted URLs, alternate hosts/routes, URL credentials/query overrides and recipient fields refuse before fetch. Redirects refuse; each request/body has a one-second deadline, response bytes are capped at 2 KiB, and exact event/project acknowledgment is required. Wrong, malformed, oversized, failed or stalled acknowledgments produce a masked delivery failure. No SMTP, email-provider, cloud or human-recipient adapter is present.
