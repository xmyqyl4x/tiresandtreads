## Contracts and authority

Application ports define owner/session, report/version/item/draft/comparison/quote, capability/asset grant, contact/consent/privacy work, delivery/attempt/receipt and outbox/inbox records. They expose branded IDs, bigint money/revisions, explicit nullable evidence, versioned digests and opaque ciphertext envelopes. No SQL, driver, pool or storage location crosses a port. The unused 009 report/permission prototypes are replaced with these concrete scoped contracts; source-fetch and clock ports remain. There is no external API change.

Owner operations require both subject and session, rechecking active subject, live session and report ownership/expiry. Wrong-owner reads reveal no report; writes fail safely. Token lookup accepts one to four distinct key versions and fixed 32-byte digests, rejecting ambiguous matches. Crypto/HMAC computation, authenticated encryption, key custody, cookies and token transport remain integration/service work. The repository validates representations and never treats a plaintext email as ciphertext.

Report publication locks its head, checks expected revision and base/current version, requires published bundle/rules, inserts immutable version/items, advances the head and clears the draft atomically. Drafts use their own revisions; expired drafts can be replaced. Comparisons append immutable revisions with at most four unique slots; quotes preserve exact bigint amounts, component snapshots and nullable SKU. Report and quote histories use owner-bound keyset pages of at most 100 plus lookahead. Items cap at 100; JSON snapshots and batches are byte/depth bounded.

Share lookup returns a version reference only, never private input/output JSON. Fixed shares retain their version; latest shares resolve the current head. Download grants bind an owner session or shared capability to an exact report/version/asset/scope and expire within 15 minutes. Resolution rechecks grant, parent authority, report, subject and ready asset. The projection contains hash/size/MIME, with no bucket/object key. A later renderer must produce a safe shared DTO; the signer must perform final authorization before object access. PDF rendering and signing are not implemented here.

## Transaction and lock protocol

All adapters use the same explicit transaction context and checked-out client. Any repository error poisons that transaction, even when caught. No adapter starts a second transaction or calls a provider.

1. Register/resolve contact identity first, locking every configured overlapping HMAC key in deterministic binary order. All callers must use the same current overlap configuration. Supply `guardSubjects` with every other subject the service will mutate; registration includes the resolved recipient in the sorted guard set. Do not acquire identity locks after subject/report/send locks.
2. When identity is already known, call `lockSubjects` once with the complete sorted owner/recipient subject set before composing writes. Each writer reuses those guards before locking report/send rows. Do not incrementally acquire new lower-order subjects. Contact identity is separate from report ownership, including when one recipient receives another owner's report.
3. Lock report/send rows, compare expected revisions and append associated rows/outbox events. Complete the transaction before object, email or other network calls. The transaction helper rejects concurrent queries on its one connection; parallel workflows use separate units of work.

Contact registration deduplicates competing identities, checks all overlap keys refer to one contact, backfills missing lookup versions and returns the established identity. Email encryption rotation and confirmation use revision checks and preserve subject binding. Before retiring an old lookup key, services/operators must finish and verify backfill; removing overlap early can create duplicate identities. Cryptographic re-encryption and verified challenge orchestration remain later services.

Consent changes append immutable event plus erasable subject link, update the purpose/scope projection and increment the subject-wide permission revision in one transaction. Unknown, pending, confirmed, withdrawn and expired remain distinct. Suppression records retain explicit scopes; the shared permission revision invalidates stale dispatch decisions. These are trusted service persistence ports: authentication, jurisdiction policy, notice review, confirmation evidence and the legal meaning of scopes remain S3. A stored confirmed record alone is not public dispatch authorization.

## Delivery and privacy boundaries

Scheduling records distinct owner/recipient IDs, a published purpose-matching template and immutable presentation/provider identity. Report sends have at least a 60-second cancellation window. Cancellation and claim serialize on the same guards/send row. Claim checks due time, revision, active owner/recipient, verified contact (except necessary confirmation), live report, current confirmed scope and permission revision, suppression scopes and a ready frozen payload hash. It appends one attempt. Completion persists the outcome and durable provider-key/payload receipt atomically. An uncertain result remains uncertain; the repository never starts an implicit retry or changes its frozen payload.

Later delivery services must derive the correct permission scope from the send, apply full policy/rate limits, recheck at final provider handoff, reconcile uncertainty and manage retries using the same provider identity. They must not expose these trusted ports directly to a caller. A committed claim is not proof of actual sending, and withdrawal after a provider handoff may be too late. No email provider is activated.

Outbox append and inbox receipt enforce durable identities and reject changed duplicates. Outbox claims use skip-locked selection and expiring token/generation fences; stale workers cannot acknowledge a reclaimed lease. Inbox transitions use expected revisions and legal processing edges. Signature verification precedes inbox receipt in a later adapter. Full worker scheduling, provider events/links/feedback, command idempotency orchestration, uncertainty reconciliation and crash recovery remain S3/014 and delivery cards.

Privacy persistence includes encrypted report data, scoped suppression, request/step records, evidence digests, deletion markers and keyset enumeration of report/session/contact/send/report-asset/request roots. Child graphs are defined by the accepted [database deletion contract](../09-database-design.md): versions/items/drafts/comparisons/quotes/private payloads/capabilities/grants hang from reports; lookup/permission/challenge/cookie/suppression records hang from subject/contact; delivery attempts/events/links and protected receipts follow send policy. Enumeration is bounded per root kind, not a claim to have erased every store. A restriction blocks owner access and future dispatch; it does not mark a request complete. Full graph traversal/deletion, legal holds, protected tombstones/receipts, quote-note/challenge/cookie lifecycle, CMS/analytics invalidation, object/provider erasure and restore replay policy remain the privacy service at 025. This role has no historical purge privilege. Services add narrow operations at their cards, never generic arbitrary-table deletion.

## Migration and validation

Additive `0013_private_access` adds `tt_private_runtime`, explicit private table/function permissions, two keyset indexes and immutable owner/contact/session bindings. Existing migration bytes/checksums, dependencies, table/view inventory and CMS are unchanged: **13 app/two CMS migrations; 120 app/28 CMS tables; 31 app views**. The role cannot read object locations, administer staff, publish datasets or delete history. Catalog/app/CMS roles gain no private access.

Bootstrap appends only the new dev/stage role secret, preserving all existing values. Migrate/status/replay and retained-volume recovery follow [local development](../development.md#p1-pr-011-private-repository-upgrade). There is no destructive down migration. Older code can leave these additive objects unused; forward repair and tested backups handle failures.

The [validation record](evidence/P1/p1-pr-011-validation.md) covers unit bounds, real-role round trips, wrong owners, rotation/collision races, publication revisions, cancellation/claim contention, consent withdrawal, cross-repository rollback, durable duplicates and stale fences. Full S2 acceptance stays at 013; operations adapters are 012. Product UI remains behind S4/031, and four live phases, option-C deployment, PostgreSQL consolidation and deferred provider/budget decisions remain unchanged.
