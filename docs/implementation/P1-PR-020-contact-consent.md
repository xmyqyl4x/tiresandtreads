## Service and trust boundaries

`createContactServices` uses the existing private repositories, restricted PostgreSQL transactions, durable command receipts and outbox. `createContactRuntime` verifies the `tt_private_runtime` role before composition. Domain code contains conservative address normalization and browser-purpose policy; cryptography/envelope encryption remain integration ports. Shared canonical-record and transaction-error helpers are extracted from report services without changing their behavior.

| Operation | Contract |
| --- | --- |
| `request` | Authenticated guest owner explicitly requests an owned report/version, offers, or both; validates the exact presented current notices; encrypts outside SQL; records separate purpose request events, seven-day inbox challenges and identifier-only outbox events atomically with a safe command receipt |
| `confirm` | POST only; verifies a purpose-separated bearer MAC, stored lookup digest, expiry, current notice and an immutable HMAC binding to the unchanged prior permission event under a subject/row lock; consumes once, verifies the address and confirms only that purpose/scope |
| `withdraw` | Purpose-scoped unsubscribe bearer plus POST; no login or human challenge; atomically withdraws, records the matching restriction and invalidates pending proofs; repeated withdrawal is safe |
| `setBrowserChoices`, `browser` | Owner/session-bound explicit choices with current notices and optimistic permission revision; append purpose evidence and a server-side receipt atomically; projections are read from PostgreSQL, never trusted from a client cookie |
| `verificationMessage` | **Internal worker-only**, never a public route: decrypts outside SQL and rechecks permission before returning the address and purpose-separated verification/unsubscribe links for a minimal confirmation message |
| `permission` | **Internal queued-operation authorization**, checks active contact/subject, current purpose policy, verification and all applicable live/tombstone restrictions; returns the permission revision for the final SQL claim |
| `suppress` | **Internal verified-provider/privacy workflow only**, idempotently records hard bounce, complaint or deletion as all-email suppression plus minimal keyed tombstones |

The public request response contains only an opaque command resource and accepted status. It never returns inbox tokens, an address, a contact identity or a claimed subscription status. Encryption and provider failures are redacted. Request retries return their original receipt, changed-body reuse conflicts, and owners/report versions are reauthorized before effects. A pre-existing report can be generated/read without entering an address.

S4 controllers must explicitly allowlist the public methods, validate unknown JSON, enforce owner-cookie/CSRF/origin policy for browser writes, and derive GPC/method signals from the HTTP request. They must not expose internal worker methods or accept a client-declared contact/permission/provider-verification proof. Map address-submission suppression outcomes to a uniform public acknowledgement to avoid address enumeration. The RFC 8058 POST route must retain its login/CAPTCHA exemption; ordinary GET links only render a page. These transport and abuse controls remain in their planned API cards.

## Purpose, lifetime and suppression rules

Report permission is scoped to `report:<report-id>:<version>`; offers use `offers`. Both selections create independent events and inbox challenges. Confirming one does not grant the other, lifecycle, analytics or identity sharing. An offers-only request creates no assessment or report. Its worker context contains only a confirmation purpose; no promotion is authorized before confirmation. A new purpose starts pending until inbox proof is confirmed; initial pending permission expires logically after 30 days, and the proof after seven days. Submitting an existing address leaves its current purpose preferences and permission revision unchanged. A separate pending grant records an immutable evidence HMAC bound to the current event and challenge; confirmation rechecks that binding. Thus an arbitrary address submission cannot reset an existing subscription or invalidate another pending inbox proof. Confirmed offers require renewal after 180 days; report permission ends with its request's seven-day window. Later delivery services must consume one requested delivery identity and apply message classification/frequency rules; this service does not authorize newsletters from a report request.

Unknown/missing/expired consent and CMP failure deny analytics and all ad purposes. Necessary session/security functions remain available. GPC independently denies targeted advertising; identity sharing is disabled in R1 regardless of any choice. Stored projections are bound to the current server policy version. Changing published notices requires advancing that version. Tire-market selection is not a privacy-jurisdiction input. These implement the approved product policy, not a new legal applicability determination.

Withdrawals apply to the exact scope and leave an independently requested report available. A fresh verified opt-in can lift only the matching `withdrawn` restriction. It cannot clear all-email/all-marketing restrictions or hard-bounce, complaint, deletion or other safety restrictions. Old pending challenges cannot restore a withdrawn grant; a later permission change makes their prior-event binding stale. Old unsubscribe links retain withdrawal authority while their record/key is retained; GET never mutates permission. Subject guards serialize confirmation, withdrawal and dispatch permission changes. The last delivery SQL claim also rechecks retained tombstones, so an earlier queued decision alone is insufficient. Dispatch already committed before withdrawal retains the existing documented no-recall limitation.

## Address storage and rotation

The accepted address contract is a bounded ASCII dot-atom mailbox with a DNS-style domain. Trim surrounding spaces and lowercase only the domain. Preserve delivery spelling, dots and plus tags in encrypted address data. Launch contact identity and suppression lookups fold ASCII case across the mailbox, preventing a case-only change from bypassing safety restrictions. The first registered spelling remains the delivery address; distinct case-sensitive mailbox identities are not supported. Provider-specific dot/plus alias equivalence, SMTPUTF8 and quoted local parts are not assumed. Header/control characters and malformed addresses are rejected without echoing them. A future provider contract may extend this explicit input policy.

Encryption binds ciphertext to `contact_email` and the actual contact ID. Existing canonical contacts retain their original correctly bound ciphertext when another request deduplicates to them. Address lookup HMACs, bearer MACs and stable command identities use separate domains/key rings. During rotation, every writer checks/writes all configured lookup versions under the existing overlap locks. Bearer rotation retains versions needed by live inbox and unsubscribe links; idempotency identities remain stable. Runtime startup rejects lookup key configuration that strands an existing contact or omits a required active tombstone key. A lookup-key version must remain available while an erased-address tombstone still requires it, unless an approved pre-erasure migration replaces that dependency. A review date is not automatic permission to delete a required suppression.

## Database and operations

Additive migration `0024_contact_services` adds immutable `privacy.contact_intents` linking a challenge, contact, requesting owner and exact grant event/scope/policy; existing challenge tokens remain digest-only. `suppressions.lifted_at` preserves withdrawal history while permitting narrowly verified resubscription. Restricted grants add challenge, cookie-receipt and tombstone access to the existing private process; catalog/public/CMS roles gain none. Generated Drizzle models cover the full migrated inventory. Existing migration checksums remain unchanged.

Retention/erasure work in P1-PR-025 must remove contact intents and challenges before deleting their contact/subject links, expire cookie receipts and pending records, and retain only justified suppression keys. Recovery must replay current deletion/suppression journals before reopening runtime access. Hosted key custody, actual sender/template/notice review, signed provider webhook handling, durable email rendering/dispatch, browser flows and live release acceptance remain later gates. No real email is sent by this PR. The existing 98 draft specialist scenarios and zero named specialist reviews are unchanged; DD01/DD02/DD06/G1 remain open.
