## Findings and recommendation

Proceed toward a small, separately approved **test-only journal record/state proof** before considering a mutating executor. The contract needs two independent facts: durable evidence of what may have happened and exclusive authority for participating executors to start another effect. Neither a receipt nor a lock supplies both. Required storage/coordination capabilities are defined here without selecting a provider, extra service, new role, paid plan or dependency. PostgreSQL remains the consolidated application store; no Redis/ClickHouse is introduced.

The [current pair coordinator](../../tests/fixtures/lifecycle-pair/pair.ts#L118) holds a transaction advisory lock in the app DB during each read-only observation batch. Its [receipt consumption](../../tests/fixtures/lifecycle-pair/pair.ts#L135) and fresh two-DB reads are useful bounded evidence. They do not serialize role provisioning, span the interval between batches, fence another SQL connection or persist journal progress. [Production bootstrap](../../scripts/database/bootstrap.ts#L77) performs per-DB setup; [CLI status](../../scripts/database/cli.ts#L54) enters migration locking and can create metadata. Neither becomes the new reconciliation command through this review.

PostgreSQL documents [cooperative advisory locks and their lifetimes](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS). It also states that [advisory locks are local to each database](https://www.postgresql.org/docs/18/view-pg-locks.html). **Design inference:** a common cluster coordination domain must bind every participating lifecycle path to the same surviving authority; choosing the same number independently in app and CMS DBs is insufficient. No maintenance DB, provider-owned default DB, SQL credential or production lock key is selected here.

[CREATE DATABASE cannot run inside a transaction block](https://www.postgresql.org/docs/18/sql-createdatabase.html). The [transaction boundary](https://www.postgresql.org/docs/18/tutorial-transactions.html) therefore cannot be stretched over database creation, separate app/CMS commits and provider requests. Journal persistence can also fail independently. The contract must tolerate uncertainty rather than promise exactly-once effects or global rollback.

| --- | --- | --- |
| Plan author / approver | Review exact target, prior state, manifest, permitted effects and recovery disposition before execution | Unconfirmed; this design authorizes no execution |
| Lifecycle executor | One bounded admitted operation; no caller SQL, unlisted resource or automatic repair; halt on lost authority | Unimplemented; Codex is not appointed operator/on-call |
| Journal writer / custodian | Authenticated conditional append; independent durable recovery and trusted current checkpoint; private access audit | Location, identity, keys, retention, coverage and rates unconfirmed |
| Coordinator | Exclusive allocation for all participating paths; independently observable ownership/liveness; safe takeover constraints | Mechanism, endpoint and provider support unresolved |
| Inspector / reconciler | Fixed allowlisted read-only inventory; exact target/TLS/version/profile; no privilege fallback or mutation | Existing disposable readers only; future production admission unresolved |
| Technical reviewer / release owner | Separate evidence review, capacity and all actual acceptance checks | Unconfirmed; receipt cannot appoint them or release holds |

The provisioning journal is distinct from the existing privacy/deletion journal. It must not copy customer data, deletion payloads or signing authority into a generic operation log. Existing real archive restore and signed-custody proofs retain their separate evidence and limitations; synthetic quarantined profiles do not replace them. Journal storage must survive rebuilding either project DB and be recoverable when the source cluster is unavailable. A separate protected PostgreSQL authority could be assessed later; the DB being rebuilt, an ephemeral file or the same failed cluster alone cannot meet independent recovery. This is a capability requirement, not a new deployment choice.

The exact **17 app + 2 CMS project roles** retain LOGIN, NOINHERIT, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION and NOBYPASSRLS, with zero incoming/outgoing memberships. There is no temporary SET/ADMIN exception or product-credential elevation. Current bootstrap leaves existing passwords unchanged; it is not a rotation mechanism. A future privileged setup/coordination authority must be separately established without weakening these rules. Unsupported provider capability means stop, not silently select a broader role or self-operated fallback.

## Proposed record contract

Records are immutable append events, not mutable status rows that erase prior uncertainty. A derived operation view may be rebuilt only from admitted records and a verified current checkpoint. Operation identity alone is not authorization. Every append must compare the expected stream head/sequence and executor epoch under authenticated authority; a conflicting append refuses. A journal backend must demonstrate atomic durable acknowledgement and current-head consistency before selection. No SQL table, migration, package or executable schema is added here.

Admission must also consult the authoritative **domain-wide outstanding-operation index**, bound to the same trusted checkpoint/coordination domain. An unresolved prior intent or uncertain operation blocks a new operation ID on overlapping resources; per-operation stream consistency alone is insufficient. Creating another envelope, changing a release label or restoring an old journal cannot bypass that block. Updating the index and accepting intent must have a demonstrated consistent backend protocol; if either side is uncertain, refuse further dispatch. Its physical schema/transaction mechanism is unselected, and no distributed atomicity guarantee is claimed.

| Record | Required proposed content | Forbidden inference |
| --- | --- | --- |
| Operation envelope | Schema/canonicalization version; operation ID; exact environment and cluster-instance binding; app/CMS target roles/names; operation kind; reviewed authority reference; expected prior profile; source commit/tree, image/config and manifest digests; allowed step/resource list; coordination scope; private credential-generation references | A branch label, DB name/OID or valid checksum cannot prove real target identity or permission |
| Step intent | Unique step/attempt ID; operation/head/epoch; exact allowlisted action and resource; precondition inventory digest/reference; expected effect; rollback boundary; proposed retry classification; provider request/idempotency reference only if actually supported | Durable intent does not prove dispatch or success |
| Dispatch observation | Exact attempt and executor/session/request correlation; observation time and available evidence; no arbitrary request/SQL bodies | Absence of a dispatch event cannot prove that dispatch never happened |
| Step outcome | Effect state and independent observation state; sanitized reason code; committed/rolled-back boundary if established; durable observation references; remaining uncertainty | Timeout, process death or a refused receipt cannot prove rollback |
| Inventory observation | Exact target/phase, observation window, source/manifests and semantic inventory digest, known provenance per resource; both DB histories separately; findings, unavailable fields | Matching present state does not identify who created it or supply an atomic cross-DB snapshot |
| Coordination observation | Domain/epoch/holder references, acquisition/loss/quiescence evidence and bounded contention outcome; explicit fencing capability/limits | A TTL, PID or increasing epoch does not terminate old work |
| Reconciliation disposition | Prior uncertain attempts; fresh observations; conflict/provenance assessment; reviewed allowed next steps or refusal; approval reference and new attempt linkage | Editing an old outcome or automatically retrying an unknown request is forbidden |
| Technical receipt | Journal checkpoint/current head, operation/epoch/target/release/profile bindings; observed successes, refused steps, unavailable observations and unknown effects; evidence references; quarantine/hold flags | Evidence is not bearer authority, product admission or acceptance |

Proposed parser limits: **64 KiB per event**, **256 UTF-8 bytes per short reference**, **64 resource references per event**, **256 planned steps per operation**. Larger operations require another explicitly reviewed envelope; no silent truncation or batching beyond the limit. These are design bounds, not tested capacity or approved retention. Use a pinned canonical JSON encoding, reject duplicate/unknown keys, invalid enums, non-finite numbers, invalid UTF-8, oversized input and out-of-order references before persistence. Canonicalization specification and implementation require later review/test evidence; raw ordinary JSON serialization is not a cryptographic canonicalization promise. Digests are lowercase SHA-256 over the specified canonical bytes and exact referenced evidence bytes.

Sequence/head/previous digest and content digests detect inconsistencies relative to a trusted checkpoint; they do **not** authenticate a writer or expose a consistently rewritten/truncated/forked history by themselves. Admission needs independently trusted current-head/custody evidence, authorization and integrity protection appropriate to the later selected backend. Signer/key identity, key continuity/recovery, checkpoint witnessing, retention/expiry and deletion authority remain unconfirmed. If continuity/currentness cannot be established, refuse re-entry. Wall-clock timestamps aid audit only; they do not elect a lock holder or establish freshness across restarts.

Persist only fixed reason codes and allowlisted identifiers/digests. No passwords or password hashes, tokens, secret values, credential-bearing URIs, raw provider error bodies, private report/row/journal bodies or unrestricted SQL. Generation references identify a private secret version without hashing the secret. Evidence locations must themselves exclude bearer credentials. Sanitize before storage and diagnostics; a redacted display cannot repair a leaked durable event. Product identities cannot write/interpret this journal as approval.

## Outcomes and transitions

Use separate axes. `effectState` is `not_dispatched`, `observed_success`, `observed_no_effect` or `unknown`. `observationState` is `available` or `unavailable`. A disposition is `refused`, `quarantined`, `awaiting_reconciliation`, `reviewed_reentry_candidate` or `technical_evidence_only`. This permits **unknown effect + unavailable observation** without mislabeling it as a known failure. `observed_success` applies to one exact bounded step, not an entire lifecycle or release.

| Boundary / observation | Required disposition | Safe next action proposed |
| --- | --- | --- |
| Admission refuses before any effect dispatch in this attempt | `not_dispatched` / available / refused | Record refusal if journal available; prior attempts retain their own uncertainty |
| Intent durably acknowledged; no later reliable dispatch/outcome evidence | unknown / available or unavailable / quarantined | Reconcile; intent-only does not justify replay after crash |
| Exact SQL commit and resulting inventory reliably observed | observed_success / available / awaiting reconciliation or technical evidence only | Preserve commit; journal success must also be durably acknowledged before any next step |
| Transaction rollback authoritatively established for the complete bounded action | observed_no_effect / available / awaiting reconciliation | Separately reviewed retry may be proposed; no surrounding provider/other-DB rollback inferred |
| Connection, process, deadline, journal append or provider response lost after possible dispatch | unknown / available or unavailable / quarantined | Stop new effects; account for old work; fresh exact inventory/outcome lookup |
| Catalog permission/network unavailable | Preserve prior effect state; observation unavailable / quarantined | No elevated fallback, absence claim or repair |
| Both DB observations match and no uncertainty remains | technical evidence only | All actual HS/S3/operator/provider holds still block runtime/product admission |

Proposed normal order: admit reviewed envelope and journal continuity → acquire common coordination → record ownership/epoch and fresh preconditions → durably acknowledge step intent → dispatch at most its exact bounded action → observe outcome/inventory → durably append result → repeat only while authority and preconditions remain valid → fresh both-DB inspection and journal reconciliation → technical receipt → release owned handles. This is a logical sequence, not an atomic distributed transaction. Revalidate authority immediately before dispatch and track in-flight work; that check alone still cannot fence an already dispatched call.

If journal admission/append is unavailable **before** dispatch, perform no new mutation. If it fails **after possible dispatch**, stop subsequent steps, retain quarantine and report uncertainty through a sanitized best-effort diagnostic; that diagnostic is not durable journal acknowledgement. A restarted process cannot assume the last acknowledged event was the last effect. Re-entry requires a fresh executor admission, verified current journal, old-work disposition, exact resource reconciliation and reviewed continuation. Duplicate known events may be recognized only by identical attempt/content under the backend contract; a duplicate must never trigger another effect.

## Resource provenance and safe re-entry

Inventory binds cluster-instance lineage, environment, DB purpose/name and exact object class/name/signature, owner, role flags, both membership directions, role/DB GUCs, ACL grantee/grantor/grantability/default semantics, RLS/definer/path/constraint/index validity and both migration histories. Preserve known absent/present/changed/unavailable observations independently. OIDs are scoped observations and may change on restore; names and a matching semantic digest alone are not ownership-of-creation proof. Unrelated provider/system resources remain outside the manifest. A pre-existing same-name resource is foreign/ambiguous until its reviewed provenance is established; do not adopt it by observing a convenient match.

Record baseline inventory before the effect and link each newly observed resource to intent plus authoritative observed creation evidence. If provenance or actual effect is ambiguous, quarantine and seek reviewed reconciliation; absence of a resource in an incomplete catalog read is not proof of noncreation. Provider idempotency/query-by-request support must be established in its real contract before use. No generic retries of CREATE DATABASE, role creation, secret mutation or provider requests after unknown results. Known committed app/CMS steps remain separate even when the peer fails; no global rollback or checksum/history rewriting.

**No inverse-command compensation:** [PR #49's recorded preparation finding](P1-PR-027-catalog-adverse-case-proof.md#test-first-finding-and-verification) showed that returning table ownership after a grantor collision did not recreate the original ACL graph. The final [owner-sink fixture](../../tests/database/lifecycle-catalog.test.ts#L477) isolates this. This is local evidence against assuming that inverse commands restore semantic state; it is not proof of provider behavior. Any later repair must compare the full reviewed semantics, not merely undo the last verb or recapture a faulty baseline. Cleanup/deletion is a separately authorized exact-resource operation with its own intent and provenance; no destructive compensation, cascading DROP, foreign-resource cleanup or reset-all-passwords fallback is introduced.

## Serialization and old-executor limits

The serialization domain is the **actual cluster instance**, covering every participating role/DB provisioning, migration/replay, rotation/offboarding and recovery/handoff path that can affect its project roles or pair. Environment/project labels alone must not split a shared cluster into unrelated locks. Future admission must refuse unregistered shared project scope or inability to establish cluster identity; it cannot guess from a hostname. Multiple source/target clusters require sorted canonical domain acquisition; within each domain use one documented app/CMS lock order. Existing per-DB migration locks remain inner controls, never a substitute for the common lifecycle allocation. All domains must be acquired before mutation; bounded failure releases only owned allocations and records specific effects/uncertainty.

If a later backend uses PostgreSQL advisory locks, all participants must use the **same surviving coordination database/session and reviewed namespace**, with explicit owner/lifetime, no pooling handoff and observable liveness. A short transaction lock ends with that transaction. A session lock may outlive a rolled-back transaction and ends with its session; it must not be confused with a lease that revokes work. The existing disposable key `7724046,1` is not chosen as a production namespace. Storage/coordination outside the DB being recreated, supported authority and any needed connection are unresolved capability requirements; no extra LOGIN project role, temporary membership, provider default DB or broad admin credential is authorized.

A linearizable epoch/conditional append protects journal ordering only at the authority that checks it. A stale executor could still finish SQL on another connection or an already accepted provider request. **No target-enforced fencing capability is established.** Loss of coordinator/session/lease/journal means stop new dispatch, invalidate receipts and quarantine. Takeover must establish old executor/session quiescence and reconcile every in-flight action under separately supported authority; expiry, missed heartbeat, PID disappearance or a new epoch alone cannot authorize it. If old work cannot be proven stopped/resolved, remain quarantined. Automatic kill/cancel/revoke procedures are not specified as available provider capabilities.

Advisory coordination cannot exclude an unrelated administrator or provider control plane. A later real operating contract needs restricted change paths, maintenance access/window, external-change detection and fresh inspection. Sequential app/CMS snapshots and matching receipts do not prove an atomic pair or remove a validation-to-handoff race. A future technical handoff requires uninterrupted participating coordination and a fresh final check; any loss/drift invalidates evidence. This review neither opens runtime access nor claims continuous isolation of privileged fault fixtures.

Use bounded acquisition/query/operation deadlines and bounded input sizes; no infinite wait or open transaction while waiting for human approval. Exact numeric timeouts, retry policy, pool allocation and provider support need later measured capacity/cost review before execution. Existing proposed hosted budgets **45/62** and local fixtures **68/69** remain unchanged; journal/coordinator/observer and overlapping old/new/recovery sessions must be included before a real trial. RTO ≤4h, RPO ≤24h and conditional PITR ≤15min remain targets with no new acceptance. Operators, backup coverage, custody, rates and full funding remain unconfirmed.
