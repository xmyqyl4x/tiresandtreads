## Protocol, authentication and packaging feasibility

This is an inbound MCP adapter over our services, separate from P2 outbound model inference. The MCP reference reviewed resolves to revision **2026-07-28**. Its [Streamable HTTP transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) changes earlier session/GET-stream behavior and requires Origin validation. Record this as a documentation reference, not a selected SDK/runtime pin or proof every target client supports it. At 015, pin an official TypeScript SDK and transport/version set actually supported by the selected clients, then test version negotiation, cancellation, bounded streams, errors and compatibility. Do not copy an older session recipe or assume a newer spec works in a client.

For private tools, the [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) defines protected-resource discovery and OAuth roles. Our design requires an established authorization server, authorization-code/PKCE, exact redirects/resource audience, short scoped tokens and current grant/owner checks per call. Reject token passthrough, wrong issuer/audience/subject, expiry, excessive scopes and revoked grants. Treat discovered metadata/redirect URLs as untrusted inputs; use reviewed HTTPS endpoints and bounded network policy. The approved staff/organization identity direction does not prove a consumer realm or OAuth authorization-server contract; do not assume one login SDK supplies both.

The current [OpenAI authentication guide](https://developers.openai.com/plugins/build/auth) describes PKCE S256, protected-resource metadata and client identification via CIMD, DCR or predefined clients. Verify the actual management-page redirect/registration settings; client transport identity is separate from end-user authorization. Keep secret exchange in the identity service/browser flow, never in model tool arguments. Provider/consumer realm, registration method and SDK versions remain unconfirmed. Optional mTLS/client allowlisting cannot replace owner authorization.

The current [MCP server guide](https://developers.openai.com/plugins/build/mcp-server) requires Streamable HTTP and a stable public HTTPS endpoint for public submission; private tunnel testing is a different activity. Neither a local endpoint nor a manifest is a directory listing. Plan remote MCP plus optional UI only where needed; do not create a legacy plugin manifest, custom API-key workaround or desktop-only package by default. There is no endpoint, tunnel, registered app or package implementation in this PR.

The [submission guide](https://developers.openai.com/plugins/deploy/submission) covers package/remote-server setup, domain verification, tool scan, review and publication. Prepare a stable server, developer identity, policy/support links, demo recording, five positive/three negative review cases and safe reviewer access; recheck current portal fields before submission. Metadata/skill changes and server changes can follow different update paths. Preserve an immutable approved package/server/contract manifest and rescan changed tools; a server-only change must not bypass our release controls. No account is inspected/created, challenge hosted, package uploaded, scan triggered or listing submitted now.

The [plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines) require a published privacy policy, minimized collection and reliable desktop/mobile behavior. Plan a separate synthetic consumer demo account for review, with private credential handoff under future authorization. If review cannot use an interactive MFA flow, reconcile a narrowly isolated demo path with security reviewers; never disable real staff/tenant MFA or expose real reports. Keep UI/CSP origins minimal if an optional embedded UI is later justified. Actual acceptance and directory availability are unproven and cannot be promised.
