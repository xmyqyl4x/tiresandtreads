## Matching and simulation

The pure domain policy accepts immutable report-derived products and bounded offers. At most three offers are selected, with one per seller. Selection never modifies tire safety, core ranking, recommendations or prices. Every matching/simulation call is deterministic and independent of SQL mutations, cash payments and bids.

Product target rows form an OR group; geographic rows form an OR group; both groups must match when present. Every selected axle must match a product target. Current supported targets are SKU, model, reviewed brand identity, exact size, rim, category, known vehicle type/tier, store-wide, region, postal and approved-location radius. Unknown source values, unsupported rules/strategies and invalid location restrictions fail closed. Brand names alone are not identity evidence. Vehicle type/tier remain unknown until source-backed mappings are available.

The nonpaid score is `(40 × relevance + 25 × saving + 15 × proximity + 10 × quality) / 90`, with factors bounded to 0–10,000. Relevance follows FR-OFR-02: exact SKU/size 10,000, model 8,000, reviewed brand 6,000, category 4,000 and store-wide 2,000. Rim/type/tier use the category-level 4,000. Geographic-only targeting uses store-wide relevance. Current quality data is unavailable, so every seller receives the same neutral 5,000; proximity is neutral 5,000 unless a matching radius yields a higher value. Later quality changes require a new policy version. Stable ties use offer ID and version; selection reasons and all scoring factors are append-only evidence without codes or location plaintext.

Savings use exact bigint arithmetic against a known immutable selected-plan USD subtotal. Unknown prices, noncash/free-service benefits, deferred rebates and conditional price matching contribute zero upfront savings. Currency/minimum-spend mismatches fail closed. Quantity must match the immutable selected-plan price evidence; a caller cannot turn a two-tire report into a four-tire offer. P1 range-only prices remain unknown to this policy, so they cannot supply invented savings or satisfy a minimum spend.

Candidate loading takes three bounded SQL queries for the entire set (offers/pools, targets and caps), not one query per offer. The local limits are 200 candidates, 100 targets per offer, 2,000 targets overall and 800 cap rows. Overflow refuses the operation rather than truncating away restrictions. This is a query-count/boundedness proof, not a production latency SLA.

## Delivery and interruption behavior

Only quiescent, unrendered P1 work can be explicitly adopted. Due work uses a generation-fenced 120-second lease. The application dispatches by send ID through an opt-in factory; no default poller, provider or hosted executor is activated. Reservation conflicts have four bounded attempts with a conservative report-only fallback. Pre-handoff failures retain the same assignment and release the worker lease so a fresh connection can resume without consuming again.

Offers require explicit inclusion, adult attestation, verified contact and separate confirmed current offers consent. A separately requested report retains its existing report-specific confirmed or scoped pending-grant path with a live challenge; a pending report grant never supplies offers consent. Global safety suppression stops both. Withdrawal/stale eligibility after rendering causes a recheck, release and rerender, at most three times. An offers-only send with no permitted offer is suppressed. A withdrawn report never contributes HTML/text/PDF to an otherwise independently permitted offers-only message.

The integration renderer preserves P1 report rendering, escapes seller text/codes, labels sponsored content and includes sender identity/postal address and an HTTPS preference endpoint. Commercial messages explicitly use the commercial stream with RFC 8058 `List-Unsubscribe` and one-click headers. Report-only messages contain no commercial block or headers. The actual preference capability route/provider binding and real inbox-client acceptance remain later integration inputs; the fixture URL is synthetic.

Before provider I/O, the exact recipient and complete HTML/text/PDF/headers are frozen, encrypted and checksum-verified. An owned SQL asset reference exists before external object I/O. A ready private object with the exact version/hash and generation is required by the final SQL claim. The send attempt/handoff marker commits before the synthetic provider call. Accepted results issue assignments; definitive refusal releases once with scoped non-use audit evidence; exceptions/malformed outcomes are uncertain and retain code/cap consumption. A lost result write leaves the marker; a fresh database connection recovers it as uncertain without calling the provider again. No exactly-once provider delivery, independent durability, real process crash, authentication or provider fencing is claimed.
