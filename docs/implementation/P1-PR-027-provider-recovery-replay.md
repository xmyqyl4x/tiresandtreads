## Local provider persistence

Stock Moto cannot export existing symmetric KMS material through its API. Its recorder cannot preserve exact key bytes or immutable S3 version IDs. The legacy containers and `/state/current/provider.json` therefore remain intact. A separate explicitly prepared fixture generation supplies restartable custody. No existing encrypted application data is migrated or rekeyed by this change.

The [derived image](../../infra/local/provider/Dockerfile) uses the existing pinned Moto digest. Although the upstream image tag says `5.2.0`, the Python package in that digest reports **`5.1.23.dev`**. The codec checks that actual version, and dependency/image upgrades require renewed codec and recovery proofs. No package, vendor, database role or migration is added.

The [fixture server](../../infra/local/provider/server.py) serializes S3/KMS requests, captures their response, and checkpoints before acknowledging it. A [fixed JSON codec](../../infra/local/provider/state.py) captures the exercised S3 bucket/version/metadata/delete-marker state and KMS material without pickle, eval or dynamically selected classes. Snapshots include a format version, target scope and monotonic sequence, authenticated with a separate random 32-byte MAC key. Writes flush a temporary file, atomically replace the checkpoint, and fsync its directory. The volume directory is 0700 and files are 0600, owned by UID 1000. Dev/stage have independent volumes and keys.

Once the MAC key exists, a corrupt, missing, incompatible, incorrectly scoped or insecure checkpoint refuses provider startup; a snapshot without its MAC key also refuses. A completely empty new volume can initialize an empty fixture, but the retained host manifest then fails its canary checks and prevents host admission. No missing canary is automatically recreated. Checkpoint failure returns 503 and poisons the process, including health, until a verified restart. If persistence succeeds but acknowledgement is lost, an unacknowledged effect can already exist: the caller must reconcile actual state. This does not promise exactly-once effects. There is no automatic replay of KMS/object mutation requests.

The local limits are 64 MiB per checkpoint, 16 MiB per object, 17 MiB request envelope, fixed codec types and depth 40. Unsupported resources, nonempty multipart uploads and S3 table/inventory state refuse a complete checkpoint and withhold acknowledgement. This deliberately bounded fixture supports the exercised operations; it is not a general replacement for S3/KMS. Provider endpoints stay inside the Docker network and accept only fixture configuration. Private snapshots contain plaintext fixture key material; their MAC does not encrypt it. They require protected local storage and encrypted backups. Hosted custody, IAM, deletion authority, independent recovery, power-loss durability and RPO/RTO remain unaccepted.

## Guarded fixture upgrade and restart

`pnpm local:host provider-upgrade dev|stage` stops the host and local workflow process, then audits both databases and the legacy provider before creating a separate generation. No other operator or writer may run during this exercise. The audit refuses observed runtime connections, any non-null encrypted/cipher/wrapped column, any stored old-key reference, any journal entry, extra KMS key, extra bucket, non-canary object/version or delete marker. The retained targets each passed five encrypted-column checks with zero encrypted values or old-key references; the old provider contained only one fixture key and four declared canary versions.

Only after those checks does it explicitly create a new synthetic KMS canary and four S3 canary versions. It commits `/state/provider-v2/provider.json` separately and selects it with an ignored local marker. It preserves host settings/key rings, credentials, SQL rows, journal directory, legacy provider and legacy manifest. These new fixture IDs differ from the legacy generation; the upgrade is **canary reprovisioning, not recovery of old KMS bytes**. Existing encrypted data or additional provider resources require a separately designed migration. Interrupted setup, orphaned resources or mismatched manifests refuse automatic adoption/reset.

`pnpm local:host cold-restart dev|stage` requires that explicit selection. It stops the host/workflow process, sends SIGKILL only to that target's new fixture provider, force-recreates its container with the same volume, checks the same encrypted canary and exact object versions, then resumes host registration. It never deletes volumes or restarts native PostgreSQL. Ordinary `stop` continues to retain PostgreSQL and both provider generations. The general `local down` guard remains.

The [measured proof](evidence/P1/p1-pr-027-recovery-local.json) confirms both provider container IDs changed; the new active manifest and all host/legacy custody stayed byte-for-byte unchanged across replacement. The original subject/session, six synthetic notices and one synthetic template remain. Each target verified all four versions and completed a fresh real cron → HTTP callback → service → SQL cleanup afterward. Fifty previously sampled completed workflow IDs per target were individually queried and remained completed. The retained privacy journals are empty; this is not evidence of recovery of nonempty retained privacy records.

## Business failures and explicit workflow replay

The maintenance callback previously returned a typed failure result as a successful cached workflow step. [Outcome validation](../../packages/integrations/src/maintenance-outcome.ts) now runs **inside** `step.run`: failed, busy or malformed outcomes throw a generic error, so the local engine records FAILED. Successful/disabled action results are bounded and reduced to public operational fields. No private error or arbitrary provider result is copied into the workflow result.

The existing maintenance function accepts its cron plus the internal local event `tt/maintenance.requested`. Event payloads cannot select actions, enable a lane or change configuration. Server composition still controls the bounded cycle; the retained setup enables only quota cleanup. No new API route, transport retry, mail send, source pull, destructive retention or public feature is enabled.

The [real-role journey](../../tests/database/service-host.test.ts) holds an actual exclusive SQL lock, dispatches through the local workflow engine and real HTTP callback, and observes FAILED with both expired/live buckets intact. After releasing the lock, the engine's actual `rerun(runID)` operation completes; only the expired bucket disappears. Replaying that successful run leaves the live bucket and disabled admission policy intact. The proof uses the SQL lane's existing idempotent cleanup; it does not establish replay safety for mail, privacy erasure or other external effects. Inspect the failed action and effect ledger before any such replay; unknown external outcomes require reconciliation.
