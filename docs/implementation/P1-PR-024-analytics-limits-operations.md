## Collection and signed context

`createAnalyticsServices.issue` accepts existing owner-session digests and trusted server GPC/CMP signals. Disabled collection, GPC or unavailable CMP returns Refused without opening a database transaction. The private authority resolves the live owner, current analytics/site permission, exact configured published notice/policy, suppression and any unfinished processing restriction. An address lookup, unverified email or client-submitted subject/revision cannot obtain authority.

The independent collection MAC audience binds subject, permission revision, site scope, fixed US/en-US market, server-selected channel, analytics session pseudonym, issue time and a 15-minute expiry. Up to four overlapping MAC keys are supported. A separate stable identity key preserves the pseudonym across MAC rotation; it derives from the existing owner session rather than IP/device fingerprinting. It is independent of contact, share, unsubscribe and quota key material. Keep the stable identity key through the lifetime of the source records it defines. Future market/protocol expansion must explicitly extend this versioned contract.

`collect` consumes a bounded JSON string with exactly one `events` array: 1–50 events, at most 64 KiB in UTF-8. Each event has only ID, registered event name, UTC occurrence time, registered route template and small allowlisted properties. Name/route combinations are checked; actual URLs, tokens, email, IP, free text, client session IDs, bot assertions and arbitrary dimensions are rejected. Server context supplies session, market, locale, channel and bot classification. Occurrence must be within 24 hours in the past/five minutes in the future, and not precede the current permission's effective time (at the contract's millisecond precision).

Before receipt, the independent limiter consumes a server-selected collector IP quota in its own short transaction. A valid attempt consumes capacity even if the downstream receipt fails. SQL rechecks the exact current permission revision, live subject, collection policy/scope, effective/expiry times, suppression and processing restriction while holding the shared subject guard. Refreshing a signed token does not change the canonical event digest; original event and authority fields define replay. Exact replay inserts zero rows; changed data under an existing ID conflicts. Receipt and dirty-day revision commit together. A stale/withdrawn context returns Refused without a behavioral row. No covert operational collection is substituted for consented analytics.

S4 maps committed Accepted to 202, Refused to 204, invalid input to 422, Limited to 429 with the returned Retry-After, and unavailable protected work to 503. It must enforce raw streaming limits, authenticate trusted signals, derive IP from the approved proxy chain rather than arbitrary forwarded headers, redact tokens, and bound client retry lifetime/queue. These services are not public routes. Collector enablement is explicit and seeded quota policies remain disabled until transport/activation review; no browser SDK or vendor is activated.

## Privacy, expiry and aggregate generations

The existing event ID/digest and leased day/generation model remains authoritative. The worker captures a consistent day source under its day lock, excluding expired events, inactive/expired subjects, currently denied permissions, bots/internal traffic and processing restrictions. It computes counts from source rows, not replay increments. A separate transaction atomically replaces the complete day and advances completion only with the same unexpired lease and unchanged privacy revision. Ordinary intake may leave an older generation visible with its actual timestamp and Pending state; privacy invalidation hides it immediately. A conflict leaves bounded retry intent; expired/lost leases cannot overwrite current output.

Migration 0029 adds immutable `collection_scope` provenance and a private `(subject, scope)` processing restriction. An analytics withdrawal with retained events creates the restriction and invalidates every affected day in the same consent transaction, without restricting unrelated report/contact authority. Analytics-purpose suppressions do the same. Receipt and withdrawal serialize through the subject guard. Partial purge cannot allow a regrant to expose or recollect old rows: collection stays blocked until the restriction's source rows are erased.

Purge records a minimal **event ID + expiry** replay barrier before removing a withdrawn source row. There is no subject, session, property or behavioral payload in this barrier. It expires 25 hours after original receipt, covering the 24-hour occurrence replay horizon plus accepted future skew. Even a re-dated copy of that old ID is refused during the barrier. An active-subject regrant requires a current context and a new event; deletion keeps its separate subject/marker barriers. Barrier cleanup and source purge are bounded and idempotent. P1-PR-025 still owns verified rights, the complete SQL/object/provider erasure graph, markers/journals and restore replay; this service is not that full fulfillment workflow.

Each published metric carries the earliest relevant event, subject, permission or scheduled suppression deadline. Read-time `valid_until` filtering prevents a generation remaining visible after authority expires merely because a cleanup worker is late. Shortening a permission deadline or changing policy invalidates captured work. Maintenance dirties expired visible generations once; already privacy-blocked work is not repeatedly invalidated and starved. Rebuild excludes newly expired sources and removes obsolete groups, including an empty day. Physical raw retention stays at most 13 months and earlier on withdrawal/rights erasure. Empty/missing or privacy-hidden metrics remain unavailable rather than being labeled an observed zero.

Initial metrics are events and exact **daily distinct sessions**, by market and all/web/app/MCP. Daily distincts cannot be summed into monthly unique visitors. `unknown`/`not_flagged` bots mean “not excluded by the available signal,” not confirmed human. Dashboard coverage explicitly says consented traffic only; it is not an unbiased total-site audience or billable attribution. Report/send records remain authoritative for their own operational facts.

## Security quotas and bounded storage

`createAdmissionServices.admit` selects policies and version 1 on the server. Report delivery checks normalized email hour/day and canonical IP hour/burst together. Collector admission uses its own IP/minute policy. Address/IP principals become purpose-separated HMACs under every retained rotation key; plaintext is not stored or used for analytics linking. Cautious email case normalization and canonical IPv6 prevent superficial alias bypasses. A deployment cannot retire a key while unexpired buckets still depend on it; overlapping deployments preserve the maximum existing usage. Policy-version replacement also requires a reviewed transition rather than a quota reset.

All windows use database time, fixed UTC alignment, ordered alias locks and one transaction. Any exhausted window returns the maximum applicable Retry-After and writes no partial increments. A successful attempt persists independently of later business failure. Missing/disabled policy or SQL/capacity failure is Unavailable for protected work. These fixed windows permit a boundary burst across adjacent windows; the short burst window supplements hour/day controls and does not implement strictly rolling marketing caps. Webhook/unsubscribe transports retain separate challenge-free policies.

`app.rate_limit_capacity` enforces a shared provisional cap of **100,000 bucket rows**, including all rotation aliases/windows. Security-definer insert/delete triggers update its exact counter transactionally; an over-cap new identity aborts every window in that attempt. Conflicting upserts do not consume extra rows, and bounded expiry deletion releases capacity. The limiter cannot alter this cap directly. This is a storage bound, not a supported traffic or user count. Platform admission/DDoS controls, queue/concurrency bounds and hot-key/growth alarms remain required at S4/027/release.

## Operations and connection budgets

The operations service requires current active staff with the `operations_read` role and rechecks that grant before returning. This role is registered but assigned to no real staff by the migration. S4 must derive the actor from authenticated staff context. A bounded day query exposes only published metrics, generation/Pending/computed time and a coverage label. There is no raw subject/event/contact export or cross-day unique sum. Currency is explicitly inapplicable to these counts rather than mixing them with ad revenue.

`admin.runtime_health` exposes capped samples of dirty analytics days, queued sends, uncertain/manual sends and pending/failed outbox work, plus quota row usage/capacity and database sample time. Each backlog sample reads at most 1,001 rows; `capped=true` means a lower bound, not an exact larger count. Operators receive no principal digests, provider identities, recipients or private payloads. Queue age/alerts, hosted monitoring and actual staff screens retain 027/S5 acceptance.

`createWorkloadPools` creates six separate bounded pools: report, worker, collector, aggregate, limiter and operations. Report/worker use private workflow credentials; collector/aggregate use the analytics credential with separate connections; limiter and dashboard have their own narrow roles. Pools have finite admission queues and statement/lock/idle/transaction deadlines; all scopes must target the same logical database. Startup verifies actual SQL roles and `replicas × sum(lane maxima) + other connections + reserve <= max_connections`, with at least ten reserved slots. Over-budget startup closes every pool and fails. Callers must account for asset/CMS/import/legacy pools in Other and count every deployment replica; do not run two compositions under an understated shared budget.

The factory is composable headless infrastructure. Existing health-only host and worker bootstraps are not silently replaced or collection-enabled. S4/027 must compose the actual service host with the global budget and worker schedules. Connection separation limits admission contention, not shared CPU/I/O failure; a PostgreSQL outage still prevents new persistent reports. Local saturation tests prove a report connection remains usable while the aggregate pool is full, not hosted report latency or throughput.
