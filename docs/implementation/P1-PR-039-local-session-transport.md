## Shared syntax, server authority

The API's opt-in Clerk verifier accepts signed session tokens, while the private screen and proxy still accepted only the older 43-character synthetic grant. A failing transport regression reproduced that mismatch. After the operator restriction was corrected, the independent reviewer still hit an older 128-character forwarded-header cap; the same positive control caught that second boundary.

A small shared contract now accepts only a 43-character opaque fixture token or a three-part URL-safe JWT shape, bounded to 8,185 credential characters and an 8,192-character Bearer header. The screen, private proxy and server reviewer path share that syntax. Browser code does not decode or trust user, role, MFA, expiry or other token claims. A syntactically valid forged token still fails at the selected SDK verifier before a provider state read. Current mapped identity, session state and business permissions remain authoritative on the server.

Operator, renewal and reviewer inputs use the same explicit bound. Credentials remain in page memory and authorization headers, with no query/storage/logging path. Renewal must retain the same verified staff identity and preserves unresolved command inputs and keys. The reviewer header has its own bounded syntax check; CSRF and command headers retain their smaller existing bounds. Exact proxy routes, body/response limits, Origin/Host checks, cookie/response credential stripping, strict CSP and recent-MFA/current-permission checks are unchanged. A refused dedicated staff verifier never falls back to fixture or owner authority.

This completes local transport of verified sessions through the existing credential workbench. It does not claim an enrolled Clerk account, a hosted SSO login/reverification ceremony or an activated operator session. Those require separately permitted provider/account/MFA/security configuration and acceptance. No Clerk browser SDK or third-party script is added to public pages, and no new signup/account authority is created. The common CMS workbench's equivalent proxy restriction is handled in its own P1-PR-038 follow-up.

The disposable native proof builds the real private Next screen, confirms its credential input bound, forwards a locally signed SDK-compatible session through the real private proxy, verifies the official SDK signature/session claims, resolves the pre-existing PostgreSQL identity and calls the existing permission-scoped mail queue. The fixture has bounded generated identities and read counts, and no actual provider account or network call. These are HTTP/service integration tests; they are not reported as manual browser sign-in, actual authentication or independent security acceptance.
