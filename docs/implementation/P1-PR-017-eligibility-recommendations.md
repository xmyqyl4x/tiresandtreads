## Responsibilities and callable boundary

`packages/engine` owns normalization, eligibility, replacement compatibility, evidence comparability, preference ordering and stable reason codes. It imports only pure domain values. It performs no SQL, network, environment, implicit-clock, random, advertising, affiliate, consent or UI work. UTC interval arithmetic uses validated explicit instants, including Gregorian leap/century boundaries; the existing ban on engine `Date` access remains enforced.

`normalizeAssessment(unknown)` accepts exactly the version-one fields: US market, resolved region key, configuration ID/wheel package or limited size input, seasonal strategy, declared winter use, one/two/four named replacement positions, up to three priorities and an optional explicit USD merchandise/installed budget. It rejects extra keys, paid terms, coercion, unsupported positions/currencies/quantity forms and invalid amounts. Size normalization only trims and uppercases; it never equates passenger, LT, euro-metric or arbitrary size patterns.

`evaluate(normalizedInput, trustedSnapshot)` evaluates at most 1,000 explicit two-axle candidate plans against one pinned bundle, at most 16 source components and bounded evidence/policy collections. It returns immutable decisions, up to five eligible picks, separately qualified above-budget/unknown-budget options, exclusions, source/recall references and engine/schema/policy/scoring/dataset versions. Every result has `purpose: technical_evaluation` and **`issuanceAuthorized: false`**. “Eligible” describes consistency with the supplied reviewed evidence; it is not certification, recall clearance or report-issuance authority.

`createRecommendationService({evidence, now}).assess(rawInput)` is the channel-neutral application entry point. It normalizes once, supplies one explicit clock value to a trusted server resolver, rejects inconsistent snapshot time/policy and safely propagates resolver failure. The resolver is an application port, not an endpoint accepting client-authored fitment, source approvals, recall clearance, scores or inspection claims. The later **019 report/refine/compare service** must implement that resolver over the accepted catalog repositories, bind tenant-authorized inspection records, verify actual policy approval, recheck current source/recall health and pin the report snapshot. No production resolver or product HTTP adapter is fabricated in 017. Future web, app and MCP adapters call the same application services.

## Eligibility and unknowns

| Concern | Implemented decision |
| --- | --- |
| Fitment | Configuration and wheel package must resolve to reviewed requirements. Both front and rear need one explicit two-wheel axle record. Size, rim and construction must match; load/speed use source-supplied ranks with no speed-symbol conversion invented here. Required load range, XL and run-flat constraints are enforced. Missing OE constraints, drivetrain or source coverage remain unverified |
| Regional context | The requested region must match the reviewed policy and current climate/market-guidance source components. Driver preferences cannot substitute for those components. No geographic/climate or legal requirement is guessed from a model name or ZIP text |
| Seasons | A dedicated winter product cannot enter a year-round/summer shortlist. A winter-set request requires winter products. Other classes and required snow markings come from the exact reviewed region/strategy/winter-use policy; class labels alone cannot prove a marking. Missing or conflicting policy remains unverified |
| Availability and rights | Replacements require current explicit availability. Every used source must have current scope and all five required rights. A stale, future, missing, wrong-market or wrong-kind source cannot establish eligibility |
| Recalls | The exact source dataset must have a complete successful check strictly less than 48 hours old. A matched recall blocks; unresolved DOT/lot mappings and unknown status require review. An absent catalog match never creates clearance. Existing target references survive failed/stale checks |
| Replacement/AWD | A reviewed vehicle-specific pattern and model combination are required even for a full set. Partial replacement additionally requires an authorized, current inspection bound to configuration, plan, replaced positions and all four fitted SKU identities, accepted retained condition, and actual tread/rolling-circumference measurements within explicit OEM limits. Missing limits are unknown. There is no generic AWD tolerance, size-derived circumference, blanket single-tire approval or inferred safe-life date |

Known incompatibilities are `blocked`; insufficient safety evidence is `unverified`. Neither enters the recommendation shortlist. The engine evaluates those constraints before budget or preference. It never manufactures a fifth option or fills a commercial tier by weakening a safety condition.

## Preference and price boundaries

Version-one measurements are SKU-specific reviewed basis-point values tied to source, method/unit/scale/normalization comparison key, review interval and confidence. Model-family measurements do not transfer automatically. The scoring contract uses the minimum supported axle value for a metric; that aggregation and all real calibrations require specialist review. The fixture's wet/comfort 50/50 weights are **synthetic**, not a production scoring default.

A numeric score requires the same complete approved dimensions across the entire eligible cohort. Missing, duplicate, expired or incompatible evidence suppresses numeric scores for the cohort and yields an evidence-limited suitability band; missing never becomes zero. Selected supported priorities apply the documented 2× multiplier followed by exact integer normalization. Unsupported/zero-weight priorities receive a reason rather than a hidden invented weight. Ordering is score, evidence confidence, comparable cost only when the whole cohort has the same usable basis, then stable plan identity. Reasons and versions make the outcome reproducible; no paid field enters the input contract.

017 accepts only a precomputed trusted comparable-cost DTO: exact integer minor units, USD, quantity, merchandise/installed basis, current source and validity. The actual source-backed cost construction, installed components, scenarios, price freshness policy and comparison mathematics remain **018**. Missing or incomparable cost cannot claim budget compliance. Above-budget eligible products are separate; budget never changes safety classification. All real prices and measurements remain unavailable until the deferred source contracts exist.

## Golden review and verification

[The review packet](evidence/P1/p1-pr-017-golden-review.json) contains **98 authored draft golden scenarios**, input/snapshot hashes, expected primary eligibility/score/reason/picks, dataset/engine/policy versions and explicit pending specialist records. It is derived from the authored fixture/expectation definitions, never from observed engine outputs. Fixtures use synthetic identities and policies. No real tire specialist, actual vehicle coverage or approved source contract is implied.

Unit and seeded property suites cover normalization, load/speed boundaries, sparse evidence, exact money beyond safe JS integers, input/source/measurement permutations, immutability, bounded 1,000-plan work, stable ties and byte-equivalent results under changing commercial sidecars. Application use cases cover resolver/time failures and exclusion of paid terms. Validation evidence is added after full Linux verification. The earlier real PostgreSQL/recovery suites remain mandatory regression gates; this pure-rules PR adds no schema or role grant.

G1 remains open: at least 50 cases must receive actual named specialist review, disputed rules/calibration and explanations need review, and selected source contracts/rights/coverage plus the 019 resolver/report integration must be proven. Merging this technical implementation cannot silently satisfy those gates. Four usable live phases, database-first construction, PostgreSQL consolidation and app/database outside Vercel remain unchanged.
