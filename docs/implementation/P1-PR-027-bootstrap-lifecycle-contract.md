## Proposed disposition

Separate **privileged provisioning, read-only validation, owner-scoped migrations, runtime admission, credential administration and quarantined recovery**. A routine release should validate existing foundations and apply reviewed owner-scoped migrations. It should not rerun privileged role administration to obtain a healthy status. A failed validation blocks the handoff; it never silently repairs roles, ownership, history or credentials.

This is a proposed lifecycle, not a change to the current bootstrap, CLI, preflight, migration, release or recovery code. Preserve all 19 exact project role names and restrictive capabilities, zero incoming/outgoing project-role memberships, app/CMS isolation, reviewed ACLs/RLS/default privileges, exact local version checks and current local-only target guards. No provider, edition, patch policy or permission exception is selected. Managed S2 remains a conditional research candidate; self-operated S1 needs actual staffing and is not an automatic fallback.

## Authorities and credential boundaries

The existing [O/P/B/D/K/V/R responsibility plan](../operations/staging-operator-responsibilities.md) supplies role slots, not assigned people. Every actual primary, distinct backup, reviewer, coverage window, rate, custody location and provider identity remains null/unconfirmed. Sensitive access changes and restore promotion retain separate human review; Codex is not a custodian or on-call operator.

| Function | Proposed accountability / executor | Permitted scope after separate authorization | Excluded credentials and actions |
| --- | --- | --- | --- |
| Provisioning | D accountable; D/P execute, K supplies scoped access, B/R review | Exact isolated cluster/DB/role allowlist; demonstrated provider-supported authority for creation, ownership, settings and grant removal | No ordinary runtime or UI process receives this identity; no arbitrary URI, foreign object adoption or provider default DB targeting |
| Validation | D accountable; dedicated owner-authenticated, read-only session, R/B review evidence | Catalog-only inspection of each exact DB and scoped cluster roles; bounded timeout, verified identity/TLS and masked findings | No password hashes, user rows, role repair, schema creation, migration metadata creation or privileged fallback. This session uses an owner credential under enforced read-only limits, not a newly invented read-only role |
| App/CMS migrations | D accountable; exact respective migrator; R reviews release | Reviewed immutable migrations, owned objects and explicit object grants to existing roles; serialized per DB | No cluster role creation/admin, membership, superuser, cross-DB owner assumption, schema push or application runtime credential |
| Runtime admission | P accountable; P with D/K evidence and R/B review | Only scoped runtime secrets after both DBs and the release pair pass validation and existing holds permit activation | No admin/migrator secrets in service composition; a technical receipt cannot release an S3/API hold |
| Rotation/offboarding | K accountable; authorized D/K mechanism, independent B/R review | Exact named credential generations, bounded drain/reconnect and revocation evidence | No bootstrap-as-rotation, extra role aliases, preserved SET/ADMIN membership or secret values in Git/logs |
| Restore/reconciliation | D accountable; D/P execute, K/V review custody/policy, B witnesses | Separate quarantined target; fresh roles/secrets, verified restore and signed current journal replay, explicit promotion review | No restore over the source, raw global-role/password import, blind provider-effect replay, real notifications or automatic promotion |

Privileged setup access must be available through an accepted recovery path when actually needed; “one-time setup” does not mean administration can be forgotten. It must not remain in a worker environment. Provisioning, migrations, validation and recovery share the declared serialized executor allocation rather than silently adding concurrent pools. Recalculate any overlapping source/target/observer connections and resource costs before a later trial; existing 45/62 hosted proposals and 68/69 local fixture totals are not changed here.

## Lifecycle and handoff conditions

These labels describe proposed states, not new acceptance gates. All transitions require an exact environment/cluster identity, reviewed operation ID, source/image/config/migration digests, expected prior state and permitted effects. A receipt is evidence of observations, not bearer authority for a later operation.

| State / transition | Required work | Handoff or refusal |
| --- | --- | --- |
| Unadmitted → target inspected | Resolve exact target, engine/tool versions, direct TLS identity, private boundary, authority/capabilities and inventory before mutation | Unknown target, existing unrelated roles/objects, unsupported capabilities or incomplete catalog visibility stop before changes |
| Inspected → foundation quarantined | Explicitly authorized provisioning establishes app/CMS DBs, all scoped roles, owner/settings/defaults and grant cleanup; runtime credentials/routes/workflows remain inaccessible | Neither DB is released while the other is partial. Required zero memberships and restrictive capabilities must hold at every validation/admission handoff |
| Foundation → foundation validated | Read-only foundation profile checks owners, role flags/settings, memberships and ACL/default baseline. It explicitly expects no application history yet | Missing future application tables are not mistaken for ready; unexpected existing history/objects is refused, not overwritten |
| Foundation validated → schema staged | Exact owners apply reviewed app/CMS migration manifests under existing lock/checksum/transaction contracts | Failure preserves the successful DB's recorded state and keeps both quarantined. No fabricated global transaction or automatic reverse migration |
| Schema staged → release validated | Read-only migrated profile checks complete expected objects, ACLs/RLS, valid constraints/indexes and matching app/CMS histories and release compatibility | Missing, stale, changed, extra or inconsistent history and any privilege drift block release |
| Release validated → runtime eligible | Fresh validation under the same serialized change window, current role/secret generations and readiness/capacity/custody evidence | Eligibility is technical only. Existing S3, provider, rights, policy and API/frontend holds remain independent; no runtime activation in this task |
| Eligible → routine release validation | Reinspect foundations, apply only pending reviewed owner migrations, validate both DBs and image/schema compatibility, drain/reconnect under the reviewed release plan | Drift opens a separately reviewed repair; routine release never invokes privileged bootstrap or accepts an earlier receipt as current state |
| Any failed or uncertain step → quarantined | Record known committed steps, unknown effects, live sessions and masked state; reconcile with fresh read-only inspection | No blind rerun, broad cleanup or automatic promotion. Re-entry must match the observed state and exact operation scope |
| Isolated restored target → recovery validated | Rebuild permitted foundations, restore app/CMS, reconcile both histories/objects and the current external deletion/restriction journal, prove denied effects | Source stays untouched; release needs separate reviewed promotion and all existing acceptance evidence |

[CREATE DATABASE](https://www.postgresql.org/docs/18/sql-createdatabase.html) is outside transaction blocks, and roles are cluster-wide ([CREATE ROLE](https://www.postgresql.org/docs/18/sql-createrole.html)). Therefore provider calls, DB creation, role steps and separate app/CMS transactions need a durable operation journal. Its private custody must be independent of the DB being rebuilt; no new dependency is selected. Record intent, observed completion and unknown outcomes without secret payloads. A future implementation must serialize the whole cluster operation, not rely on per-DB migration locks to serialize shared roles. No distributed transaction is promised.

That lifecycle lock coordinates participating executors; it cannot prevent an unrelated administrator or provider control plane from changing state. A later operating contract must also restrict those change paths, establish the maintenance window and revalidate after any external change. Each DB inspection is a separate snapshot. A matching pair of receipts does not establish a global cross-DB snapshot or eliminate the need for fresh handoff checks.

## Invariant profiles and evidence

The proposed inspector uses bounded, schema-qualified catalog queries in a fresh repeatable-read/read-only transaction, closes the connection on failure, and never calls mutation-capable helpers. PostgreSQL [transaction controls](https://www.postgresql.org/docs/18/sql-set-transaction.html) provide the transaction boundary; local target and TLS guards remain additional requirements. Read-only transactions alone do not authorize arbitrary SQL/functions or make an owner credential minimally privileged. Use an allowlisted query set, no user-provided SQL, and separate negative behavior tests in disposable fixtures.

| Invariant | Foundation profile | Migrated / release profile | Quarantined recovery profile |
| --- | --- | --- | --- |
| Target/version/TLS | Exact approved local identity/version/tools; no redirection or version-range waiver | Same, plus source/image/config binding | Exact separate target and accepted archive/tool compatibility; no source connection substitution |
| Scoped roles | Exact 17 app + 2 CMS names from [role definitions](../../packages/config/src/database-roles.ts); LOGIN, NOINHERIT, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS; zero incoming/outgoing scoped memberships | Same, including no provider/admin membership involving a scoped role | Same restrictive flags and zero memberships; fresh target credential references, never copied passwords |
| Owners/settings | Exact respective migrator owns DB/public schema; owner and runtime search paths/timeouts match [bootstrap](../../scripts/database/bootstrap.ts) | All owned schemas, relations, sequences, routines/types and migration metadata match the manifest/inventory; roles' per-DB settings remain exact | Same ownership/setting rules, with runtime admission deliberately denied |
| ACLs/defaults | PUBLIC DB/public-schema grants absent; restricted runtime grants match baseline; no future public function EXECUTE/type USAGE | Full reviewed object ACLs, grantability, RLS policies/flags, security-definer ownership/search paths, valid constraints/indexes and expected runtime permissions | Same restored object controls; runtime CONNECT denied and no live workers/queues/routes allowed to reach target |
| History | Explicit fresh state; absent future history is allowed only here | Exact ordered ID/checksum manifests; no gaps/extra/changed entries; CMS native history agrees | Archive's reviewed historical manifests first, then explicitly reviewed forward migrations and both final histories; no ledger surgery |
| Release/custody | Provisioning journal, cluster-wide role state and clean handoff | Both DBs compatible with exact release; fresh validation after mutations; no partial release | Verified archives, independent key/journal continuity and post-restore current reconciliation; no lost privacy marker or automatic effect replay |

Unrelated provider system roles may exist; they may not create memberships involving a project role. A catalog-permission failure is `unavailable`, not proof of absence. Compare ACL privileges, grantee, grantor and grantability canonically, retaining empty/default ACL semantics; compare role settings and both membership directions. Never compare only array order, role count, a revoked command's success message or the presence of `NOINHERIT`. Read-only inspection must not serialize password hashes or customer rows. Runtime denials/RLS behavior require separate scoped tests; an owner session is not evidence of runtime access restrictions.

A proposed private receipt contains operation/target references, expected/observed profile, timestamp, source/tree/image/config/manifest digests, server/tool versions, role/ownership/settings/ACL summaries, findings, completed/uncertain steps, quarantine state and custody references. It contains no password, connection URI, token, raw report, journal body or unrestricted dump. Evidence retention/location/reader permissions require later K/V review. No new evidence retention period or actual signer/custodian is appointed here. A summary/hash alone is neither trusted signing nor a release lock.

## Provider capability and ownership contract

[PostgreSQL role creation](https://www.postgresql.org/docs/18/role-attributes.html) can grant an ordinary creator automatic ADMIN membership; permission to administer, inherit and assume roles is distinct. [REVOKE](https://www.postgresql.org/docs/18/sql-revoke.html) must be evaluated against actual remaining grants and grantors. [Ownership transfer](https://www.postgresql.org/docs/18/sql-alterdatabase.html), actual [SET ROLE](https://www.postgresql.org/docs/18/sql-set-role.html) and [default privileges](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html) have separate authority requirements. The accepted local experiment demonstrates those distinctions; it is not a provider support contract.

| Required capability | Evidence required before an adapter/host is accepted | Current result |
| --- | --- | --- |
| Exact scoped names and flags | Actual edition SQL/API user creation and resulting catalog flags; no hidden mandatory memberships | Unknown for candidate provider. [DigitalOcean guidance](https://docs.digitalocean.com/products/databases/postgresql/how-to/modify-user-privileges/) still lists Advanced names without underscores and new-user CREATEDB; no rename or flag exemption approved |
| Remove automatic/admin/SET grants | Supported authorized mechanism demonstrates every scoped membership absent, including the grantor's automatic row, then future admin/rotation/recovery remains possible | Ordinary tested creator is insufficient. No managed privileged cleanup function/API is documented as established by this review |
| Establish owner/settings/default ACLs | Correct DB/schema/object ownership and actual execution identity for defaults; inspect all role-specific settings; no `local_harness` import | Local privileged control only; provider-owned default DB cannot simply be relabeled a supported target |
| Repeatable administration | Supported lifecycle for additions, changed settings, credential rotation, interrupted setup, revocation and independent restore without surviving memberships | Unresolved; retaining role-creation power is not proof of required grantor cleanup |
| Constrained inspection/migration/recovery | Catalog visibility, verified direct TLS, exact owners, locks/history and isolated restore with correct ACLs and quarantine | Existing local proofs only. [DigitalOcean limits](https://docs.digitalocean.com/products/databases/postgresql/details/limits/) exclude customer superuser access; equivalent provider authority must be demonstrated separately |

If a provider cannot meet the unchanged policy, mark that candidate unsupported for this contract and stop. Any exception, alternate role naming/NOLOGIN structure, persistent membership or broader owner/runtime power requires a separate explicit policy proposal and review. Do not grant temporary SET/ADMIN privileges to make routine migrations pass. Provider-created intermediate grants cannot be handed to runtime; a separately authorized, isolated setup mechanism must demonstrably remove them before validation. No such mechanism is implemented or authorized here. Public documentation does not prove its availability or universal impossibility.

## Release, rotation and recovery failure handling

**Migration replay versus provisioning replay:** Re-running immutable owner migrations may legitimately apply zero pending migrations. It must not recreate missing roles or reset a password. Re-running privileged bootstrap is a different administrative event, with its own scope and audit. A stale/partial app/CMS release stays blocked until reviewed forward recovery or an image rollback compatible with both observed schemas. Do not edit applied checksums, run Payload schema push or assume destructive `down` operations are safe. Advisory locks are per database; cross-DB release serialization and fresh end-state checks remain necessary.

**Credential rotation:** [ALTER ROLE](https://www.postgresql.org/docs/18/sql-alterrole.html) distinguishes self-password changes from administration of other roles. With zero memberships, future privileged access must be separately established. Proposed rotation records only private secret-generation references, drains affected clients, changes the exact role through the supported authority, refreshes scoped configuration, tests new authentication and old-authentication refusal, and drains/terminates old sessions through separately permitted authority. Changing a password does not by itself establish that old sessions are gone. PostgreSQL's single role password is not a dual-password overlap strategy; no duplicate project roles, fixed grace period or zero-downtime guarantee is introduced. On uncertain results, quarantine and reconcile actual secret/session state; do not reset all roles. Existing bootstrap leaves existing passwords unchanged and must never be sold as a rotation mechanism.

**Recovery:** Per-DB [SQL dumps](https://www.postgresql.org/docs/18/backup-dump.html) do not carry cluster role definitions. Recreate exact roles with fresh target credentials using the separately accepted provisioning mechanism; never restore raw cluster globals or password hashes. Preserve the existing reviewed archive/history checks and owner-scoped restoration; [pg_restore ownership behavior](https://www.postgresql.org/docs/18/app-pgrestore.html) must not be confused with restoring role administration. App/CMS archives are separate snapshots: record their pair/window and reconcile CMS publication/outbox and current deletion/restriction state rather than claiming one atomic cross-DB backup. Keep target routes, workflow scheduling, workers, credentials and CONNECT boundaries quarantined before any restored data can be used, including setup intervals. Do not assume a later CONNECT revoke terminates existing sessions.

Source remains intact; restore only to a separately identified target under a reviewed resource allowance. Verify full inventory, ownership/ACLs/RLS/history, corruption rollback, fresh credentials, retained key versions, nonempty signed journal and unknown-effect handling before proposing promotion. DB invariants passing does not release mail, publication, deletion, AI/provider calls, product APIs or frontends. Preserve RTO ≤4 hours/RPO ≤24 hours and the conditional ≤15-minute PITR requirement; no new timing or staffing result is claimed. Backup teardown, keys, storage retention and custody must be reconciled independently of DB removal.
