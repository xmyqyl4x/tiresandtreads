## Verified receipt and atomic effects

`createResendWebhookIngress` is the transport-independent raw-byte boundary. It verifies Svix v1 HMAC-SHA256 over message ID, delivery timestamp and exact bytes, using constant-time comparison, up to four overlapping secrets, a five-minute past/future delivery tolerance and a 256-KiB body limit. JSON is decoded only after verification. Duplicate/header-array handling and streaming body limits must also be enforced before this boundary by S4; neither parsed JSON nor client-supplied normalized observations may bypass it. Provider occurrence time is separate from the fresh delivery signature timestamp, so delayed events remain admissible.

Only an allowlist of normalized fields is retained: provider receipt identity, raw-byte digest, provider message ID, opaque delivery key, occurrence/receipt times, event type and conservative classification. Recipient addresses, subject, link URL, IP and user agent are discarded. **Minimization decision:** raw bodies are not persisted in this implementation; `raw_asset_id` remains null. The existing 30-day restricted raw-payload policy is a maximum when diagnostic retention is explicitly enabled, not a requirement to retain unnecessary PII. Encrypted raw retention would require its own reviewed adapter and erasure integration. Normalized observations remain private operational inbox records, not an analytics intake bypass; P1-PR-025 owns retention/deletion of these records.

The transaction deduplicates `(provider, provider_event_id)` with exact digest comparison, stores the immutable normalized observation, derives event facts and commits suppression/completion together. Changed content under an existing receipt conflicts. A database failure returns failure and rolls back the entire receipt/effect; the future HTTP adapter must acknowledge success only after durable commit. Unsupported event semantics and conflicting message/key associations are quarantined rather than guessed. Scheduled/in-flight/unmatched callbacks stay pending with a short deferral. Recovery selects at most 20 due inbox IDs; deferral rotates unresolved entries so they do not monopolize the first batch.

Resend submissions carry a `tt_delivery_key` tag containing the stable opaque provider key. A signed callback can therefore correlate a timeout before the acknowledgement/message ID was saved. It never matches by callback recipient address. Both known message ID and supplied tag must agree; conflicting identities are quarantined. This extends the still-disabled provider payload before production activation; no deployed live payload is migrated or resent under a changed body.

## Delivery facts, permission and metrics

Delivered, delayed, bounced and complained observations remain independent facts. Reordered events do not regress dispatch state or imply that inbox arrival equals provider acceptance. A positively correlated callback can settle an **uncertain** send as accepted with the same identity and permanent receipt. An in-flight dispatch is not overwritten; its callback remains replayable after acknowledgement. Cancelled/suppressed/failed sends do not become accepted. An anonymized send does not regain its recipient or become actionable.

Complaint/permanent bounce effects serialize on the same sorted subject/send guards used by dispatch. All-email suppression and address lookup tombstones commit with the event, preventing future sends, including a re-entered address. Resend's documented `email.bounced` is permanent; `email.delivery_delayed` is temporary and does not globally suppress. Already handed-off mail cannot be recalled.

Open/click facts require separate current **analytics/email** permission and no current analytics/email suppression. The existing product flows do not grant that permission automatically. Received callback minima support restricted verification/recovery only. Scanner signatures are classified `machine`, ordinary browser-like clicks at most `suspected_human`, absent/unknown agents and opens `unknown`; no observation proves human activity or becomes billable here. Raw agents/IPs are discarded. Operator status derives delivered/bounced/complained booleans per send, so repeated or separate duplicate observations cannot increment a delivery counter twice. P1-PR-024 owns aggregate analytics and must continue using distinct eligible send identities and current privacy guards.

## Preferences and final actions

Preferences use the existing independent unsubscribe MAC audience and contact-intent binding; they expose only the proof's purpose/status, never address lookup or another purpose's preferences. GET/HEAD reads do not grant or withdraw permission. Existing confirmation and withdrawal services remain POST-only. Confirmation proof cannot substitute for unsubscribe proof and vice versa.

`oneClick` accepts exactly the decoded `List-Unsubscribe=One-Click` POST field and delegates immediate, idempotent withdrawal to the existing consent/suppression transaction. It needs no login, cookie, CAPTCHA or additional confirmation. The scope is the subscription/purpose identified by the MAC; a report link does not withdraw independent offers. A headers helper generates the two RFC 8058 headers only after validating the proof and configured HTTPS origin. It is preparation for later rendered mail; DKIM coverage and actual recipient-client compliance remain release evidence. Ordinary preference forms still require S4's browser security controls; the one-click machine POST must remain cookie-independent.

Feedback and education links use a separate versioned HMAC audience, stored digest, fixed send/slot identity, expiry and revocation. Replays cannot change a destination or final answer. Helpful Yes/No GET/HEAD displays a minimal page; only a deliberate POST records the immutable answer. Repeating the same answer succeeds; a different answer conflicts. The link MAC grants no report edit/view/PDF authority and cannot confirm a contact or redeem an offer.

Redirects accept only a configured first-party HTTPS origin and clean `/learn/<slug>` paths currently present in the reviewed public publication view. External/protocol-relative destinations, backslashes, queries, fragments and encoded traversal are rejected. Visits recheck publication, send/contact/subject/report lifetime and revocation. A withdrawn or expired article stops redirecting. The service never accepts a destination on a visit, records no final action/analytics on GET, and returns no token-bearing destination. Private report/PDF routes continue through their existing capability services; this PR introduces no alternate bypass. S4 must emit no-store, noindex and `Referrer-Policy: no-referrer` on bearer/action routes and redact tokens from logs.

## Operator recovery and database contract

`pnpm exec tsx scripts/mail/recover.ts pending|status <send-id>|replay <inbox-id>|reconcile <send-id>` is a trusted operator command. Configure `MAIL_OPERATIONS_DATABASE_URL` for `tt_private_runtime` and `CONTACT_LOOKUP_VERSIONS` in the process environment. Keep credentials out of command arguments/history. Reconciliation may read a **known** provider message ID only when `MAIL_PROVIDER_READS_ENABLED=true` and a server-side `RESEND_API_KEY` is configured. The one-connection pool drains on exit; errors expose stable application codes only.

Retrieval happens outside SQL. Missing identity/404 returns manual-review guidance; it does not invent a lookup by idempotency key or create a replacement send. A matching positive provider observation settles uncertain acceptance, and authoritative complaint/bounce retrieval also suppresses. Retrieval never fabricates a provider delivery event or metrics. Unknown/failed observations do not authorize automatic retries. There is no force-accept, force-resend, recipient-change or dedupe-window reset command. P1-PR-027 owns automatic cadence, worker binding and alarms; operator commands are available now.

Migration `0028_mail_events` adds an immutable six-column `email.callback_observations` child of the durable inbox, indexed by message/key, plus a provider/due inbox index. Private runtime receives the needed explicit grants on observations, event facts, link records and feedback; public/catalog/CMS roles receive none. Existing send/event/link/feedback identities and CAS constraints remain. P1-PR-025 must delete observations before inbox rows, and links/feedback/events before send erasure, with current tombstones preserved. Full-schema synthetic recovery checks do not establish this future actual erasure graph or hosted RPO/RTO.
