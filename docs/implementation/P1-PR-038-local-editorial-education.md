## Application boundaries and native persistence

The domain module validates bounded plain-text drafts and defines the optimistic revision state machine. The application service reauthorizes current roles, separates authors from reviewers, captures commands before asynchronous work, binds unchanged retries to the same actor and command digest, and emits revision-bound publication requests. Its store, authorization and publication ports support other interfaces without moving business logic into React. Every publication/withdrawal remains subject to the existing content service and public projection. A committed CMS revision followed by an uncertain publication result can be retried unchanged; a stale revision or changed payload is refused.

The new opt-in headless Payload adapter uses the pinned native Local API, native version tables, editorial-review collection and one native transaction. It does not introduce a parallel custom CMS schema or write CMS tables directly. A private object-identity request seal and `overrideAccess: false` deny forged contexts. Transaction-scoped advisory serialization and bounded lock/statement waits protect the exact document; compare-and-save uses the recorded revision. Restoring one of the document's retained native versions makes a higher **unreviewed draft**, never a historical public approval. The existing Payload configuration retains at most 20 versions. Legacy documents without the ownership envelope fail closed and require a separately reviewed adoption plan.

Native admin and GraphQL remain disabled. Only the new headless configuration disables Payload's admin edit-lock mechanism: native updates otherwise delete admin lock rows. The explicit application transaction/revision protocol governs this interface. The original production configuration is untouched. Activating a real CMS later requires reviewed identity issuance/MFA, author/reviewer/publisher assignment and revocation, DB grants, audit retention, existing-document adoption, connection ownership/budget and the existing deployment/acceptance inputs. This PR does not select those authorities.

The disposable integration proof uses a new synthetic restricted role and grants on existing fixture tables, including the relation-row deletes required by native Payload updates. They exist only in its owned throwaway databases and are removed during teardown. Pinned Payload 3.92 retains its first pool client for a reconnect listener and does not end the pool in `destroy()`: the fixture captures only its own first client, rolls back its own remaining transactions, releases that client and ends its owned pool. This is test-support cleanup evidence, not production pool-lifecycle acceptance. Package importer changes reference already pinned Payload/PostgreSQL versions; no dependency override or threshold is weakened.

## Editorial interface

`/editorial` is an explicit loopback-only local preview. The separate editor bundle keeps credentials in memory, sends authorization only in headers, stores no staff credential and uses no cookies. The proxy and handler require exact Host/Origin, a fixed local upstream, bounded request/response sizes and deadlines. Unknown results retain a frozen command/key for reconciliation; definite validation/permission/conflict responses allow correction. Duplicate clicks are guarded synchronously. Authoring, independent review/rejection, publication, withdrawal and native-history rollback use their current role/state controls. Reviewers and publishers see read-only article fields; authors must save edits before changing review/publication state.

Redirect controls require a publisher and a distinct currently authorized reviewer, validate the existing bounded CSV/rule contract and use immutable snapshot revisions/checksums. They load current authority before preparing a higher revision. Retry submits the same frozen snapshot; rollback means a newly reviewed higher revision. The public boundary permits only validated relative public targets and 301/302/410 behavior; incoming queries are discarded on redirects. It does not provide an open redirect or expose staff state.

## SEO and publication limits

SSR provides titles, descriptions, canonical URLs, same-origin public hreflang links and visible-content JSON-LD (Article/DefinedTerm, Organization, WebSite and BreadcrumbList). JSON is escaped without changing semantic text. Public projections exclude the private editorial envelope, staff IDs and command bodies. Draft, withdrawn, expired and future-dated content is unavailable; the hub queries only current eligible public projections. Metadata is read from the public service, never directly from a staff draft.

Sitemap XML serialization accepts bounded same-origin public canonical entries and valid timestamps; private/capability/query-bearing paths are refused. Under current holds, the actual local endpoint intentionally emits an empty sitemap, `robots.txt` disallows crawling, HTML and headers retain noindex and nofollow, and Search Console has no actual verified property or indexing action. An explicit validated verification-token head contract is exercised with a synthetic token only. Real domain ownership, indexing, the existing crawler/search provider and production composition remain separate acceptance work; structured data promises no rich result.
