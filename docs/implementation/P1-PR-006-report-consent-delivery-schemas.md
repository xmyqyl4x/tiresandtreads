## Integrity and service boundaries

Report versions and comparison/item snapshots reject UPDATE. Reports use a named, initially deferred `(id,current_version)` FK so one transaction can create a report and its first version. Drafts reference an actual base version and carry a positive revision and seven-day activity TTL. Picks have unique ranks 1–5; comparison revisions have four numbered slots and unique source selections. Quotes retain optional SKU links, explicit quantity/currency/cost basis and bounded components. Bundle/rule IDs pin exact records; publishing eligibility, coherent bundle membership, snapshot sanitization and domain eligibility are later service validations.

View capabilities contain only 32-byte token digests with key versions and fixed/latest report bindings. Download grants add explicit `report_id`, `report_version`, `view_scope`, `owner_subject_id` and `share_version_binding` columns. Composite FKs bind the asset to its report/version/scope, the owner session to the report owner, or a share capability to the same report and eligible fixed version. Generated capability binding 0 represents latest. Exactly one authority is allowed; a share cannot download owner-only output. Grant lifetime is at most 15 minutes. Expiry/revocation, current owner permission, current/latest version selection, asset readiness/purpose and object existence must still be rechecked by services on every use.

Contacts contain opaque, bounded envelope bytes and key versions. SQL cannot prove encryption or key custody; later cryptographic adapters must encode/authenticate/decrypt the envelope. Lookups have HMAC/key-version uniqueness, with one lookup per contact/key version. Cross-key identity resolution is a transactional service responsibility. Notice purpose is part of the consent-event FK. Consent projection FKs bind its source event to the same subject, purpose and scope; current grant/action/policy semantics and subject permission revision updates remain atomic service operations. GPC receipts reject identity sharing/targeted advertising selections. Notices/events are immutable facts; identifying mappings are separately erasable.

Rights requests and steps have bounded status/retry fields and unique `(request,store,action)` identities. Ciphertext/key pairs cannot be half-populated, completed requests require completion timestamps, and hold/review/expiry indexes support bounded jobs. Deletion/suppression markers deliberately have no contact FK and can survive contact removal. SQL does not enumerate all stores, approve exceptions, execute deletion, verify deadlines by jurisdiction or prove anonymity.

Sends bind a recipient separately from the report owner, with composite owner/version/comparison FKs. Report cancellation and send deadlines coincide and are at least 60 seconds after accepted request creation; `accepted_at` means provider acceptance. Dispatch states have timestamp/payload requirements and allowed transition edges. Recipient, report/comparison, template, provider identity and deadlines cannot be edited in place. After dispatch starts, payload asset/hash remain frozen through uncertain reconciliation. Requested purposes and the recorded consent decision never replace a current authorization check. Template versions freeze after review/publication; topic selections and signed links use stable identities. Safe dispatch, cancellation races, rendering, current suppression and provider reconciliation still require their S2/S3 implementations.

Privacy erasure can atomically clear recipient/owner/report/comparison/notice/payload references, clear requested purposes and set `anonymized_at` only on an ineligible state. An erased row cannot resume processing. Attempts, events, links, payload objects and other children still require ordered fulfillment; this PR supplies storage constraints, not a purge worker. Minimal send receipts use a logical `send_id` without an FK so deduplication can survive removal of a send. Purpose-specific retention and access remain mandatory.

Request identities fix actor/operation/key/body digests and canonical version; completed retry records have at least a seven-day lifetime. Outbox event identities and webhook provider/digest identities cannot be rewritten. Response/outbox JSON has narrow allowed keys and byte bounds; services must validate each value and never put secrets in allowed string fields. Job checkpoints remain bounded private operator data. Lease shape and increasing fencing generations reject partial/reused claims; services must use compare-and-set tokens/generations to reject stale worker publication. Database identity and lease constraints alone do not prove exactly-once execution or transport delivery.

All FKs, including `privacy` and `email`, have leading indexes. Additional access paths cover report history, due sends, incomplete attempts, pending/leased work, expiry and review queues. These are provisional access paths, not production performance evidence. S2 must establish bounded query plans and transaction budgets.

## Audit sequencing and retention

`admin.audit_events` stores minimal action/resource-kind/result/digest/field names. `audit_identity_links` holds separately erasable staff/subject/encrypted context. Migration 0009 creates these tables, adds named `import_publications_audit_fk` and its leading index, then removes the 005 NULL-only check. Existing NULL approvals survive; no approval is fabricated. Future publication services must validate authorization and event meaning, even though the nullable FK permits previously recorded publications. P1-PR-007 extends this foundation with staff configuration and its other assigned schemas.

New report/consent/audit snapshot guards reject UPDATE, while existing runtime roles have no DELETE rights. Ordered deletion by the restricted migration owner is possible for tests and later reviewed retention procedures; immutable snapshots are not permanent personal-data retention. Existing published-source/publication history guards from 005 are unchanged. Migrator DDL/TRUNCATE power is operator authority, never a runtime escape hatch. Full deletion orchestration, restore replay and S1 recovery evidence remain later planned work.
