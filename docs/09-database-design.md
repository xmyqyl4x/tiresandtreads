Each table has one module owner and one migration owner. Foreign keys can cross schemas inside the application database; no FK or transaction crosses into Payload or S3. Stable IDs, schema versions, outbox events, and reconciliation bridge those stores. Never let a CMS editor write consent, report, engine, or billing tables through a generic admin API.

## 2. Relational conventions

The table catalogue below is the implementation contract for core columns; module migrations may add technical columns with documented purpose. Notation: `PK` primary key, `UQ` unique, `FK` foreign key, `?` nullable, `ts` UTC `timestamptz`, `json` versioned/validated `jsonb`, `bytes` `bytea`. Unmarked columns are `NOT NULL`. Unqualified FK targets use the current schema; cross-schema targets are explicit.

- Unless a composite key is listed, each table has `id uuid PK` and `created_at ts DEFAULT now()`. Mutable records also have `updated_at ts` and `revision bigint DEFAULT 1 CHECK (revision > 0)`. Event/snapshot/version rows are append-only during their permitted lifetime; retention deletion is a separate privileged operation.
- Use lowercase plural `snake_case` names and explicit, named PK/FK/UQ/check constraints. UUIDs are generated without encoding customer identity. Timestamps are UTC; market timezones are explicit IANA strings for later scheduling.
- Money is `bigint` minor units with `currency char(3)` validated against enabled currency codes. Bounds reject negatives except signed ledger postings/refunds. Ratios/measurements use bounded `numeric`, not floating point where rounding affects decisions. Store tire dimensions and distance with explicit canonical units; keep original unit/source alongside imported facts.
- Use `text` plus named checks/reference tables for evolving status/purpose codes, so releases can expand allowed values safely. Country/market, locale, unit, and purpose are validated against their registries. No universal `status` meaning across unrelated entities.
- Relational columns own keys, ownership, money, time, permission, status, and frequently filtered facts. JSON holds validated immutable engine/presentation snapshots or versioned rules. Do not hide foreign keys, coupon uniqueness, tenant boundaries, or balances inside JSON.
- Default FKs use `ON DELETE RESTRICT`. Aggregate-owned disposable children can cascade only through an authorized purge; erasable identity links may cascade or be explicitly detached. Cross-domain deletion is an orchestrated operation, not an indiscriminate cascade.
- Index referencing FK columns when used for joins or parent deletion; PostgreSQL does not automatically create those indexes. A `CHECK` cannot enforce a cross-row total or arbitrary relationship. Use FKs/unique constraints plus locked transactions or a reviewed constraint trigger for such rules. These distinctions follow [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).
- Keep credential/token digests and key versions together. Never store raw capability, verification, API, or webhook secrets in tables or logs. Envelope-encrypted fields store ciphertext, encrypted data key, algorithm/key version, and necessary nonce/authentication metadata; adapters own the concrete encoding.

**Versioned source row convention:** catalogue rows marked **V** have `dataset_version_id uuid FK app.dataset_versions`, `source_record_key text`, and `UQ(dataset_version_id, source_record_key)`. Their `id` identifies one immutable revision; provider identity plus source key identifies the source entity across revisions. Cross-revision references are explicit. Where two rows must belong to the same dataset, add `UQ(dataset_version_id,id)` and a composite FK. A published dataset is never modified in place.

Exact location/shop text is not copied into public/shared DTOs, analytics, or engine-cache keys. Full normalized private input remains protected where needed for owner editing; the immutable engine snapshot uses only the versioned facts required for reproducibility.

**006 physical refinements:** Download grants carry report/version/view scope plus nullable owner subject or share version binding. Composite FKs bind asset→report/version, owner session→report owner, and share→same report/fixed version (generated binding 0 means latest). `canonical_version` fixes idempotency hashing; outbox/jobs use lease tokens and monotonically increasing generations. Audit events and erasable links are created in 006 so the existing import approval reference becomes a validated FK. Published-bundle eligibility, current permission and purpose rules remain later service obligations. Snapshot UPDATE guards coexist with restricted, ordered retention DELETE; no runtime gains DELETE rights here. See [006 boundaries](implementation/P1-PR-006-report-consent-delivery-schemas.md#integrity-and-service-boundaries).

**Report pointer integrity:** create a report in draft state, insert version 1, then set current_version and active state within one transaction. The circular current-version FK is deferred until commit. Reruns lock the report, check expected base/revision, insert a new version and items, then advance the pointer. Normal roles cannot UPDATE a historical version. The privacy purge can delete the parent aggregate and its children under a dedicated procedure; immutability is not indefinite retention.

**Comparison integrity:** each save creates a new comparison revision and up to four immutable slot rows. Delivery references that revision, never a mutable "current comparison." The application validates item eligibility and source identity; the database enforces revision ownership, slots, and unique selections.

**Event receipt and permission:** verify signed context against current server state; serialize receipt with consent withdrawal/deletion using the subject guard and permission_revision. Reject stale/unknown revisions or deleted subjects, not just expired cookies. Each accepted batch is at most 50 events/64KB for one authorized subject. Insert/dedupe events and increment each affected dirty-day revision once in the same transaction. Lock dirty days in ascending date order. Duplicate ID/body is an existing receipt; mismatched digest/subject returns a generic conflict without exposing the other event. Denied collection returns 204 without storing behavior; invalid input returns 422, limit exhaustion 429, unavailable receipt 503; 202 means committed. Clients may retry only within 24 hours of occurrence and with a valid current context; reject events over 24h old or more than 5 minutes in the future. These browser-analytics bounds do not change verified delayed-provider-webhook handling.

Keep events' original collection permission and current processing restrictions. A newly granted purpose cannot authorize old forbidden collection. Deletion locks/restricts the subject and marks all days containing that subject's events privacy_blocked in the same initial transaction, before batched erasure begins. Aggregation excludes subjects with an active analytics-erasure restriction even if some source rows await physical purge. The initial restriction and each purge batch increment both requested_revision and privacy_revision for affected days; ordinary new events increment only requested_revision. Each purge batch invalidates its affected days again; no intermediate rebuild can reintroduce the restricted subject. Track the restriction until all relevant source rows are erased. Bound the initial day enumeration by the 13-month retention window and use the subject index. Remove subject-linked analytics before deleting its subject FK. Deletion markers plus the subject/permission barrier prevent an old event batch recreating deleted data. Withdrawal stops new collection immediately; the reviewed purpose policy determines whether past permitted events must also be purged. Required operational totals use existing report/send facts, not covert analytics rows without consent.

**Aggregate generation:** the worker leases a dirty day with a unique fencing token and captures requested_revision `g`, privacy_revision `p`, and all metric inputs (including active erasure restrictions) in one consistent source snapshot. In a short publication transaction lock the day, require a matching unexpired lease, unchanged privacy_revision `p`, and completed_revision < `g`. Replace all rows for that day (including removing no-longer-present groups), set completed_revision to `g` and clear privacy_blocked atomically. Ordinary new intake may advance requested_revision beyond `g` while calculation runs: publish the accurate older generation with its timestamp and leave the day pending for another pass. A changed privacy_revision invalidates the candidate and requires recomputation; never publish a generation containing newly restricted data. Duplicate/expired workers cannot overwrite a newer generation. Row replacement and completion commit together, so a crash cannot leave half a generation. Bound retries/backoff and show actual freshness under sustained privacy invalidations or overload.

Dashboard reads join the completed generation and hide any privacy_blocked day. Ordinary intake may leave a previous generation visible with its real timestamp; privacy invalidation may not. Recompute exact counts from retained permitted rows, not additive replay counters. Define unique-session/visitor grain separately; never sum daily distincts into monthly distincts. Minimum-cell and anti-differencing policy applies before any later external/partner aggregate exposure. The initial R1 metrics are internal and do not authorize a data product.

**Limits:** derive hour/day/burst windows from database time and versioned server policy. For each request, consume all applicable fixed-window keys using capped upserts in a single short transaction, in deterministic key order. Roll back all increments if any window is exhausted; successful attempts consume capacity even when the downstream business command later fails. A retried HTTP request is another attempt, while business idempotency still prevents a duplicate effect. Return the maximum applicable Retry-After; SQL failure is 503 for protected actions. Keys for email must use cautious normalized address HMAC even before a contact exists. Rotate HMAC keys with a transition preserving active limits; a key/policy deployment must not silently reset quotas. Existing strictly rolling offer-frequency rules continue to use their dedicated guards/reservations.

Expire buckets after their window plus a short retry/diagnostic margin (initially 1 hour, maximum 48 hours total for the launch hour/day policies). Read validity is determined by current window, never by whether cleanup already ran. Limit accepted bucket cardinality and concurrent writes using configured workload budgets and platform admission controls; alert on growth/hot-key locks. No raw IP/email or analytics session-linking purpose is added by these security records. Verified provider webhooks and RFC 8058 suppression retain dedicated policies and do not acquire a human challenge.

**Cache:** construct keys from canonical non-identifying inputs plus every dataset/engine/rule/schema/locale version relevant to the value. Read only unexpired matching entries. Treat parse/version mismatch as a miss. Bound entries and total bytes per namespace; Inngest sweeps expired entries in keyset batches, and new writes stop at the configured cap until space is available. No automatic sliding TTL or access-time write per hit. Test identical outputs with cache enabled, empty, stale and unavailable; live recall freshness and authorization are checked outside it. Default delivery starts with indexed reads and public CDN caching, so this table is optional rather than a mandatory replacement for every former Redis use.

**Retention and load:** raw events retain the existing maximum 13-month policy, with earlier subject/purpose erasure. Batched purge marks affected days dirty; aggregate retention requires a documented deidentification review or expires with the source policy. Remove finished dirty-day metadata only after associated metrics/source retention is resolved. Start unpartitioned; if volume later warrants time partitions, PostgreSQL requires partition keys in partitioned unique constraints, so add a separately constrained event-identity registry with the full accepted replay horizon before migrating. Do not quietly weaken global event-ID deduplication to per-partition uniqueness.

Use restricted analytics ingest, aggregation and dashboard roles/pools with explicit grants, short statement/lock timeouts and bounded concurrency. Dashboard readers see aggregate views, not raw events or contact tables. Aggregators can read permitted events and write owned projections; collector permission checks use a narrow privacy-service interface, not general access to contacts. Schema separation alone does not isolate compute. Test mixed report/collector/limiter/aggregate/purge load against the [capacity criteria](11-postgresql-and-build-order.md#capacity-failure-and-reconsideration). Scheduled Inngest sweeps drive recomputation/expiry; PostgreSQL stores durable intent and does not run a background worker by itself.

## 10. Transaction boundaries and concurrency

| ID | Invariant | Enforcement and failure behavior | Required test |
| --- | --- | --- | --- |
| DB01 | One command identity produces one report/send outcome | UQ actor/operation/key + body hash; claim and business records/outbox in one transaction; conflict retries read committed result after reauthorization | Parallel duplicate and changed-body requests, UC01/UC06 |
| DB02 | Report head and version belong to the same report | Composite FK, active-state check, report row lock, expected base/revision, immutable version insert | Two reruns; one stale conflict; old snapshot unchanged, UC03 |
| DB03 | Comparison has ≤4 distinct items per immutable revision | Slot check 1–4, composite PK/FKs, source UQ, atomic save | Fifth/duplicate item and concurrent save, UC04 |
| DB04 | Cancellation and dispatch cannot both win | Lock/check scheduled row, database deadline comparison and conditional state update; provider call occurs after commit | Two real connections/barrier, exact deadline and delayed worker, UC06 |
| DB05 | Retried handoff cannot create a new payload/key | Persist fixed payload digest/provider key before call; ambiguous response becomes uncertain; reconcile only with same identity | Accepted-but-timeout and crash after handoff, UC07 |
| DB06 | Provider retry is one logical event | Unique provider/event inbox, digest mismatch quarantine, normalized event UQ | Duplicate, reordered and delayed events, UC07 |

The 60-second window guarantees no dispatch claim before send_after. Cancellation atomically changes a still-scheduled row; if a worker is late, cancellation may still win after the displayed countdown. Once the dispatch claim wins, cancellation returns the existing 409 outcome. Test both orderings at the deadline instead of assuming that a browser timer establishes server state.

Default isolation is Read Committed with explicit unique constraints, compare-and-set updates, and row locks for known aggregates. Use Serializable only for a demonstrated multi-row invariant that simpler locking cannot protect; retry serialization failures with bounded jitter. An optimistic revision protects a specific record, not an arbitrary set-wide total. These choices follow [PostgreSQL isolation semantics](https://www.postgresql.org/docs/current/transaction-iso.html).

Acquire locks consistently (subject/purpose guards → send → partner cap/budget guards → code rows) within each workflow; review inter-workflow lock ordering to avoid cycles. Keep transactions short and do not call external providers while holding them. In `pg`, all statements in a transaction must share one checked-out client; pass that context through repositories rather than calling `pool.query` inside it. See [node-postgres transactions](https://node-postgres.com/features/transactions).

Suppression and send handoff have a defined boundary: withdrawal committed before the final dispatch authorization prevents the applicable content from dispatching. Handoff after that point may already be irreversible; record the decision/permission revision and do not promise recall. Recheck after lengthy rendering immediately before provider handoff. If permission changed before the first attempt, rebuild permitted content or suppress; once a provider attempt is uncertain, do not change its payload under the same key or issue a fresh send to bypass uncertainty.

## 11. Indexes and query design

Index catalogue entries above are initial designs, not measured performance results. Confirm plans with production-shaped synthetic/licensed test data. Use B-tree indexes for equality/range/sort patterns, narrow partial indexes for active work, and selective GIN only for a documented JSON/search query. Do not index all snapshots by default.

| Query | Index/access plan | Bound and caveat |
| --- | --- | --- |
| Picker and exact fitment | Dataset/market/make/model/year + configuration/axle keys | Bounded picker results; approved dataset head resolved once |
| Candidate SKU set | (dataset_version_id,size_code,construction), joined evidence for selected candidates | Batch evidence fetch; no N+1 query per tire/metric |
| Current price evidence | (sku_id,market,observed_at DESC,id) | Filter retailer/currency/basis, apply staleness; no unbounded history load |
| Owner report history | (owner_subject_id,last_owner_activity_at DESC,id) | Keyset cursor; default 25/max100 |
| Report details | PK(report_id,version), item and comparison composite prefixes | Explicit safe projection, no contact joins on shared read |
| Pending sends/outbox/jobs | Partial indexes on state + due time + id; separate lease-expiry index | Predicate uses stable states, not `now()`; compare time in query |
| Capability/recipient lookup | Unique (key_version,digest) | Never log digest/token values; lookup role cannot bulk reveal contacts |
| Partner dashboards | (org_id,status,created_at,id) and relevant composite parents | Tenant predicate present before pagination; aggregate outputs bounded |
| Analytics receipt and rebuild | Event PK/digest, subject index, day/name/market index, pending/lease day indexes; daily metric composite PK | Restricted roles, bounded batch/window; dashboard reads published generations and hides privacy-blocked days |
| Rate limits and optional cache | Composite bucket/cache PK; expiry indexes | Atomic quotas and read-time expiry; no unbounded new-key cardinality or cache access-write churn |
| Retention/privacy queues | (expires_at,id), (status,due_at,id) | Batched keyset deletion; audit counts; avoid large blocking transactions |

Partial-index predicates and query predicates must align to be usable; parameterized statements may affect plan choices. Verify actual prepared-query plans, following [PostgreSQL partial-index guidance](https://www.postgresql.org/docs/current/indexes-partial.html). `SKIP LOCKED` is for queue/code allocation, not for silently skipping records in user-visible reads.

Record E02 budgets for pool size, statement/lock/idle transaction timeout, query count, result bytes, and per-use-case latency; tune from measurements and provider limits. Monitor slow queries, lock waits, deadlocks, bloat, pool wait, import duration, storage growth, outbox lag, and replication/backup health. Prefer one bounded fetch/read projection over loading an ORM relationship graph. Analytics and large exports run asynchronously and do not contend with report request pools without explicit limits.

Partition only when volume, retention removal, or query plans justify it. Candidate high-volume tables are raw events/inbox/attempts; monthly partitioning changes uniqueness constraints and must preserve global provider-event dedupe via an unpartitioned identity registry or equivalent proven design. Small R1 tables remain unpartitioned.

## 12. Roles and row security

Domain import workers receive staging grants; publication requires a separate reviewed service permission. P2 inference/image workers read only authorized task packets and owned objects and publish through fenced service commands; they receive no broad contact, partner export or CMS rights. Shared AI scope creation requires a reviewed nonpersonal template policy. Owner query scoping and compound ownership tests cover every AI/photo repository.

| Role | Allowed | Denied |
| --- | --- | --- |
| Migration owner | Reviewed DDL for its database; controlled backfill | General web runtime use |
| Public report runtime | Published catalogue reads, authorized report/application operations | Schema changes, staff/CMS credentials, raw contact export |
| Delivery/privacy worker | Narrow contact decrypt/permission/send/fulfillment procedures | General editor access or unrestricted partner export |
| Partner runtime from R2 | Own-organization rows under RLS plus approved aggregate views | BYPASSRLS, table ownership, contact/frequency identity tables |
| Staff runtime | Module-specific approved operations with role checks and audit | Automatic unrestricted access because user is staff |
| Analytics collector / worker / dashboard reader | Separate narrow event receipt, owned projection rebuild, and aggregate-view grants | Raw event reads by dashboard role; contact reads, operational consent/send/ledger writes or DDL |
| CMS runtime/migrator | Its separate database/approved public storage | Application DB ownership or contacts |

A single deployment may compose adapters using different restricted credentials; do not expose one superuser pool as a universal repository. R1 report-owner authorization is enforced in application services and repository scoping; report-owner RLS may add defense in depth but is not claimed to exist without implementation/tests. Partner RLS is mandatory for R2 and must include `USING` and `WITH CHECK` policies as appropriate.

Set organization context transaction-locally from a verified actor; missing/empty context denies access. All tenant queries share that transaction connection. Use a runtime role that neither owns tables nor has BYPASSRLS; consider FORCE RLS for owner-executed maintenance where appropriate, without assuming it restricts superusers. PostgreSQL documents these [RLS bypass rules](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Restrict function execution grants and pin safe search paths for any security-definer procedure; avoid dynamic SQL in privileged functions.

## 13. Retention, purge and recovery

[AI/photo retention](14-ai-analysis-and-photo-design.md#privacy-retention-limits-and-operations) is normative for new P2 records: images/candidates 24h or explicitly saved images ≤30 days; owner artifacts follow report lifetime (unattached ≤30 days); reviewed shared artifacts ≤30 days; reuse validity ≤7 days/source expiry. Purge reuse entries and artifacts as well as objects, and fence late workers. Domain staging/diffs/rejections expire within 30 days or earlier source-rights limits.

| Data group | Baseline retention and action |
| --- | --- |
| Drafts | 7 days after activity; delete draft and temporary authority |
| Anonymous report aggregate | 180 days after owner activity, capped at 12 months from creation without renewal; revoke shares/downloads, delete private inputs/quotes/compare/snapshots/assets |
| Unsaved quote private notes | 30 days; deliberately saved notes follow report retention |
| PDF bytes | 30 days from generation, earlier on deletion; metadata tombstone records object purge |
| Pending offers confirmation | Token 7 days; pending subscription 30 days |
| Contacts | At most 24 months inactivity while purpose continues; erase lookups/ciphertext/links; retain only justified suppressions |
| Email events | 24 months; remove identifying links on deletion sooner; minimal receipt retention reviewed by purpose |
| Raw webhook/security data | 30 days baseline; encrypted/restricted; documented incident exceptions |
| Consented analytics | At most 13 months raw data; earlier subject/purpose purge and immediate aggregate invalidation; only reviewed deidentified aggregates may persist |
| Rate buckets / optional cache | Buckets expire after window plus 1h (launch max48h); cache TTL initially ≤24h and source validity; read-time expiry plus bounded sweeps |
| Consent/audit evidence | Active reliance plus reviewed limitation period; erasable identity mappings and minimal event facts |
| Suppression/deletion markers | Necessary enforcement/replay period, reviewed annually; protected pseudonymous records |
| Catalog/licensed data, financial/legal records | Retention follows license/financial/legal policy set at the relevant gate; no invented universal TTL |

On deletion: (1) verify scope, suppress and revoke; (2) enumerate affected resources and create idempotent fulfillment steps; (3) remove private artifacts and erase/detach identifying SQL data under controlled transactions; (4) purge analytics events and rebuild invalidated generations, request applicable provider deletion and record evidence; (5) enforce markers on imports/outbox replay; (6) close only when required steps or documented exceptions are resolved. Detached events/sends cannot remain eligible for processing. Report deletion removes snapshots despite their normal immutability; do not keep copies in JSON audit or cached payloads.

S3 object keys are random resource IDs, not emails/report capabilities. Purge object versions and derived exports under the selected bucket versioning/lifecycle policy; a delete marker alone may not remove old bytes. Daily backup/PITR scope and inaccessible backup expiry follow the reviewed recovery plan. After restore, replay current suppression/deletion records before opening application access; prove RPO/RTO through a drill. Deletion of identifiers is not equivalent to permission to retain every derived feature.

The [008 recovery procedure](implementation/P1-PR-008-database-validation-recovery.md#backup-and-restore-procedure) validates 119 app/28 CMS tables (including ledgers), constraints, indexes, grants and complete synthetic row fingerprints in a second cluster. Current deletion/suppression replay and CMS publication reconciliation precede runtime reopening. This supplies local S1 evidence only: full-size chosen-host recovery, protected independent journals, object bytes and provider recovery remain release obligations.

## 14. Migration and implementation sequence

The [approved option-C deployment plan](16-deployment-and-local-environments.md) uses local Docker dev/test/stage and standard `pg` connectivity to PostgreSQL outside Vercel, with bounded pooling, separate app/CMS migration runners and off-host recovery ownership. Neon is no longer the prescribed production provider; typed tables/invariants remain unchanged. The approved [environment topology](16-deployment-and-local-environments.md#environment-topology-and-local-resources) uses separate dev/stage clusters and disposable tests without modifying existing native databases.

1. **S0/E02 prerequisites:** pin the production PostgreSQL major/driver, isolated test environments, migration ownership and least-privilege credentials. Resolve Payload/Clerk compatibility headlessly; establish restore and invariant harnesses.
2. **S1/E04a schema:** create app/privacy/email/admin/analytics foundations, then referenced identities/assets/staff/lookup tables, E35/E36 reference/staging/recall extensions and E37/E38 public SEO/ad operations, catalog and coherent bundle tables, report/version/comparison tables, contacts/permissions, delivery/reliability, content/config, event/aggregate and limiter tables. Resolve circular report pointers through deferred FKs and staged constraint creation. Generate separate Payload migrations. Seed synthetic fixtures and prove empty/upgrade, real-role, constraint, purge/replay and restore behavior. Later-release tables and unused optional caches wait.
3. **S2/E04b data access:** define pure entity/value and repository port contracts, Drizzle storage models, explicit mappers, authorized query projections and one-client transaction contexts. Implement and verify repositories against the accepted schema with rollback, concurrency and query-plan evidence; no Active Record objects or service logic embedded in SQL adapters.
4. **S3 service behavior:** E05/E06/E08/E10a/E11–E18 backend parts implement invariants and use cases using those ports; prove business and database behavior before exposing handlers. Race tests accompany consent, dispatch, analytics, limits and privacy workflows.
5. **S4/E34 APIs:** run headless functional/contract/security/load checks against real repositories; pass the complete launch API gate before S5 screens/templates. Future schema adjustments use reviewed expand/contract migrations and dependent test reruns.
6. **R2/R3/R4:** add P2 AI/reuse/photo schema from docs/14 and repeat schema → data access → services → API → presentation for tenant/offer, billing, ownership/client and audience extensions with their own tests and release gates.

Use reviewed versioned migrations with checksums and one deployment executor per database.
