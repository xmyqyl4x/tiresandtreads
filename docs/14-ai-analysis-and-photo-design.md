# AI analysis, persistent reuse and tire photos

**Specification 1.0 · October 22, 2026 · Approved October 23, 2026.** P2 adds AI-assisted report explanations, PostgreSQL reuse and web tire-photo extraction; P3 reuses them from the Expo app and scoped AI-client tools. Nothing here is implemented. The deterministic engine, source rights, privacy, database-first construction and TDD remain prerequisites. This specification extends [database design](09-database-design.md) and [four live releases](12-live-product-phases-and-gap-review.md).

## AI responsibility and provider boundary

The application calls the OpenAI API from a server-only L6 adapter behind `AnalysisProvider` and `ImageExtractionProvider` ports. Use the official SDK and Responses API with strict structured output where supported; pin the SDK, model snapshot or explicit model identifier, schema and prompt at the P2 feasibility gate after evaluation. A consumer ChatGPT subscription or browser session is not the application integration. Keep the ports narrow; no vector database, autonomous agent framework, Redis or ClickHouse is required.

The allowed use is to explain already verified choices, summarize tradeoffs from supplied facts, produce questions for an installer and suggest relevant reviewed education. The model does not decide fitment eligibility, recall clearance, tire condition, rankings, prices, savings, load/speed requirements or legal compliance. Those remain L4/source-controlled values. Do not pass commercial bids or ad performance into the AI context. AI text is labeled and visually separate from the authoritative report facts.

L3 `ReportAnalysisService` builds a bounded context packet containing normalized confirmed parameters, locale/market, immutable report outcome, reason codes, authorized evidence/citation IDs, source versions, and curated advice facts. Omit email, precise address, full ZIP, VIN, owner/share tokens, free-form contact notes and unrelated history. Prefer climate category to location. Runtime facts and imported text are untrusted data, never instructions. No model-driven network browsing, arbitrary tools, database writes or external actions are part of this use case.

The output schema contains summary, supported tradeoffs, limitations, installer questions and citations to supplied IDs; lengths/item counts are bounded. The presentation layer renders plain text, not provider HTML or executable Markdown. Source IDs must exist, be authorized/current and support their attached claim; numerical statements must match supplied authoritative values. Reject unknown citations, fabricated values, re-ranked choices, unsafe condition claims, schema failures, refusals and incomplete/truncated responses. Structural validation alone is insufficient: [OpenAI Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs) explicitly notes that conforming output can still be mistaken. At launch constrain factual statements to validated claim/reason IDs and render critical numbers from source DTOs; specialist-reviewed evaluations test the remaining prose.

## Report enrichment flow

1. Create the deterministic report using the current approved data bundle and existing safety checks. Return it immediately with optional analysis status `not_requested`, `pending`, `available`, `unavailable` or `expired`. AI never extends the core report response-time budget.
2. On an explicit assistance request, authorize the owner, capture the notice/processing choice and data scope, enforce per-owner/IP/cost quotas, and compute the exact reuse identity below. A valid authorized artifact may be attached without another provider call. Reading a previously authorized artifact does not authorize a new external call after processing choice withdrawal.
3. On a miss, commit request/job identity and outbox work in PostgreSQL. Inngest claims a short lease, rechecks permission/source validity and reserves budget before calling the provider outside a DB transaction.
4. Validate the response, record model/prompt/schema/evidence versions and publish one immutable accepted artifact plus its attachment under the current lease fence. Rejected/failed/uncertain results never become a reusable success. If inputs, rights, permission or live safety state changed while running, discard the result and reconcile cost; do not attach stale output.
5. Expose owner-scoped status/attachment APIs. The UI offers manual explanation/education when assistance is delayed or unavailable. Never retry indefinitely or auto-send a second report email when AI finishes.

An analysis attachment is versioned independently from the immutable engine report. Before scheduling delivery, freeze the chosen analysis artifact (or the explicit no-AI fallback) into the existing presentation/send version, alongside report/comparison/template versions. PDF and email render that exact selection; retries do not regenerate AI. A later refreshed analysis needs an explicit new presentation and ordinary send/cancellation rules. A revoked fact or new recall produces the existing current safety overlay and may hide affected AI guidance; historical text is not presented as current assurance.

## Persistent reuse and refresh

This is a **required P2 business artifact store in PostgreSQL**, separate from the optional ≤24-hour pure computation cache in DB20. It persists accepted outputs, provenance and attachments. It does not rely on provider prompt caching or stored provider responses.

An exact lookup identity is SHA-256 over a versioned canonical serialization of task type, market/locale, normalized confirmed parameters with explicit units/unknowns, authoritative output/claim hashes, dataset bundle and source/mapping/advice versions, engine/rule versions, provider/model identifier, prompt/output-schema/validation-policy versions and reuse-scope ID. Arrays are sorted only where order is semantically irrelevant; round only according to declared domain rules. Store the canonicalization version and verify the canonical input digest/manifest on a hit. A model alias changing underneath a deployment is a new model revision and invalidates eligibility.

Owner-specific analysis uses a scope tied to the verified subject, including guest subjects; it can be reused for that owner's exact matching input without embedding a report ID when report identity is irrelevant. Cross-owner shared reuse is allowed only for approved general explanation templates built from a strict nonpersonal parameter allowlist, with no owner identifiers, precise location, free text, images or identifying combinations. A content reviewer approves the template and reuse policy. Deriving a shared artifact by merely removing the subject ID from a private prompt is prohibited. Photo outputs always stay owner-scoped. Exact matches are required; semantic/nearest-neighbor similarity never substitutes for safety-relevant parameter equality.

Initial reuse TTL: at most **7 days** for general explanation and owner report analysis, shortened to the earliest relevant evidence/license expiry. Photo extraction is reusable only for the same owner's identical sanitized image hash and extraction model/schema, within the image's retention window. Read-time validity checks always compare current permission, source/claim invalidation and safety state; TTL alone never establishes freshness. New recall/fitment/policy/prompt/model revisions, corrected data, revoked rights, owner deletion or withdrawn processing invalidate affected keys immediately through transactional dirty state and outbox propagation. Each read checks authoritative revision state so a delayed job cannot expose revoked guidance.

An hourly bounded job refreshes only popular still-eligible shared keys and expires cold entries; owner-scoped work refreshes on a new authorized request, not by reprocessing every user's data silently. Refresh at 80% of TTL only if the entry is still valid and budget allows. Valid old output may serve until expiry; expired or invalidated output is never served as fresh while regenerating. The deterministic report remains available. One worker per key claims a lease; a generation/fence token rejects late publication after lease expiry. Deadlines, bounded retries and a circuit breaker preserve provider and database capacity. Provider timeouts can incur a charge even when no artifact is published: do not claim exactly-once external billing.

## Tire-photo user flow and limits

P2 web allows optional sidewall photos and close-ups; P3 app camera/upload uses the same APIs. Explain the purpose before upload and request only a tire crop without people, license plates or location details. Manual entry remains fully usable. The service may suggest visible tire brand/model, size, load/speed marking, DOT/TIN/date fragments, seasonal/run-flat markings and image-quality feedback. Every candidate shows its source image and uncertainty; low-confidence or conflicting readings remain unknown. Confidence is a calibrated product status, not an unverified model probability.

The user confirms or corrects each field before it changes assessment inputs. Record extracted versus corrected values and origin, then validate them with the same size/code rules and source lookup used for manual entry. A confirmed tire sidewall size is still not proof of approved vehicle fitment. A partial DOT/date code cannot establish recall clearance; request another view or manual/full-code verification. Do not claim to measure safe tread depth, pressure, internal damage or roadworthiness from a normal photograph. Condition concerns lead to a physical measurement/installer check and approved educational guidance. [OpenAI vision documentation](https://developers.openai.com/api/docs/guides/images-vision) describes accuracy, small-text and rotation limitations that inform this confirmation flow.

Upload intent binds a random private S3 key to owner, purpose, checksum and short expiry. Initial limits: 4 images per assessment, 10 MiB each, decoded image ≤40 megapixels; supported JPEG/PNG/WebP, with HEIC only after a tested safe conversion path. Upload grants expire within 10 minutes. Finalization verifies bytes, MIME/magic, dimensions, quota and object ownership; repeated finalization is idempotent. Quarantine, scan and decode in an isolated bounded job, strip EXIF/location metadata, re-encode and downscale for the selected provider. Originals and sanitized derivatives are never public CDN assets. Do not accept arbitrary remote image URLs.

Only a sanitized image is sent through the provider adapter after the explicit processing choice and permission recheck. Use direct image bytes where supported or a tightly scoped private delivery mechanism; never expose long-lived storage URLs or capability tokens in logs. Image content can contain adversarial instructions; treat it solely as extraction input, with no model tools. Cap dimensions/token budgets and report blurry/unsupported/unreadable outcomes honestly. Users may remove images/candidates and continue manually.

## Privacy, retention, limits and operations

Show a separate AI/photo processing notice and explicit action; declining does not block deterministic advice. This is not marketing/ad consent and cannot be repurposed for audience profiles, model training, publication or sales. Recheck current authorization before the external call and publication. Use `store: false` where supported, minimize retained provider application state, and verify the selected account/endpoint/model data controls and image exceptions. This setting does not itself promise zero retention: [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data) distinguish application state, abuse monitoring and special cases. Record provider agreement/region/subprocessor/retention facts at G2 for P2; do not claim zero data retention without the relevant approval and configuration.

| Data | Proposed maximum retention | Refresh/deletion rule |
| --- | --- | --- |
| Unconfirmed uploads and sanitized images | 24 hours from upload | Earlier owner deletion/processing withdrawal; purge all object versions and extraction candidates |
| Deliberately saved tire images | 30 days, explicit owner choice | Same privacy controls; no silent extension merely from viewing |
| Photo candidates and extraction artifacts | No longer than associated image | Retained confirmed facts in report are ordinary owner data, not a reusable image cache |
| Owner analysis output/attachments | Existing report retention, or 30 days if unattached | 7-day reuse validity does not extend retention; erase with owner/report; remove orphan entries and manifests |
| Shared reviewed generic artifacts | 30 days rolling retention maximum unless deliberately published through editorial workflow | Reuse ≤7 days/source validity; refresh creates new immutable revision; never shared by copying private inputs |
| Minimal AI attempt/cost records | 30 days with identifying links; thereafter only permitted deidentified aggregates | Raw debugging packets, if explicitly enabled, encrypted and ≤7 days; secrets/PII never operational logs |

Confirm these as product policies at the relevant privacy gate; upstream rights or deletion requests can shorten them. Deletion invalidates reuse entries first, cancels jobs, revokes access and purges image/artifact/manifest/attempt links and provider files where applicable. Jobs recheck tombstones after provider return to prevent recreation. Restore drills replay deletions before reopening access. Withdrawn processing cancels future inference; ordinary retained confirmed report facts follow the owner's report-retention/deletion choice.

Initial operational budgets to validate in P2: one active analysis per owner/key, a maximum of two automatic retries for retryable failures, 30-second provider attempt deadline and 2-minute total job deadline, bounded image/response sizes, SQL-backed admission and daily cost reservations. Owner-approved monetary caps are required before activation. SQL budget windows/reservations serialize admission and settle each attempt once; uncertain charged attempts remain reserved until reconciled. Retries reserve their own upper bound, and a provider price change requires revised limits before calls resume. Circuit breaker or budget exhaustion returns assistance unavailable while the deterministic product stays usable. Measure accepted/rejected/refused outputs, citation failures, correction rates, warm-hit rate, invalidations, stale-result rejection, p50/p95 latency, cost per successful analysis/photo, provider errors, queue age and purge lag. Co-locate/bound SQL pools and jobs so AI maintenance does not consume report capacity.

## APIs and TDD acceptance

Planned L2 routes: `POST /api/v1/reports/{id}/analyses` with expected report version/idempotency key; `GET /api/v1/analyses/{id}` and report attachment reads; `POST /api/v1/tire-photos` for upload intent; `POST /api/v1/tire-photos/{id}/finalize`; extraction/status reads; `POST /api/v1/tire-photos/{id}/confirm`; `DELETE /api/v1/tire-photos/{id}`. Owner capability/account, CSRF where applicable, body limits and quotas apply. Share tokens cannot upload, invoke AI, confirm fields or reveal private prompts/images. Public MCP tools cannot call owner endpoints without an appropriate authenticated grant. JSON responses expose states and reason codes, not provider internals.

Before implementation, write failing unit tests for canonicalization, policy/source expiry, matching and output validation; application scenarios for opt-in, hit/miss, withdrawal and fallback; real PostgreSQL tests for scopes, lease takeover, invalidation and publication races; API tests for every unauthorized/expired/changed-body case. At S5 add upload/confirmation accessibility, slow job/manual fallback and email/PDF attachment tests. UC14–UC16 and AT23–AT26 cover these paths. Pin synthetic/redacted model fixtures for deterministic CI, and run budgeted live evaluations before model/prompt/schema changes and release. A mock-provider pass is not an AI quality acceptance.

The release evaluation includes every existing safety golden case plus at least 50 specialist-reviewed explanation cases and 50 representative tire images across lighting, rotation, small/partial text and ambiguous markings. Require zero observed critical fitment/recall/condition misclaims, no unsupported critical numeric/citation claims, 100% enforced confirmation before field use, and documented per-field precision/abstention and human correction rates against agreed thresholds. Finite evaluation does not establish guaranteed safety; keep deterministic enforcement, user confirmation and monitoring. Failed critical cases block activation; do not lower the gate to meet a phase date.
