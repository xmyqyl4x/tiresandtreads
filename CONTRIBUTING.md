# Contributing to Tires and Tread

Application development has not started. The architecture and engineering specifications, as amended by the [PostgreSQL/build-order review](docs/11-postgresql-and-build-order.md), define implementation and review. The [four-phase/domain/AI amendment](docs/12-live-product-phases-and-gap-review.md), approved October 23, 2026, extends implementation scope while preserving historical approvals. Every phase must preserve a usable existing product.

1. Select a dependency-satisfied card from the [working project task list](docs/15-project-task-list.md), assign its owner/reviewer and link exact requirements. Confirm the preceding [S0–S6 construction gate](docs/04-implementation-plan.md#build-stages-and-exit-gates) is satisfied. Database → data access/entities → services → exposed APIs → product frontends is the required order, within each of the four live releases. Identify the phase and its complete API gate; future-phase schemas are not prerequisites for earlier UI. Start from the relevant [requirement](docs/05-requirements-traceability.md), work package, and [use case](docs/08-test-driven-development.md#use-case-catalogue). Specify normal, denied, boundary, and recovery behavior.
2. Use a focused `codex/` branch and a reviewable change. Follow the [test-driven cycle](docs/08-test-driven-development.md#required-development-cycle): demonstrate the intended failure, implement, refactor, then verify affected real integration boundaries.
3. Respect [package and API boundaries](docs/10-coding-standards.md), the [database design](docs/09-database-design.md), and the [approved decisions](docs/07-stack-and-layer-signoff.md#7-signoff-decisions). Shared application/domain logic serves all channels. SQL records, domain entities/value objects and wire DTOs remain distinct; no ORM-shaped public API. PostgreSQL replaces the removed analytics/cache/transport vendors; any new dependency needs a measured use case and decision record.
4. Include tests and migrations with the feature. Use real PostgreSQL for constraints, transactions, and tenant isolation; use synthetic data and allowlisted provider sandboxes. No production contacts in fixtures or previews.
5. For domain imports/AI/photos, follow the [source publication](docs/13-domain-data-and-imports.md) and [inference/reuse/confirmation](docs/14-ai-analysis-and-photo-design.md) contracts. Include source rights, source/model version invalidation, scoped retention and bounded cost/load evidence; model mocks do not prove quality.
6. Run the affected quality gates and link evidence in the PR. Exact commands will be defined and committed during E02; do not report a planned check as an executed test.
7. Update the master task ledger, task-card checkboxes, actual PR/commit/test evidence, traceability, contracts, operational documentation, and relevant design decisions. Mark Accepted only when the declared outcome is verified; phase release cards also require the live production journey. Changes to scope, permissions, rankings, or architecture need an explicit rationale and review.

Documentation-only work uses link/structure/consistency checks. Implementation is complete only when the [definition of done](docs/08-test-driven-development.md#definition-of-ready-and-done) is satisfied.

The [deployment/local-environment proposal](docs/16-deployment-and-local-environments.md#local-validation-before-github) defines the requested workflow for testing locally before GitHub push, then verifying independently in CI and on the selected host. Local setup and verification commands will be implemented in P1-PR-002; do not report them as available today or reset existing workstation resources to approximate them.
