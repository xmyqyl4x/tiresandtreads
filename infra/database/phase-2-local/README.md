# Opt-in local Phase 2 migrations

This reviewed SQL track is for the owner's early local P2-PR-002 groundwork. The default application/CMS manifests, production bootstrap/CLI/preflight, role inventory and P1 generated models stay at their current baseline. No runtime or CLI discovers this directory automatically. Only fixed disposable test support applies it with the existing restricted-owner migration runner after the complete P1 history. Persistent dev/stage and hosted targets are outside this scope.

`app/manifest.json` binds the exact P1 manifest bytes and the local extension source hash. The installer refuses an unreviewed base, missing/unlisted source or changed checksum. The extension shares the existing transaction/advisory-lock migration protocol and appends to the disposable database's history; it never rewrites the 33 P1 entries. A repeated install is a no-op. The current production preflight does not admit an extended local database; no compatibility or admission change is claimed.

## Storage and permission contract

| Organization         | `organizations`, `memberships`, `organization_assets`, `agreements`, `verification_records`, `locations`, `organization_domains` | Tenant keys/FKs, private organization asset binding, versioned noncharging terms, verified-domain evidence, current membership and missing-context denial                                      |
| Offers               | `offers`, `offer_versions`, `offer_targets`                                                                                      | Deferred own-version pointer, reviewed immutable terms/targets, seven specified discount types, three-day minimum validity, explicit SKU/location scope and superseded-version linkage         |
| Codes and selection  | `coupon_pools`, `coupon_codes`, `coupon_reservations`, `offer_decisions`                                                         | Same-tenant/version/pool/code references, bounded ciphertext/HMAC metadata, one live unique code, slots 1–3 and one organization per send; decisions are append-only                           |
| Limits               | `frequency_guards`, `frequency_reservations`, `offer_cap_windows`, `cap_reservations`                                            | Stable subject/scope across organizations, explicit evaluated windows and policy; bounded counters and reservation links. Atomic allocation/reconciliation belongs to the later S2/S3 services |
| Corrections/disputes | `redemption_events`, `disputes`, `dispute_events`                                                                                | Immutable correction/reversal history, same-tenant/same-reservation parents, encrypted private details and reported-redemption semantics; no billing/verified-sale claim                       |
| Insights             | `insight_heads`, `daily_metrics`                                                                                                 | Generation-scoped internal aggregates and a tenant projection with reviewed current generation and cohort suppression; no recipient or visitor identity in partner output                      |

All partner-owned children carry `org_id`, an organization FK and compound tenant parent FKs, including grandchildren. Cross-organization subject frequency controls are worker-only. Forced RLS applies to the new tables. Tenant reads require both transaction-local organization and current active actor membership; missing, foreign or revoked context denies reads. Runtime credentials remain server-only: setting context is not external authentication, and the future API/service must derive it from a verified actor on one transaction connection.

The local roles are `tt_p2_partner_runtime` (own safe projections), `tt_p2_staff_runtime` (review/provisioning metadata) and `tt_p2_worker_runtime` (private code/selection/limit/aggregate work). They neither own tables nor have superuser, role/database creation, inheritance or RLS bypass. Existing P1 roles get no new schema access. Test support creates fresh role credentials only in its admitted disposable cluster; this is not a production role-provisioning command.

Shared coupon text is encrypted on a shared-mode pool. Shared reservations have no exclusive code ID. Unique/generated pools use individual code IDs and the one-live-assignment constraint. Composite pool-mode and pool/version references keep these modes distinct. This preserves FR-RSL-08's shared/generated/unique semantics without allowing an exclusive code to be double-assigned. Plaintext codes and subject/send links remain unavailable to tenant readers.

The opt-in extension adds an `(id, owner_subject_id)` unique key to the existing `email.email_sends` table solely to enforce compound send/subject references. It changes no P1 row, trigger, grant or original migration checksum. Other new objects live in `partners`. Ordinary records default to pending/draft/quarantined states; no service consumes these tables in the running P1 application.

P1 already owns consented visitor events and analytics deletion/replay. Do not duplicate visitor capture here. Only the missing organization aggregate dimension is added. Existing privacy services are not claimed to erase the new graph: P2 service/privacy integration, purge ordering, invalidation and restore/deletion replay must be accepted before real data or production promotion. Application rules still own consent, verified staff, source/coupon terms, allocation locks, rolling/calendar policies, reconciliation and privacy-safe publication.

## Promotion boundary

P2-PR-005's actual upgrade/schema gate and later privacy/service/API gates remain open. Before ordinary migration promotion, review the then-current base/order/checksums, actual owner/role provisioning, P1/client upgrade compatibility, RLS/grants, indexes, complete private-data purge/restore graph and deployment rollback evidence. Production-host selection, operators, provider/model/cost decisions, pilot agreements and all current acceptance/deployment holds persist. Local proof or merge does not authorize target provisioning, purchases, actual notifications, partner serving or a phase/gate closure.
